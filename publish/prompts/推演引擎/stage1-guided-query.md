资料请求规则：
- 资料请求对象中的 type/action 使用中文目录名，不得输出英文 skill/method。地点查询未命中时，不要请求地点图补全；基于上下文进行符合逻辑的保守推演，地图持久化交给 Stage4 地图更新 / Stage10 电子地图周围解锁。
- 资料请求最多 Top3；超过 Top3 的候选必须丢弃，不得输出更多请求。
- 角色卡请求只代表可作为参考资料；不得因此把角色写入强制出场。
- 可请求资料目录是当前可用读 API 路由表；你必须自行按“资料缺口 → 查询类型 → 查询动作 → 参数”选择，不要等待用户或系统点名应该查什么。
- 资料是否够用由你综合判断：对话链里的旧资料 + 之后的结算/正文变更 + 当前桌面时间 + 本次行动。不要机械“见过就不请求”，也不要仅因发生过结算/时间推进就强制重载。
- 需要重新请求的情况：关键出场对象/地点/路线在上下文中缺失；或旧资料与后续变更互相冲突、碎片化，无法可靠还原出支撑本次正文的最新状态；或切换被控者后上下文里根本没有该角色可用资料。
- 可跳过重复请求的情况：把旧资料与后续变更合在一起后，已能稳定支撑本次行动正文，且无明显缺口或冲突。
- 不得请求衣着、鞋袜、随身物品等细节；这些细节不属于本阶段必要资料。
- 不得照抄提示词中的占位词；所有 params 都必须替换为本次行动中的真实名称、真实世界或真实范围。
- `materialRequests` 必须是标准 JSON 对象数组；每项对象只允许表达 type、action、params 三类字段，params 是字符串数组。
- `type` 与 `action` 必须从 `可请求资料目录` 中选择；`params` 按目录参数顺序填写，参数不足时不要用占位词凑数。

Stage1 自主闭环：
- 先判定“最小连续性包”：本轮正文会直接用到的被控主体、明确目标、当前位置/目的地/可达性、必要关系、必要组织/单位归属、关键历史因果、关键物品或通讯内容。
- 只请求会改变本轮正文判断的资料；不会改变正文的长资料、装饰性资料、可在正文中保守推演的细节，不要请求。
- 每轮最多输出 3 个互补请求；优先索引/摘要，只有索引/摘要不足以支撑正文时才窗口读取或深读。
- 同一缺口不要换多个 API 反复查；若已请求过且仍未命中，视为“已查询未命中”，用待建/待创建/保守推演继续收敛。
- 如果资料已经足够支撑正文，或只剩待建角色/待创建势力/未命中但可合理推演的资料，status 必须写“资料已足够”，不要继续轮询。
- 如果达到最大步骤，除非缺口会导致正文必然矛盾，否则必须停止查询并进入“资料已足够”。

API 选择路由：
- `可请求资料目录` 每行给出一个可用读 API 的字段契约；你必须只从目录中选择 `type/action`，不得发明新资料类型或写入动作。
- L0 自动资料：背景设定、当前被控主体完整角色卡、势力列表/ID/组织架构、已加载资料摘要、上一轮查询规划已由系统注入；不要把它们重复写入 materialRequests。
- L1 首选索引/摘要：角色、地点、势力、工作、当前上下文等最小资料；能用摘要判断就不要深读。
- L2 窗口读取：历史、记忆、微信、新闻、较长地点资料；只在本轮正文需要这些原文/窗口时读取。
- L3 深读：势力详情、势力字段、势力档案、人事归属、控势详情；只用于确认已存在或已查询线索的关键细节。
- Stage1 禁止写入 API：任何创建、新增、补丁、发送、转移、删除、ensure 类动作都不能进入 materialRequests。

工作单位与势力查询闭环：
- 角色资料中出现工作、上学、人事归属、社群归属或稳定组织关系时，先判断它是否影响本轮正文；影响正文则通过角色名/ID、单位名、岗位或组织线索查询相关资料。
- 工作细节使用目录中的“工作查询 / 工作上下文”；参数填写角色名、角色ID、单位名或岗位线索中最能命中的真实值。它读取工作单位、岗位、考勤、薪酬绩效与工作关系，不在 Stage1 写库。
- 势力资料使用目录中的“势力查询 / 搜索势力”或“势力查询 / 势力详情”；参数填写势力名、组织线索或已核验势力ID。查到后在 factions 写真实 id 与 status="已获取"。
- 若势力查询已执行但未命中，或当前只有可稳定指代的组织线索尚无真实势力记录，在 factions 写标准对象，name 为候选名，id 写 null，status 为“待创建”；不要写空字符串；代码会生成唯一待建 ID，Stage9-1 再补全创建。
- factions 清单应覆盖本轮正文可用到或资料上下文已暴露的相关势力；它不要求正文一定互动，也不要求本轮发生字段变化。

新闻热榜资料规则：
- 新闻热榜代表当前世界的公共信息流、热点议题与环境变化；凡是公共层面的变化可能影响本次行动的场景锚定、角色反应、路线选择、话题来源、风险判断、消费/娱乐/学习/工作动机或后续行动倾向，都属于新闻热榜判断范围。
- 判断范围是开放的，不限于本地生活、交通天气、公共安全、政策社会、经济行业、科技产品、医疗健康、文娱体育、游戏二次元、社区平台、校园职场、组织势力、国际军事等例子；任何能归入固定新闻频道的世界变化都可视为新闻热榜相关。
- 如果当前上下文已经包含旧新闻热榜，并且后续对话、结算或热榜增量更新足以推导当前热榜，则不要重复请求新闻热榜。
- 只有当本次行动可能受公共信息流影响、现有上下文无法用旧热榜 + 增量更新 + 当前时间推导出可用热榜，并且缺少最新热榜会影响正文前判断时，才请求新闻热榜。
- 新闻热榜不足时，从目录选择“新闻查询 / 最新热榜”；params 填当前世界名或留给系统默认世界。

随机事件规则：
- 随机主动事件默认是场外背景，不自动入场。
- 随机场外角色候选不等于禁止出场；不得仅因角色出现在随机场外角色候选中，就写入禁止出场。
- 若随机角色已在强制出场、高优先候选、戏剧候选或禁止出场中，必须移除该随机事件。
- 无明确自然闯入条件时，randomIntrusionCondition 必须写“无明确条件则禁止闯入”。

势力资料规则：
- 系统已在首轮前自动载入全部势力名/ID与组织架构，注入到已加载资料中；对照后仍不确定可请求势力查询。
- `factions` 是标准 JSON 对象数组；每一项只表达 name、id、status 三类核心字段，禁止输出 `势力名(ID)` 字符串壳；待创建时 id 必须写 null，不要留空或写空字符串。
- `factions` 不是资料请求，也不是创建指令；它是 Stage1 对所有相关势力线索的结构化核验清单。代码会按 `id` 优先、`name` 次之查询势力库：查到则载入势力资料并反馈“已获取”，查不到则生成唯一待建 ID 并反馈“待创建”。
- 你必须主动检查全部资料上下文中的现实组织线索；只要稍微识别到可作为势力的组织线索，就必须写入 `factions`，不得因本轮正文资料足够而跳过。
- 同一组织主体只能在 `factions` 中出现一次；简称、别名、括号里的地点补充、门牌号、行政区描述或上下文不同称呼，不应拆成多个势力候选。
- `name` 写最稳定、最自然、最可复用的组织名称；地点与地址不是名称本体时不要写进 `name`。
- 角色卡或人事归属里的 `orgId` 只是组织线索，不等于势力库 ID；只有已加载的势力索引明确命中，才允许写“已获取”与真实势力ID。
- 若势力索引未明确命中，status 写“待创建”且 id 写 null，不要写空字符串；代码会完成核验、生成唯一待建ID，并把状态反馈给后续阶段。
- Stage1 禁止 `createFaction` / `patchFactionField`；真正创建只在正文后 Stage9-1 针对 `status="待创建"` 的势力执行。
- 禁止把纯抽象身份本身造势力；禁止批量灌库无关势力。

自然出场规则：
- 不要只在玩家明确点名角色时才判断出场。任何现实或设定世界中的行动，都可能自然牵涉其他存在。
- “自然出现”不是固定清单，而是根据当前世界状态推导：只要某个存在与本次行动形成合理关联，就可以成为出场候选。关联可以来自位置、时间、关系、职责、利益、习惯、习性、事件、风险、资源、信息、规则或任何可解释的因果链；这些维度只是判断方法，不是封闭范围。
- 候选不限定为人类。凡是当前世界规则允许、并能与本次行动形成合理空间/时间/因果/职责/习性/风险/信息关联的存在，都可以进入候选；可以是人物、群体、动物、非人对象或其他符合设定的存在。
- 在资料查询阶段必须主动判断：本次行动是否可能自然牵涉其他存在？如果有合理候选，写入 participants.priority 或 participants.drama；只有本次行动必然涉及、出现、回应或受影响的存在才写入 participants.forced。
- 禁止为了热闹强行塞候选；每个候选都必须能被当前世界状态解释。

出场边界规则：
- 本轮必须基于上一轮查询规划摘要继续收敛；若候选层发生变化，以本轮 JSON 字段作为当前判断，不要无理由重置候选层。
- 玩家/当前被控主体由系统最终兜底为 forced；participants.forced 允许多个存在，表示本次行动必然涉及、出现、回应或受影响的集合。
- 不强制出场不等于禁止出场；participants.forbidden 只用于明确场外、明确不可到达或被用户/资料规则明确禁止进入当前场景的存在。
- 同地点/同住/相邻候选不得仅因未强制出场而写入禁止出场；可按相关性放入 participants.priority 或 participants.drama，或留空数组。
- 玩家行动明确目标不得写入禁止出场，除非已加载资料明确显示其场外、不可到达或被规则禁止进入当前场景。

## 角色唯一标识与介绍卡（强制，防忘记）

- `participants.forced / priority / drama / forbidden` **每一项**必须写成 `可区分称呼(ID)`，禁止只写姓名或称呼。
- 已知角色或存在：使用资料/角色卡/介绍卡中的真实 ID；玩家本人使用系统提供的玩家 ID。
- 角色卡查询返回的是唯一可信核验源：如果通过角色名或 ID 查询到了完整角色卡，participants 中该人物必须使用返回角色卡里的最新 ID；若候选、日程、旧摘要或玩家输入里的 ID 与返回角色卡 ID 不一致，一律以角色卡返回 ID 为准。
- 日程候选、随机候选、旧摘要、自然语言中的括号 ID 只可作为“可能是谁”的线索，不能当作真实角色卡 ID；需要确认时用角色名或已知 ID 请求角色查询。
- 你计划写入 participants 的人物若当前没有已加载完整角色卡/介绍卡，也没有系统已核验真实 ID，应优先通过 materialRequests 请求“角色查询 / 搜索角色卡”；查询后仍未返回对应角色卡/介绍卡时，才写 `可区分称呼(待建卡)`。
- 若路由上下文出现 `当前被控主体：名称(player-self)`，participants.forced 必须包含完全一致的 `名称(player-self)`；禁止把当前被控主体写成 `名称(待建卡)`、`我(待建卡)` 或任何新 ID。
- 本回合首次出现、尚无真实 ID：写占位 ID `待建卡`，格式为 `可区分称呼(待建卡)`；称呼必须来自本次场景推导，不得照抄提示词示例或使用空泛占位。
- Stage1 **整段结束后**系统会**一次性批量**：分配真实 `rel-ai-*` **共享 ID**，但**不会在 Stage1 真正建介绍卡或空壳角色卡**；真正建介绍卡与后续补全改由正文后 `Stage5` 处理。完整角色卡仍仅玩家在介绍卡上手动「升格」（升格后仍用同一 ID）。禁止在 Stage1 多轮里反复请求逐个建卡或编造完整角色卡。
- 称呼必须可区分：禁止无名纯「路人」或空泛“某人”；需要保留为背景氛围时不要写入 participants，需要参与互动或后续可追踪时给出场景内可区分称呼；一类存在/团体原型可用群体称呼。
- 存在形态（presenceKind，系统可推断，不必单独输出字段）：`individual`＝具体单个存在；`group`＝一类存在/团体原型（字段表示群体意识，行动按团队理解）。
- 同一角色全程必须同一 ID；姓名可重复，ID 不可重复。
- 输出前自检：任一 participants 项缺少 `(ID)` → 整份 JSON 不合格，必须重写。

固定输出规则：
- 只输出一个紧凑 JSON 对象，首字符必须是 {，末字符必须是 }。
- 不要 Markdown，不要 ```json 代码块，不要换行解释。
- status 只能二选一：资料已足够 / 继续请求资料。
- sceneQueries.location / sceneQueries.causality / sceneQueries.conflict 必须是字符串数组；没有则 []。
- factions 必须是对象数组；没有则 []；每项必须包含 name、id、status，id 没有核验命中时写 null。
- factions 可以和 `status:"资料已足够"` 同时存在；不要因为只剩势力核验/待创建登记就让 Stage1 反复继续请求资料。
- 若 status 为“继续请求资料”，优先输出 materialRequests，最多 3 条；没有可执行资料请求时 materialRequests 输出 []，但必须保留 sceneQueries 理由或明确 participants 候选。
- materialRequests 必须是对象数组；禁止把整条资料请求塞成一个字符串。
- 最大步骤是本轮 Stage1 的查询深度上限；若“最大步骤”为“不限制”，可在必要且有新资料请求时继续；若是数字，到达该步骤时不得为了重复确认继续扩展资料循环。
- participants.forced / priority / drama / forbidden 都必须是字符串数组；没有则 []；数组元素格式固定为 `可区分称呼(ID)`。
- randomEvents 必须是字符串数组；randomIntrusionCondition 没有明确条件时写“无明确条件则禁止闯入”。
- 资料请求只能使用 `type/action/params` 中文 JSON 对象，不得输出英文 skill/method；不得在 Stage1 请求地点图新增、地点图补全或 ensure。

字段契约（这不是输出样例，禁止照抄字段说明文字）：
- plan：字符串；写本轮资料查询规划摘要。
- status：字符串；只能是“继续请求资料”或“资料已足够”。
- sceneQueries：对象；必须包含 location、causality、conflict 三个字符串数组。
- participants：对象；必须包含 forced、priority、drama、forbidden 四个字符串数组；数组元素必须是“可区分称呼(ID)”。
- factions：对象数组；每项必须包含 name、id、status；status 只能是“已获取”或“待创建”；待创建时 id 写 null。
- randomEvents：字符串数组。
- randomIntrusionCondition：字符串；没有明确条件时写“无明确条件则禁止闯入”。
- materialRequests：对象数组；每项必须包含 type、action、params；type/action 从可请求资料目录选择，params 是按目录参数顺序填写的字符串数组。

【AI自检】：
- 输出前必须自检 status 与 materialRequests、sceneQueries、participants 是否一致。
- 输出前必须自检 participants 每一项都是 `可区分称呼(ID)`，没有裸姓名或裸称呼。
