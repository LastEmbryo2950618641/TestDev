# 角色卡初始数值组生成

只返回一个合法 JSON 对象，不要 Markdown、代码块或解释。请尽量沿用下方完整 JSON 骨架的结构，只改 value/status/reason。先数清字段列表数量，再逐项输出，输出前不要自行挑选“相关项”。本请求通常只包含少量 key，请尽量不要漏掉字段。

## 任务

为人物“{人物姓名}”生成初始{数值组名称}数值。

根字段必须是 `{根字段}`，值是数组。

本次只生成字段列表里的这些 key：{字段列表}。

数组应只包含字段列表中的对象，不要额外生成其他 key；字段列表有几个 key，数组就应有几个对象。即使某个 key 证据很弱，也请输出该 key，避免只输出最有感觉的一项。

## 参数说明

| 参数 | 含义 | 生成时如何使用 |
| --- | --- | --- |
| `{人物姓名}` | 当前要生成数值的人物本人 | 所有数值都必须围绕这个人物本人，不要写成玩家或其他联系人。 |
| `{数值组名称}` | 当前数值组的中文名称，通常是“情绪”或“对玩家感觉” | 决定 value/status/reason 的判断视角。 |
| `{根字段}` | JSON 根字段，只能是 `emotions` 或 `playerFeelings` | 返回 JSON 必须使用这个根字段，不能换成别名。 |
| `{字段列表}` | 本轮要生成的 key 列表 | 只生成这些 key，顺序、名称、数量都必须一致。 |
| `{完整JSON骨架}` | 由代码生成的标准输出结构 | 必须复制结构，只改每项的 `value`、`status`、`reason`。 |
| `{人物角色卡}` | 当前人物的姓名、身份、关系、背景、外貌、性格、社群、势力 | 判断数值的第一证据来源。 |
| `{玩家资料}` | 玩家姓名、身份、家庭、关系、备注等完整激活信息 | 生成 `playerFeelings` 时必须重点参考。 |
| `{世界观资料}` | 当前世界背景与势力等 | 用于判断人物处境是否合理。 |
| `{世界字段}` | 当前世界可用的 RPG 字段 | 仅作为背景参考，不要输出到本 JSON。 |
| `{剧情关系事件}` | 微信联系人、关系同步或剧情上下文 | 用于判断人物与玩家之间的具体关系证据。 |

## 字段语义

| 字段 | 类型 | 含义 | 写法要求 |
| --- | --- | --- | --- |
| `key` | string | 固定数值名，必须来自字段列表 | 不能改名，不能翻译，不能新增。 |
| `value` | number | 0-100 的当前初始数值 | 按证据判断，骨架里的 0 只是占位。 |
| `status` | string | 当前数值状态解释 | 说明“这个 key 为什么是当前数值/阶段”。 |
| `reason` | string | 形成该数值的具体原因 | 说明“是什么经历、处境、动机或关系证据造成这个值”。 |

## 完整 JSON 示例

```json
{"playerFeelings":[{"key":"了解","value":72,"status":"了解因为长期同住让她熟悉玩家作息习惯","reason":"了解源于多年家庭生活积累出的具体观察和相处经验"},{"key":"信任","value":80,"status":"信任因为玩家长期承担照顾者责任","reason":"信任源于她在家庭变故后持续依靠玩家处理生活问题"},{"key":"依赖","value":88,"status":"依赖因为现实生活和情感安全都倚重玩家","reason":"依赖源于同住处境、家庭缺口和长期被玩家保护的经历"}]}
```

示例只说明结构和写法；实际输出必须使用本轮 `{根字段}` 与 `{字段列表}`，不得照抄示例 key 或数值。

## 生成规则

1. 每一项都必须只有 `key`、`value`、`status`、`reason` 四个字段；`reason` 是强制字段，不能因为 status 已经很长就省略。
2. 字段顺序必须固定为 `key` → `value` → `status` → `reason`，每个对象都必须写完四个字段。
3. `reason` 必须写在同一个对象内部，禁止写成数组里的独立字符串或对象外字段；禁止出现 `},"reason"`、`],"reason"`、`"status":"..."}` 这类漏 reason 结构。
4. 每个对象必须以 `reason` 作为最后一个字段；写完 `reason` 后必须立刻用 `}` 结束当前对象，再用逗号进入下一个对象。
5. 禁止重复字段名，尤其禁止在同一对象里写两个 `key`、两个 `status` 或两个 `reason`；不要把下一个 key 写进当前对象。
6. 必须按“字段列表”和“完整 JSON 骨架”的顺序逐项生成，每个 key 精确出现一次，不能漏项、不能多项、不能改名。
7. `value` 是 0-100 数字，由 AI 按当前人物性格、处境、经历、关系证据、玩家资料、世界观和剧情事件判断；骨架里的 0 只是占位，不得照抄为默认值。
8. 生成 playerFeelings 时必须优先读取玩家资料和剧情/关系事件；若证据中存在亲属、恋人、暧昧、依赖、占有、肉欲、畏惧、尊敬、支配等明确关系，相关 key 必须给出匹配数值，不能写成 0。
9. 只有证据明确缺乏对应关系、冲动或情感时，对应的亲情、爱情、肉欲、依赖、占有欲等才允许为 0。
10. `status` 必须是 20-50 个汉字的短句，必须以当前 key 开头，使用“{当前key}因为……”或“{当前key}源于……”句式。
11. `reason` 必须是 20-50 个汉字的短句，必须以当前 key 开头，使用“{当前key}因为……”或“{当前key}源于……”句式。
12. `reason` 必须写形成该数值的具体原因，结合角色动机、处境与过去经历；不能和 status 完全重复，不能只写抽象性格词。
13. 证据弱或没有触发时 `value` 可以为 0，但也必须输出该 key，例如“嫉妒因为暂无竞争对象”。
14. 禁止写“默认、初始化、根据上下文、系统生成、综合判断、阶段定义、背景信息、个人动机与过去经历”等空话。
15. 不要返回英文 key、`initial_metrics`、`affection`、`dependency`、`trust_level` 等替代结构。
16. 输出过程按字段列表逐项完成：先写第1项，再写第2项，直到最后一项；禁止只写你认为最相关的项。
17. 只返回一行紧凑 JSON；不要 Markdown 代码块，不要换行，不要解释。

## 返回格式

只返回上方“完整 JSON 骨架”对应的完整对象。数组长度应等于字段列表里的 key 数量；不要只返回第一项，不要额外补充其他 key。
