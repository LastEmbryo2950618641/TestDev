# 角色卡初始数值组生成

只返回纯文本行格式，不要 Markdown、代码块、JSON、解释或额外标题。每个 key 单独一行，格式固定为：key,value,status,reason。先数清字段列表数量，再逐项输出，输出前不要自行挑选“相关项”。本请求通常只包含少量 key，请不要只输出前三项，也不要漏掉字段。

## 任务

为人物“{人物姓名}”生成初始{数值组名称}数值。

本次只生成字段列表里的这些 key：{字段列表}。

每个 key 必须输出一行，行数必须等于字段列表数量。即使某个 key 证据很弱，也请输出该 key，避免只输出最有感觉的一项。

## 参数说明

| 参数 | 含义 | 生成时如何使用 |
| --- | --- | --- |
| `{人物姓名}` | 当前要生成数值的人物本人 | 所有数值都必须围绕这个人物本人，不要写成玩家或其他联系人。 |
| `{数值组名称}` | 当前数值组的中文名称，通常是“情绪”或“对玩家感觉” | 决定 value/status/reason 的判断视角。 |
| `{根字段}` | 当前代码接收的数值组标识，只能是 `emotions` 或 `playerFeelings` | 只作为上下文参考，不要输出。 |
| `{字段列表}` | 本轮要生成的 key 列表 | 只生成这些 key，顺序、名称、数量都必须一致。 |
| `{完整行格式骨架}` | 由代码生成的标准输出行 | 必须复制行数和 key，只改每行的 `value`、`status`、`reason`。 |
| `{人物角色卡}` | 当前人物的姓名、身份、关系、背景、外貌、性格、社群、势力 | 判断数值的第一证据来源。 |
| `{玩家资料}` | 玩家姓名、身份、家庭、关系、备注等完整激活信息 | 生成 `playerFeelings` 时必须重点参考。 |
| `{世界观资料}` | 当前世界背景与势力等 | 用于判断人物处境是否合理。 |
| `{世界字段}` | 当前世界可用的 RPG 字段 | 仅作为背景参考，不要输出到本 JSON。 |
| `{剧情关系事件}` | 微信联系人、关系同步或剧情上下文 | 用于判断人物与玩家之间的具体关系证据。 |

## 行格式语义

每行固定 4 段，用英文逗号分隔：

```txt
key,value,status,reason
```

| 段位 | 类型 | 含义 | 写法要求 |
| --- | --- | --- | --- |
| `key` | string | 固定数值名，必须来自字段列表 | 不能改名，不能翻译，不能新增。 |
| `value` | number | 0-100 的当前初始数值 | 按证据判断，骨架里的 0 只是占位。 |
| `status` | string | 当前数值状态解释 | 说明“这个 key 为什么是当前数值/阶段”，不要包含英文逗号。 |
| `reason` | string | 形成该数值的具体原因 | 说明“是什么经历、处境、动机或关系证据造成这个值”，不要包含英文逗号。 |

## 完整行格式示例

假设 `{字段列表}` 是 `了解、信任、依赖`，合法返回示例是：

```txt
了解,72,了解因为长期同住让她熟悉玩家作息习惯,了解源于多年家庭生活积累出的具体观察和相处经验
信任,80,信任因为玩家长期承担照顾者责任,信任源于她在家庭变故后持续依靠玩家处理生活问题
依赖,88,依赖因为现实生活和情感安全都倚重玩家,依赖源于同住处境家庭缺口和长期被玩家保护的经历
```

示例只说明结构和写法；实际输出必须使用本轮 `{字段列表}`，不得照抄示例 key 或数值。

## 生成规则

1. 每一行都必须只有 `key,value,status,reason` 四段；`reason` 是强制段，不能因为 status 已经很长就省略。
2. 段位顺序必须固定为 `key` → `value` → `status` → `reason`，每一行都必须写完四段。
3. 必须按“字段列表”和“完整行格式骨架”的顺序逐项生成，每个 key 精确出现一次，不能漏项、不能多项、不能改名；字段列表有 6 个就返回 6 行，有 10 个就返回 10 行。
4. `value` 是 0-100 数字，由 AI 按当前人物性格、处境、经历、关系证据、玩家资料、世界观和剧情事件判断；骨架里的 0 只是占位，不得照抄为默认值。
5. 生成 playerFeelings 时必须优先读取玩家资料和剧情/关系事件；若证据中存在亲属、恋人、暧昧、依赖、占有、肉欲、畏惧、尊敬、支配等明确关系，相关 key 必须给出匹配数值，不能写成 0。
6. 只有证据明确缺乏对应关系、冲动或情感时，对应的亲情、爱情、肉欲、依赖、占有欲等才允许为 0。
7. `status` 必须是 20-50 个汉字的短句，必须以当前 key 开头，使用“{当前key}因为……”或“{当前key}源于……”句式。
8. `reason` 必须是 20-50 个汉字的短句，必须以当前 key 开头，使用“{当前key}因为……”或“{当前key}源于……”句式。
9. `reason` 必须写形成该数值的具体原因，结合角色动机、处境与过去经历；不能和 status 完全重复，不能只写抽象性格词。
10. 证据弱或没有触发时 `value` 可以为 0，但也必须输出该 key，例如“嫉妒,0,嫉妒因为暂无竞争对象,嫉妒源于当前关系中没有明确竞争者”。
11. 禁止写“默认、初始化、根据上下文、系统生成、综合判断、阶段定义、背景信息、个人动机与过去经历”等空话。
12. 不要返回英文 key、`initial_metrics`、`affection`、`dependency`、`trust_level` 等替代结构。
13. 输出过程按字段列表逐项完成：先写第1行，再写第2行，直到最后一行；禁止只写你认为最相关的项。
14. status 和 reason 内不要使用英文逗号 `,`；需要停顿时用中文逗号 `，`。
15. 只返回纯文本行；不要 JSON、不要 Markdown 代码块、不要标题、不要解释。

## 返回格式

只返回上方“完整行格式骨架”对应的完整多行文本。行数应等于字段列表里的 key 数量；不要只返回第一行，不要额外补充其他 key。
