# 出场人物固化设定

为 AI RPG 视觉小说生成出场人物固化设定。只返回 JSON，不要 Markdown，不要解释。

## 变量区说明

这个模板中的变量不是抽象说明，而是由代码按游戏 UI / 数据区域组织后填充的内容。调整提示词时，应围绕这些变量区规定 AI 如何使用对应数据。

## 人物预设资料区

来源：只有在该人物命中本地人物索引并成功读取预设 md 时才会填入；否则显示无预设。

{人物预设资料区}

使用规则：
1. 如果这里有“预设人物 md”，该人物是主要/预设人物，姓名、身份、年龄、性别、原作背景优先遵循该 md，再结合当前事件补足状态。
2. 如果这里显示“无预设人物 md”，该人物不是预设人物，不得套用当前主角或其它预设角色资料；必须只根据人物基础区、玩家资料区、关系事件区和世界观资料生成。
3. 无预设人物的年龄、性别、身份、关系必须来自上下文明确证据；没有证据时生成合理短档案，但不得读取或继承当前主角年龄。

## 人物基础区

来源：候选人物资料，可能来自原作角色、微信联系人、玩家关系或剧情临时人物。

{人物基础区}

使用规则：
1. 最终角色卡必须固化“候选人物”本人；候选姓名是正式姓名时不得改成亲属、联系人或关系事件里的其他人。
2. 候选姓名若是“妹妹/父亲/联系人”等称谓，必须结合命名要求和玩家资料生成正式姓名。
3. 身份/关系/叙事定位不能直接当职业。
4. 人物背景摘要、外貌线索和性格线索只作为证据，不得无依据扩写亲密关系。
5. 外貌必须单独固化到 appearance，性格必须单独固化到 personality，不要把二者混入 detail。
6. 已整理关系为空时，不要编造关系；必须从下方玩家区、微信区或剧情区找证据。
7. 无预设人物必须把关系事件区当作最重要来源：例如“默认账号妹妹/微信妹妹/剧情中新出现的人”都要按上下文生成独立角色卡，而不是继承当前主角资料。

## 玩家基础资料区

来源：手机激活页“姓名 / 性别 / 生日”输入与年龄计算。

{玩家基础资料区}

使用规则：
1. 这些字段确定玩家本人，不是当前待生成人物。
2. 亲属、同学、同事、同居者等联系人必须与玩家年龄、性别、生日逻辑相容。

## 玩家现实身份区

来源：手机激活页“现实身份”输入、AI 补全后的工作/学校/组织与地位，以及世界观补全。

{玩家现实身份区}

使用规则：
1. 现实身份决定联系人来源：学校、公司、社区、家庭、社交圈等。
2. 工作/学校/组织与地位可以影响人物 role、detail、rank，但不要直接塞进 job。
3. 世界观补全用于补足现实处境，不得覆盖明确玩家输入。

## 玩家居住家庭区

来源：手机激活页“具体地址 / 居住状态 / 父母信息”，以及 AI 补全后的详细地址、居住状态、父母状态、父母去世原因。

{玩家居住家庭区}

使用规则：
1. 地址决定地域文化、生活圈、姓名风格和人物行动范围。
2. 居住状态决定是否同居、照顾、依赖、合租、宿舍等关系强度。
3. 父母状态和死因会影响兄弟姐妹、监护、家庭创伤、亲情和依赖。

## 玩家人际关系区

来源：手机激活页“与你相关的人际关系”区域。

{玩家人际关系区}

使用规则：
1. 这是生成玩家关系联系人时的最高优先级关系证据。
2. 只固化这里明确写出或能由其直接推理的关系。
3. 不要擅自新增玩家未填写的重要亲密关系。

## 玩家备注区

来源：手机激活页“补充设定”区域。

{玩家备注区}

使用规则：
1. 备注必须参与关系、性格、生活压力、秘密、目标、边界和初始数值推理。
2. 如果备注说明某段关系紧张、隐藏、依赖、疏远、恋爱倾向、身体吸引或占有欲，initialMetrics 必须体现。
3. 不得忽略备注，也不得把备注当成无关旁白。
4. 若资料存在年龄冲突，必须优先采用明确成年、现实合法且与居住状态一致的设定；不要把未成年角色写入恋爱或身体吸引相关指标。

## 关系事件区

来源：调用人物固化时传入的具体上下文，例如微信联系人资料区、当前剧情、原作证据或事件原因。

{关系事件区}

使用规则：
1. 若该区域来自微信联系人资料，必须优先解释此联系人与玩家的微信关系。
2. 若该区域来自剧情事件，必须说明人物为什么在当前事件中出现。
3. 关系事件区不能覆盖玩家已填写的核心资料，只能补足当前人物相关证据。

## 世界观资料区

来源：世界观固化资料，包括世界背景、势力、特殊职业和职业等级。

{世界观资料区}

使用规则：
1. 现代现实人物优先遵循 2026 现代都市逻辑。
2. 原作/异世界人物优先遵循所属作品设定。
3. 社群角色和势力地位都是角色卡必要信息：社群角色用于说明“属于哪个社区/家庭/社交圈并在其中是什么角色”，势力地位用于说明“在有等级制度的势力里处于什么组织层级和职位”。

## 社群角色规则

1. 必须返回非空 factions 数组，每项包含 faction 与 role；显示会合并为“社群 / 角色”。
2. faction 只表示居住社区、家庭、社交圈、临时群体、生活圈或无层级公共地点；role 是其在其中承担的社会角色，不是等级。
3. 同一角色可以有多个社群角色，最多 4 个；例如“锦苑小区3栋2单元601号 / 居民”、“刘悠家庭 / 同居妹妹”、“本地跑团社群 / 群友”。
4. 玩家亲属或同住者必须根据玩家具体地址补出居住社群；如果住址具体到小区楼栋门牌，优先使用该具体住址作为 faction，role 写“居民/同住者/家庭成员”等。
5. 若角色既不是居民、学生、工作者，也不属于任何组织，必须在 factions 写出特殊处境，例如“城市街头 / 流浪者”、“临时避难点 / 滞留者”，并在 detail 备注原因。
6. 原作/异世界角色也必须返回社群角色，例如“冬木市 / 居民”、“远坂家 / 家庭成员”、“圣杯战争相关者 / 参战者”。
7. 学校、公司、科室、部门、军队、教会、宗门、贵族家族、魔术家系等有等级制度的归属，不要只写入 factions；必须同时或优先写入 forcePositions。

## 势力地位规则

1. 必须返回非空 forcePositions 数组，每项包含 force 与 position；显示会合并为“势力 / 地位”。
2. 已知势力库出现的国家级势力也可作为 force；现代中国居民通常应包含“中华人民共和国 / 公民”，不要新造同义国家名。
3. 其他 force 必须有内部层级、职级、年级、职位或等级划分，例如公司、学校、科室、部门、军队、宗门、教会、贵族家族、魔术家系。
4. force 写组织架构中的具体势力层级，现代公司至少到公司级；医院可到科室，学校可到学校或年级。
5. position 必须是该势力内的法定身份、职位、年级、职级或等级，例如“公民”、“高三学生”、“高级后端工程师”、“研发二部经理”、“急诊科主治医师”、“家主”。
6. 只有“居民/同住者/妹妹/朋友/联系人/路人”这类普通社会角色时，不要因此新增组织势力；但若其处于现代中国现实世界，仍可保留国家级公民地位。
7. 现代亲属或同住者必须按年龄和上下文判断学校/工作/特殊状态：有学生证据写“具体学校或合理学校 / 高三学生、大学生”等；有工作证据写“公司或部门 / 岗位职级”；两者都没有时，detail 必须说明待业、辍学、自由职业、家庭照料或其他原因。
8. 势力地位最多 4 个；不要用 forcePositions 表示住址居民身份。

## 命名规则

1. 姓名必须是人物正式姓名，不得是“妹妹、父亲、联系人、微信好友、同事”等关系称谓。
2. 若人物基础区含命名要求，必须严格执行。
3. 不要硬套同姓：母亲、配偶、继亲、养亲、朋友、同事可能不同姓。
4. 亲属命名要符合玩家地址、地区文化、家庭结构与玩家资料。
5. 若无法确认姓名来源，可结合文化习俗生成合理姓名，但不要写“未知/待补全/需要AI生成”。

## 关系固化规则

1. relationships 只写已经可从玩家区、人物区、关系事件区或世界观区推理出的关系。
2. 格式必须是“关系：姓名”，多项用中文分号分隔。
3. 不要照抄长描述，例如不要写“妹妹：需要AI按现实世界观生成姓名”。
4. 不要擅自新增玩家未填写的重要亲密关系。
5. 如果是玩家亲属，要让 relationships 与玩家资料、居住状态、父母状态互相吻合。
6. 如果是微信联系人，要体现其与玩家的微信关系，而不是只写泛泛身份。

## 职业固化规则

1. 职业是人物内化能力、长期训练、资格或专业经验，不等同当前公司、学校、雇佣状态或叙事标签。
2. 学生、妹妹、父亲、主角、配角、悲剧核心、联系人不是职业；这些必须写入 role 或 factions.role。
3. 只有百分之百确认该角色拥有职业时，才返回 job 且 jobConfirmed=true。
4. 不确定时 job 为空字符串，jobConfirmed=false，但仍必须通过 factions 写出住址、家庭、社区、社交圈或特殊处境；如存在公司/学校/部门等层级势力，则通过 forcePositions 写出其势力地位。
5. 职业一旦提出会落库固化，所以不能为了丰富人物而硬造职业。
6. rank 只是兼容字段，来自 forcePositions[0].position；正式展示统一以 forcePositions 势力地位列表为准。

## 世界属性规则

worldValues 只返回有明确依据的字段：{世界字段}。

1. 只填世界专属字段，不要把通用属性混进 worldValues。
2. 没有证据的字段不要返回。
3. 返回值必须是可落库的短值，不要写长段解释。
4. 若字段与人物基础冲突，以当前人物固化资料为准。

## 初始情绪与对玩家感觉

必须返回 initialMetrics，用于该非玩家角色第一次生成时的情绪和“其余”关系数值。数值必须与变量区证据一致，不得使用默认值敷衍；这是强校验字段，缺少任意情绪 key、任意对玩家感觉 key、任意 value 或任意 reason 都会导致 JSON 被判定失败。

### 情绪维度

可用情绪字段：{情绪字段}

- 担忧：角色对处境、家人、玩家或风险的担心。
- 悲伤：丧亲、创伤、失落、分离导致的低落。
- 紧张：面对未知、冲突、危险或压力的反应。
- 恐惧/愤怒/屈辱等：按上下文选择，不要机械填充。

### 对玩家感觉维度

可用对玩家感觉字段：{关系指标字段}

- 亲情：玩家亲属通常应高于 0，但若证据显示长期伤害、疏离、虐待、抛弃、欺骗或被迫断亲，也可以为 0；无论数值高低，reason 必须写清具体家庭经历。
- 了解：长期相处、共同生活、同学同事、亲密关系不应接近陌生人；若为 0，必须说明为什么完全不了解。
- 信任：被照顾、共同经历、依赖关系会提高信任；若为 0，必须说明背叛、伤害、恐惧或缺乏接触等具体原因。
- 依赖：经济、心理、生活照料、丧亲后的共同生活会提高依赖；若为 0，必须说明独立、疏远、敌对或没有现实依靠的具体原因。
- 爱情：成年角色资料明确写出恋爱、爱意、心动、爱慕、超越亲情等证据时必须高于 0；没有恋爱依据时保持 0。
- 肉欲：成年角色资料明确写出身体吸引、欲望、暧昧试探、性吸引等证据时必须高于 0；没有身体吸引依据时保持 0。
- 占有欲：资料明确写出占有、嫉妒、排他、独占倾向时必须高于 0。

### 初始数值规则

1. 情绪与对玩家感觉都属于角色状态词条；首次生成时只要返回某个数值，就必须同时返回具体 reason，说明该值来自哪段关系事实、经历、家庭处境、互动历史或当前事件。
2. reason 禁止写“初始化”“根据角色资料推理”“根据上下文判断”“首次生成”“系统结算”这类空话；必须写成可落库的事实原因，例如“过去哥哥长期欺负她，她虽然有血缘关系但感受不到亲情”，或“父母已故后兄妹相依为命，她把哥哥视为唯一家人”。
3. 如果该角色是玩家妹妹、姐姐、父母、子女、配偶等亲属，亲情通常应明显高于 0；但若上下文显示长期伤害、疏离、虐待、抛弃、欺骗、怨恨或断亲，亲情可以为 0，必须在 reason 写清具体负面经历。
4. 亲情、爱情、肉欲、占有欲彼此独立：同一个成年角色可以同时拥有很高亲情、很高爱情、很高肉欲和很高占有欲；不得因为亲情已高就把爱情或肉欲压成 0。
5. 如果上下文显示共同生活、父母去世、经济或心理依靠、被玩家照顾等，依赖、信任、了解应相应提高；若这些值为 0，reason 必须解释为什么这些证据仍不足以形成该感受。
6. 如果上下文显示长期亲密相处，了解不应接近陌生人；若了解为 0，必须说明失忆、隐瞒身份、长期分离或从未真正接触等原因。
7. 如果玩家备注或关系事件明确写出成年角色对玩家有恋爱倾向、超越普通关系的爱意，爱情必须高于 0，并在 reason 引用该证据。
8. 如果玩家备注或关系事件明确写出成年角色对玩家有身体吸引或欲望依据，肉欲必须高于 0，并在 reason 引用该证据。
9. 如果玩家备注或关系事件明确写出占有欲、排他、独占或嫉妒倾向，占有欲必须高于 0，并在 reason 引用该证据。
10. 如果没有恋爱或身体吸引依据，爱情和肉欲保持 0；如果角色不是成年人，爱情/肉欲/暧昧类指标必须保持 0，并用 reason 说明缺少恋爱或身体吸引证据、或年龄/关系边界不允许。
11. 如果存在不安、丧亲、生活压力，担忧、悲伤或紧张可提高；若这些情绪为 0，reason 必须说明为什么当前没有对应压力或触发点。
12. 每个返回项都要写 status 与 reason，status 写当前阶段表现，reason 写造成该数值的具体事实。
13. initialMetrics 必须返回全部情绪字段和全部对玩家感觉字段；证据弱或没有触发时数值可以为 0，但 reason 必须说明为什么没有形成该情绪或感觉，不能省略字段。

## 初始装备 / 物品 / 穿着

1. 所有人物都必须根据其世界、身份、年龄、住址、学校/工作、当前事件合理返回 equipment、items、wearing。
2. equipment 是重要工具、武器、防具、法器、手机、背包等可装备或可调用物；每项必须包含 name、description、equipSlots、reason，equipSlots 必须写可装备部位或“装备”，reason 绝不能省略，必须说明该装备与人物身份、训练、职业、住址、当前事件或长期生活经历的关系。
3. items 是普通持有物或消耗品；每项必须包含 name、description、quantity、reason；若物品也可穿戴/装备，也要写 equipSlots。reason 绝不能省略，必须说明该物品为什么由此人物持有。
4. wearing 是当前已穿戴/携带在槽位上的项目；每项必须包含 slot、name、description、reason。reason 绝不能省略，必须说明该穿着为什么符合人物年龄、身份、场景、生活习惯或当前处境。
5. 可用穿着槽位：内衣、上衣、内裤、下衣、袜子、鞋子、外套、手套、头部、颈部、腰部、包具、饰品、装备。饰品和装备可不写数字，系统会自动分配为饰品1、装备1等。
6. 现代现实人物不要生成夸张武器；原作/异世界人物可按世界观生成合理装备，但不得无依据塞神器。
7. 普通生活、上学、工作、外出、会客等常规场景必须补齐基础穿着槽位：内衣、上衣、内裤、下衣、袜子、鞋子；名称可按身份和世界观克制推断。
8. wearing 省略某基础槽位不等于“未知”，系统会按常规衣物补齐；如果确实未穿，必须显式返回该 slot 的 name 为“未穿戴”并在 description 写明特殊原因。
9. “未穿戴”表示该部位真实空置：内衣未穿戴就是无内衣，上衣/内衣/下衣/内裤均未穿戴就是赤裸；这种情况只能由明确特殊上下文触发，不能因信息不足生成。

## 角色卡字段原因规则

1. 必须返回 roleCardFieldReasons 对象，且必须完整包含这些固定中文 key：姓名、所属世界、身份、职业、性别、生日、人际关系、外貌、性格、人物说明、社群角色、势力地位；不得省略任何一个。
2. 每个 key 的值都是该角色卡词条首次固化原因，必须说明该字段为什么这样写，依据来自人物基础区、玩家资料区、居住家庭区、关系事件区、世界观资料区或预设资料中的具体事实。
3. 禁止写“来源于角色资料/剧情证据/世界规则/根据上下文/初始化/系统生成/综合判断/默认”等抽象套话。
4. 原因主语必须是当前生成的角色本人；除“人际关系”字段外，不得把妹妹、父母、联系人等亲属的身份或经历当成本人的字段原因。
5. 例：“姓名按四川成都现代家庭命名习惯生成，并保留其作为刘悠同居双胞胎妹妹之一的独立身份”；“外貌来自备注中两名双胞胎外貌一致的设定，因此固化为与另一名妹妹相同但姓名独立的形象”。
6. skills、equipment、items、wearing 数组中每一项都必须带非空 reason 字段，说明该技能、装备、物品或穿着为什么属于此角色；任何一项缺 reason 都是不合格 JSON，不要只写 description，也不要把 reason 写成“默认/初始化/根据上下文”等空话。
7. factions 与 forcePositions 的每一项必须有 reason 或 changeMode，说明这个社群角色或势力地位为什么成立。

## RPG 字段原因规则

1. 必须返回 rpgFieldReasons 对象，且必须完整包含“{RPG字段列表}”里列出的每一个英文 key；不得省略任何一个，也不得只返回基础 12 项。
2. 每个 key 的值都是该 RPG 词条首次生成原因，必须解释“为什么是这个值/水平/当前状态”，并结合人物过去经历、教育/训练、家庭处境、职业履历、创伤、长期生活环境、玩家填写资料或当前关系事实推演生成。
3. 禁止写“来源于角色资料/剧情证据/世界规则/根据上下文推理/初始化/缺少明确证据所以默认/系统生成/综合判断”等抽象套话。
4. 原因必须解释当前角色本人的状态；亲属事实只能作为关系背景，不能替代本人的年龄、身份、能力、外貌、性格或职业原因。
5. 原因必须具体到经历。例如“她长期照顾病重父母又兼顾学业，意志高于普通同龄人”；“她没有接受过运动或战斗训练，力量只保持普通日常水平”；“父母已故后长期与哥哥相依为命，精神稳定受家庭压力影响”。
6. 不要用固定模板；每个字段必须分别写不同角度的原因。即使某字段很低、为空或接近普通，也要说明具体原因，例如缺少训练、长期普通生活、身体病弱、社会经历少、学习经历多但运动经历少等。

## 返回 JSON 格式

只返回一个 JSON 对象。根字段规范如下：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| name | string | 是 | 正式姓名。 |
| gender | string | 是 | 性别。 |
| relationships | string | 是 | 与玩家或核心人物的固化关系，格式为“关系：姓名”，多项用中文分号。 |
| role | string | 是 | 身份、社会角色或关系定位。 |
| detail | string | 是 | 个人背景；说明住址、学校、工作、特殊处境和上下文联系，不写外貌与性格长段。 |
| appearance | string | 是 | 外貌词条；描述可见外观、气质、穿着、体态或辨识特征。 |
| personality | string | 是 | 性格词条；描述稳定性格、处事方式、关系边界和心理倾向。 |
| faction | string | 是 | 兼容字段，取 `factions[0].faction`。 |
| factions | array<object> | 是 | 社群角色列表，1 到 4 项。 |
| forcePositions | array<object> | 是 | 势力地位列表，1 到 4 项。 |
| job | string | 是 | 确认职业；无可靠依据返回空字符串。 |
| jobConfirmed | boolean | 是 | 职业是否确认。 |
| rank | string | 是 | 兼容字段，取 `forcePositions[0].position`。 |
| skills | array<object> | 是 | 可确认技能列表。 |
| equipment | array<object> | 是 | 初始装备列表。 |
| items | array<object> | 是 | 初始物品列表。 |
| wearing | array<object> | 是 | 当前穿着列表。 |
| worldValues | object | 是 | 世界专属字段取值；只放有明确依据的字段。 |
| roleCardFieldReasons | object | 是 | 角色卡字段固化原因，必须包含固定中文 key。 |
| rpgFieldReasons | object | 是 | RPG 字段生成原因，必须包含 `{RPG字段列表}` 的全部英文 key。 |
| initialMetrics | object | 是 | 初始情绪与对玩家感觉。 |

### 嵌套对象规范

| 路径 | 类型 | 必填字段 | 说明 |
| --- | --- | --- | --- |
| factions[] | object | faction, role, reason | `faction` 写社群名；`role` 写其中承担的角色；`reason` 写成立证据。 |
| forcePositions[] | object | force, position, reason | `force` 写组织/势力；`position` 写职位、年级、职级或法定身份；`reason` 写成立证据。 |
| skills[] | object | name, desc, reason | 技能名、技能说明、为什么属于此角色。 |
| equipment[] | object | name, description, equipSlots, reason | 装备名、说明、可装备部位数组、持有原因。 |
| items[] | object | name, description, quantity, reason | 物品名、说明、数量、持有原因；可装备物也要含 `equipSlots`。 |
| wearing[] | object | slot, name, description, reason | 槽位、穿着名称、说明、为什么当前穿戴。 |
| roleCardFieldReasons | object | 姓名, 所属世界, 身份, 职业, 性别, 生日, 人际关系, 外貌, 性格, 人物说明, 社群角色, 势力地位 | 每个 key 都写具体固化原因，不得省略。 |
| rpgFieldReasons | object | {RPG字段列表} | 每个 RPG 字段都写具体经历、状态或证据原因。 |
| initialMetrics.emotions[] | object | key, value, status, reason | 必须为 `{情绪字段}` 中每一个字段各返回一项；`value` 为 0 到 100 数字。 |
| initialMetrics.playerFeelings[] | object | key, value, status, reason | 必须为 `{关系指标字段}` 中每一个字段各返回一项；`value` 为 0 到 100 数字。 |

### initialMetrics 完整性要求

1. `initialMetrics.emotions` 不能是空数组，必须完整覆盖 `{情绪字段}` 中列出的每个 key。
2. `initialMetrics.playerFeelings` 不能是空数组，必须完整覆盖 `{关系指标字段}` 中列出的每个 key。
3. 每一项都必须包含 `key`、`value`、`status`、`reason` 四个字段。
4. `value` 必须是 0 到 100 的数字；证据弱或没有触发时可以为 0。
5. `status` 必须写当前阶段表现；`reason` 必须说明为什么是该数值，即使 value 为 0 也不能省略。
6. 不允许只返回示例里的少数项，不允许返回空数组，不允许用“原因/当前状态”等占位词。
