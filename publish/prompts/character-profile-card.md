# 出场人物固化设定

为 AI RPG 视觉小说生成出场人物固化设定。只返回 JSON，不要 Markdown，不要解释。

## 变量区说明

这个模板中的变量不是抽象说明，而是由代码按游戏 UI / 数据区域组织后填充的内容。调整提示词时，应围绕这些变量区规定 AI 如何使用对应数据。

## 人物预设资料区

来源：只有在该人物命中本地人物索引并成功读取预设 md 时才会填入；否则显示无预设。

{人物预设资料区}

使用规则：
1. 如果这里有“预设人物 md”，该人物是主要/预设人物，姓名、身份、年龄、性别、原作背景优先遵循该 md，再结合当前事件补足状态。
2. 如果这里显示“无预设人物 md”，该人物不是预设人物，不得套用当前主角或其它预设角色资料；必须只根据人物基础区、玩家资料区、关系事件区和世界观资料生成。
3. 无预设人物的年龄、性别、身份、关系必须来自上下文明确证据；没有证据时生成合理短档案，但不得读取或继承当前主角年龄。

## 人物基础区

来源：候选人物资料，可能来自原作角色、微信联系人、玩家关系或剧情临时人物。

{人物基础区}

使用规则：
1. 候选姓名若是“妹妹/父亲/联系人”等称谓，必须结合命名要求和玩家资料生成正式姓名。
2. 身份/关系/叙事定位不能直接当职业。
3. 人物背景摘要、外貌线索和性格线索只作为证据，不得无依据扩写亲密关系。
4. 外貌必须单独固化到 appearance，性格必须单独固化到 personality，不要把二者混入 detail。
5. 已整理关系为空时，不要编造关系；必须从下方玩家区、微信区或剧情区找证据。
6. 无预设人物必须把关系事件区当作最重要来源：例如“默认账号妹妹/微信妹妹/剧情中新出现的人”都要按上下文生成独立角色卡，而不是继承当前主角资料。

## 玩家基础资料区

来源：手机激活页“姓名 / 性别 / 生日”输入与年龄计算。

{玩家基础资料区}

使用规则：
1. 这些字段确定玩家本人，不是当前待生成人物。
2. 亲属、同学、同事、同居者等联系人必须与玩家年龄、性别、生日逻辑相容。

## 玩家现实身份区

来源：手机激活页“现实身份”输入、AI 补全后的工作/学校/组织与地位，以及世界观补全。

{玩家现实身份区}

使用规则：
1. 现实身份决定联系人来源：学校、公司、社区、家庭、社交圈等。
2. 工作/学校/组织与地位可以影响人物 role、detail、rank，但不要直接塞进 job。
3. 世界观补全用于补足现实处境，不得覆盖明确玩家输入。

## 玩家居住家庭区

来源：手机激活页“具体地址 / 居住状态 / 父母信息”，以及 AI 补全后的详细地址、居住状态、父母状态、父母去世原因。

{玩家居住家庭区}

使用规则：
1. 地址决定地域文化、生活圈、姓名风格和人物行动范围。
2. 居住状态决定是否同居、照顾、依赖、合租、宿舍等关系强度。
3. 父母状态和死因会影响兄弟姐妹、监护、家庭创伤、亲情和依赖。

## 玩家人际关系区

来源：手机激活页“与你相关的人际关系”区域。

{玩家人际关系区}

使用规则：
1. 这是生成玩家关系联系人时的最高优先级关系证据。
2. 只固化这里明确写出或能由其直接推理的关系。
3. 不要擅自新增玩家未填写的重要亲密关系。

## 玩家备注区

来源：手机激活页“补充设定”区域。

{玩家备注区}

使用规则：
1. 备注必须参与关系、性格、生活压力、秘密、目标、边界和初始数值推理。
2. 如果备注说明某段关系紧张、隐藏、依赖、疏远、恋爱倾向、身体吸引或占有欲，initialMetrics 必须体现。
3. 不得忽略备注，也不得把备注当成无关旁白。
4. 若资料存在年龄冲突，必须优先采用明确成年、现实合法且与居住状态一致的设定；不要把未成年角色写入恋爱或身体吸引相关指标。

## 关系事件区

来源：调用人物固化时传入的具体上下文，例如微信联系人资料区、当前剧情、原作证据或事件原因。

{关系事件区}

使用规则：
1. 若该区域来自微信联系人资料，必须优先解释此联系人与玩家的微信关系。
2. 若该区域来自剧情事件，必须说明人物为什么在当前事件中出现。
3. 关系事件区不能覆盖玩家已填写的核心资料，只能补足当前人物相关证据。

## 世界观资料区

来源：世界观固化资料，包括世界背景、势力、特殊职业和职业等级。

{世界观资料区}

使用规则：
1. 现代现实人物优先遵循 2026 现代都市逻辑。
2. 原作/异世界人物优先遵循所属作品设定。
3. 社群角色和势力地位都是角色卡必要信息：社群角色用于说明“属于哪个社区/家庭/社交圈并在其中是什么角色”，势力地位用于说明“在有等级制度的势力里处于什么组织层级和职位”。

## 社群角色规则

1. 必须返回 factions 数组，每项包含 faction 与 role；显示会合并为“社群 / 角色”。
2. faction 只表示居住社区、家庭、社交圈、临时群体、生活圈或无层级公共地点；role 是其在其中承担的社会角色，不是等级。
3. 同一角色可以有多个社群角色，最多 4 个；例如“锦苑小区3栋2单元601号 / 居民”、“刘悠家庭 / 同居妹妹”、“本地跑团社群 / 群友”。
4. 玩家亲属或同住者必须根据玩家具体地址补出居住社群；如果住址具体到小区楼栋门牌，优先使用该具体住址作为 faction，role 写“居民/同住者/家庭成员”等。
5. 若角色既不是居民、学生、工作者，也不属于任何组织，必须在 factions 写出特殊处境，例如“城市街头 / 流浪者”、“临时避难点 / 滞留者”，并在 detail 备注原因。
6. 原作/异世界角色也必须返回社群角色，例如“冬木市 / 居民”、“远坂家 / 家庭成员”、“圣杯战争相关者 / 参战者”。
7. 学校、公司、科室、部门、军队、教会、宗门、贵族家族、魔术家系等有等级制度的归属，不要只写入 factions；必须同时或优先写入 forcePositions。

## 势力地位规则

1. 必须返回 forcePositions 数组，每项包含 force 与 position；显示会合并为“势力 / 地位”。
2. force 必须是有内部层级、职级、年级、职位或等级划分的势力，例如公司、学校、科室、部门、军队、宗门、教会、贵族家族、魔术家系。
3. force 写组织架构中的具体势力层级，现代公司至少写到公司级；大厂可写“腾讯某事业群/某中心/某部门”，医院可写“某医院急诊科”，学校可写“某学校某年级”。
4. position 必须是在该势力内部有等级含义的地位、职位、年级或职级，例如“高三学生”、“高级后端工程师”、“研发二部经理”、“急诊科主治医师”、“代行者”、“家主”。
5. 展示应形成“势力 / 地位”，例如“成都星河云栈科技有限公司 / 软件工程师”、“腾讯云计算公司 / 高级后端工程师”、“成都市第三人民医院急诊科 / 科室经理”。
6. 只有“居民/同住者/妹妹/朋友/联系人/路人”这类普通社会角色时，不要写入 forcePositions，只写入 factions。
7. 现代 18 岁人物通常要判断学校/工作势力：有学生证据则写“具体学校或合理学校 / 高三学生、大学生”等；有工作证据则写“公司或部门 / 岗位职级”；没有学生和工作证据时，forcePositions 可为空，但 detail 必须说明是待业、辍学、自由职业、家庭照料者或其它特殊状态。
8. 势力地位可以有多个，最多 4 个；不要用 forcePositions 表示住址居民身份。

## 命名规则

1. 姓名必须是人物正式姓名，不得是“妹妹、父亲、联系人、微信好友、同事”等关系称谓。
2. 若人物基础区含命名要求，必须严格执行。
3. 不要硬套同姓：母亲、配偶、继亲、养亲、朋友、同事可能不同姓。
4. 亲属命名要符合玩家地址、地区文化、家庭结构与玩家资料。
5. 若无法确认姓名来源，可结合文化习俗生成合理姓名，但不要写“未知/待补全/需要AI生成”。

## 关系固化规则

1. relationships 只写已经可从玩家区、人物区、关系事件区或世界观区推理出的关系。
2. 格式必须是“关系：姓名”，多项用中文分号分隔。
3. 不要照抄长描述，例如不要写“妹妹：需要AI按现实世界观生成姓名”。
4. 不要擅自新增玩家未填写的重要亲密关系。
5. 如果是玩家亲属，要让 relationships 与玩家资料、居住状态、父母状态互相吻合。
6. 如果是微信联系人，要体现其与玩家的微信关系，而不是只写泛泛身份。

## 职业固化规则

1. 职业是人物内化能力、长期训练、资格或专业经验，不等同当前公司、学校、雇佣状态或叙事标签。
2. 学生、妹妹、父亲、主角、配角、悲剧核心、联系人不是职业；这些必须写入 role 或 factions.role。
3. 只有百分之百确认该角色拥有职业时，才返回 job 且 jobConfirmed=true。
4. 不确定时 job 为空字符串，jobConfirmed=false，但仍必须通过 factions 写出住址、家庭、社区、社交圈或特殊处境；如存在公司/学校/部门等层级势力，则通过 forcePositions 写出其势力地位。
5. 职业一旦提出会落库固化，所以不能为了丰富人物而硬造职业。
6. rank 表示首要势力地位，来自 forcePositions[0].position；如果没有层级势力地位，rank 可以为空。

## 世界属性规则

worldValues 只返回有明确依据的字段：{世界字段}。

1. 只填世界专属字段，不要把通用属性混进 worldValues。
2. 没有证据的字段不要返回。
3. 返回值必须是可落库的短值，不要写长段解释。
4. 若字段与人物基础冲突，以当前人物固化资料为准。

## 初始情绪与对玩家感觉

必须返回 initialMetrics，用于该非玩家角色第一次生成时的情绪和“其余”关系数值。数值必须与变量区证据一致，不得使用默认值敷衍。

### 情绪维度

可用情绪字段：{情绪字段}

- 担忧：角色对处境、家人、玩家或风险的担心。
- 悲伤：丧亲、创伤、失落、分离导致的低落。
- 紧张：面对未知、冲突、危险或压力的反应。
- 恐惧/愤怒/屈辱等：按上下文选择，不要机械填充。

### 对玩家感觉维度

可用对玩家感觉字段：{关系指标字段}

- 亲情：玩家亲属必须明显高于 0；亲情与爱情、肉欲、占有欲是独立指标，不互相排斥。
- 了解：长期相处、共同生活、同学同事、亲密关系不应接近陌生人。
- 信任：被照顾、共同经历、依赖关系会提高信任。
- 依赖：经济、心理、生活照料、丧亲后的共同生活会提高依赖。
- 爱情：成年角色资料明确写出恋爱、爱意、心动、爱慕、超越亲情等证据时必须高于 0；没有恋爱依据时保持 0。
- 肉欲：成年角色资料明确写出身体吸引、欲望、暧昧试探、性吸引等证据时必须高于 0；没有身体吸引依据时保持 0。
- 占有欲：资料明确写出占有、嫉妒、排他、独占倾向时必须高于 0。

### 初始数值规则

1. 如果该角色是玩家妹妹、姐姐、父母、子女、配偶等亲属，亲情必须明显高于 0。
2. 亲情、爱情、肉欲、占有欲彼此独立：同一个成年角色可以同时拥有很高亲情、很高爱情、很高肉欲和很高占有欲；不得因为亲情已高就把爱情或肉欲压成 0。
3. 如果上下文显示共同生活、父母去世、经济或心理依靠、被玩家照顾等，依赖、信任、了解应相应提高。
4. 如果上下文显示长期亲密相处，了解不应接近陌生人。
5. 如果玩家备注或关系事件明确写出成年角色对玩家有恋爱倾向、超越普通关系的爱意，爱情必须高于 0，并在 reason 引用该证据。
6. 如果玩家备注或关系事件明确写出成年角色对玩家有身体吸引或欲望依据，肉欲必须高于 0，并在 reason 引用该证据。
7. 如果玩家备注或关系事件明确写出占有欲、排他、独占或嫉妒倾向，占有欲必须高于 0，并在 reason 引用该证据。
8. 如果没有恋爱或身体吸引依据，爱情和肉欲保持 0；如果角色不是成年人，爱情/肉欲/暧昧类指标必须保持 0。
9. 如果存在不安、丧亲、生活压力，担忧、悲伤或紧张可提高。
10. 每个返回项都要写 status 与 reason，说明为什么是这个值。
11. 不要返回无依据的全量字段，只返回确实需要初始化或解释的项。

## 返回字段拆分

- name：正式姓名。
- gender：性别。
- relationships：与玩家或其它核心人物的固化关系。
- role：身份/社会角色/关系定位。
- detail：个人背景，说明生活处境、经历、与上下文的联系，不写外貌和性格长段。
- appearance：外貌词条，描述可见外观、气质、穿着、体态或辨识特征；没有证据时根据世界观克制生成。
- personality：性格词条，描述稳定性格、处事方式、关系边界和心理倾向；必须与上下文证据一致。
- faction：首要社群名称，来自 factions[0].faction；不要写“无”，除非确实没有任何社群归属。
- factions：社群角色数组，每项含 faction 与 role，表示“社群 / 角色”；必须尽可能补全居住社区、家庭、社交圈、临时群体等必要信息。
- forcePositions：势力地位数组，每项含 force 与 position，表示“势力 / 地位”；填写有等级制度、组织层级、职级、年级、职位划分的公司、学校、部门或组织。
- job：确认职业；无可靠依据则空字符串。
- jobConfirmed：职业是否确认。
- rank：首要势力地位，来自 forcePositions[0].position；没有层级势力地位时可为空。
- skills：可确认技能数组，每项含 name 和 desc。
- worldValues：世界专属字段取值。
- initialMetrics：初始情绪与对玩家感觉。
