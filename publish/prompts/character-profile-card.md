# 出场人物固化设定

为 AI RPG 视觉小说生成出场人物固化设定。只返回 JSON，不要 Markdown，不要解释。

## 模板构成拆分

这个提示词由以下可调整组件组成：

1. 任务定位：告诉 AI 这是“出场人物固化设定”，不是剧情续写，也不是临时旁白。
2. 人物基础：提供当前候选人物的原始字段，作为姓名、身份、关系、职业、世界属性的基础证据。
3. 当前剧情与关系上下文：提供玩家、现实关系、微信联系人、原作剧情或当前事件，用于推理人物与玩家/角色的关系。
4. 世界观上下文：提供世界背景、势力、特殊职业、职业等级，决定人物是否属于某势力、是否拥有特殊职业。
5. 命名规则：约束 AI 生成正式姓名，禁止把关系称谓直接当姓名。
6. 关系固化规则：约束 relationships 字段如何写，防止照抄长描述或新增无证据关系。
7. 职业固化规则：约束 job/jobConfirmed，防止把叙事标签、学生身份、公司岗位误当职业。
8. 世界属性规则：约束 worldValues，只写明确有依据的世界专属字段。
9. 初始情绪与对玩家感觉：生成 initialMetrics，避免亲属、同居者、熟人被默认成 0 关系。
10. 返回 JSON 结构：限定可返回字段和字段含义，方便代码落库。

## 可调项说明

- 想让亲属关系更强：调整“初始情绪与对玩家感觉”中的亲情、依赖、信任规则。
- 想减少 AI 擅自补关系：强化“关系固化规则”中“只写上下文确认关系”。
- 想增加职业判定：调整“职业固化规则”中 jobConfirmed=true 的门槛。
- 想让世界观影响更大：强化“世界观上下文”和“世界属性规则”。
- 想让名字更本土化：调整“命名规则”，加入地区、姓氏、文化习俗要求。

## 人物基础输入

这部分是代码传入的候选人物资料。可能来自原作角色、微信联系人、玩家关系、剧情中临时出现的人物。

```json
{人物基础}
```

### 人物基础字段拆分

- name：候选姓名；若是“妹妹/父亲/联系人”等称谓，必须重新生成正式姓名。
- gender：候选性别；若上下文明确则保持，未知则结合关系与设定推理。
- role：人物身份/关系/叙事定位，不能直接当职业。
- detail：人物背景摘要，可用于推理家庭、工作、处境。
- personality：性格线索，用于关系和初始情绪。
- work：所属作品或世界。
- nameRule：命名要求；若存在必须遵守。
- relationshipHint：关系线索；只作为推理证据，不能无依据扩写。

## 当前剧情与关系上下文

这部分决定人物为什么会出现、与玩家/主角/联系人有什么关系。

{当前剧情}

### 剧情上下文拆分

1. 玩家关系证据：玩家资料、居住状态、父母状态、备注、人际关系。
2. 联系人证据：微信关系、手动添加关系、联系人描述。
3. 原作证据：角色原作身份、剧情索引、世界设定。
4. 当前事件证据：本回合出现原因、场景、冲突或行动。
5. 关系强度证据：同居、照顾、丧亲、债务、上下级、敌对、熟人等。

## 世界观上下文

- 背景：{世界背景}
- 势力：{势力}
- 特殊职业：{特殊职业}
- 职业等级：{职业等级}

### 世界观使用规则

1. 世界观只用于补足合理身份、势力、职业、能力，不得覆盖明确人物证据。
2. 现代现实人物优先遵循 2026 现代都市逻辑。
3. 原作/异世界人物优先遵循所属作品设定。
4. 没有证据时宁可留空，也不要硬塞特殊职业或势力。

## 命名规则

1. 姓名必须是人物正式姓名，不得是“妹妹、父亲、联系人、微信好友、同事”等关系称谓。
2. 若人物基础含 nameRule，必须严格执行。
3. 不要硬套同姓：母亲、配偶、继亲、养亲、朋友、同事可能不同姓。
4. 亲属命名要符合地区文化、家庭结构与玩家资料。
5. 若无法确认姓名来源，可结合文化习俗生成合理姓名，但不要写“未知/待补全/需要AI生成”。

## 关系固化规则

1. relationships 只写已经可从上下文推理或调整出的关系。
2. 格式必须是“关系：姓名”，多项用中文分号分隔。
3. 不要照抄长描述，例如不要写“妹妹：需要AI按现实世界观生成姓名”。
4. 不要擅自新增玩家未填写的重要亲密关系。
5. 如果是玩家亲属，要让 relationships 与玩家资料、居住状态、父母状态互相吻合。
6. 如果是微信联系人，要体现其与玩家的微信关系，而不是只写泛泛身份。

## 职业固化规则

1. 职业是人物内化能力、长期训练、资格或专业经验，不等同当前公司、学校、雇佣状态或叙事标签。
2. 学生、妹妹、父亲、主角、配角、悲剧核心、联系人不是职业。
3. 只有百分之百确认该角色拥有职业时，才返回 job 且 jobConfirmed=true。
4. 不确定时 job 为空字符串，jobConfirmed=false。
5. 职业一旦提出会落库固化，所以不能为了丰富人物而硬造职业。
6. rank 只写有证据的等级、阶位、职级或社会地位。

## 世界属性规则

worldValues 只返回有明确依据的字段：{世界字段}。

1. 只填世界专属字段，不要把通用属性混进 worldValues。
2. 没有证据的字段不要返回。
3. 返回值必须是可落库的短值，不要写长段解释。
4. 若字段与人物基础冲突，以当前人物固化资料为准。

## 初始情绪与对玩家感觉

必须返回 initialMetrics，用于该非玩家角色第一次生成时的情绪和“其余”关系数值。数值必须与全量上下文一致，不得使用默认值敷衍。

### 情绪维度

可用情绪字段：{情绪字段}

- 担忧：角色对处境、家人、玩家或风险的担心。
- 悲伤：丧亲、创伤、失落、分离导致的低落。
- 紧张：面对未知、冲突、危险或压力的反应。
- 恐惧/愤怒/屈辱等：按上下文选择，不要机械填充。

### 对玩家感觉维度

可用对玩家感觉字段：{关系指标字段}

- 亲情：玩家亲属必须明显高于 0。
- 了解：长期相处、共同生活、同学同事、亲密关系不应接近陌生人。
- 信任：被照顾、共同经历、依赖关系会提高信任。
- 依赖：经济、心理、生活照料、丧亲后的共同生活会提高依赖。
- 爱情/肉欲：没有恋爱或欲望依据时保持 0。

### 初始数值规则

1. 如果该角色是玩家妹妹、姐姐、父母、子女、配偶等亲属，亲情必须明显高于 0。
2. 如果上下文显示共同生活、父母去世、经济或心理依靠、被玩家照顾等，依赖、信任、了解应相应提高。
3. 如果上下文显示长期亲密相处，了解不应接近陌生人。
4. 如果没有恋爱依据，爱情和肉欲保持 0。
5. 如果存在不安、丧亲、生活压力，担忧、悲伤或紧张可提高。
6. 每个返回项都要写 status 与 reason，说明为什么是这个值。
7. 不要返回无依据的全量字段，只返回确实需要初始化或解释的项。

## 返回字段拆分

- name：正式姓名。
- gender：性别。
- relationships：与玩家或其它核心人物的固化关系。
- role：身份/社会角色/关系定位。
- detail：个人背景，说明生活处境、经历、与上下文的联系。
- personality：性格摘要。
- faction：所属势力或“无”。
- job：确认职业；无可靠依据则空字符串。
- jobConfirmed：职业是否确认。
- rank：等级、阶层、职级或社会地位。
- skills：可确认技能数组，每项含 name 和 desc。
- worldValues：世界专属字段取值。
- initialMetrics：初始情绪与对玩家感觉。

## 返回 JSON 结构

```json
{"name":"姓名","gender":"性别","relationships":"妹妹：姓名；父亲：姓名","role":"身份","detail":"个人背景","personality":"性格","faction":"所属势力或无","job":"职业，无法可靠判断则空字符串","jobConfirmed":false,"rank":"等级","skills":[{"name":"技能","desc":"说明"}],"worldValues":{"字段key":"该人物固化取值"},"initialMetrics":{"emotions":[{"key":"担忧","value":40,"status":"当前状态","reason":"原因"}],"playerFeelings":[{"key":"亲情","value":85,"status":"当前状态","reason":"原因"}]}}
```
