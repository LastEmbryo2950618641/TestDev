# 我狠狠操控

这是一个以 AI 推演、角色状态演化、现实世界/异世界双线叙事为核心的网页游戏项目。
当前项目以 `publish/` 为运行主目录，使用本地开发服务器直接加载页面与静态资源；后续目标是逐步完成结构规范化、平台适配解耦，并为桌面 `exe` 与移动端 `apk` 预留演进空间。

## 项目目标

- 提供以“控制 / 上线 / 下线 / 角色反馈 / 现实推演”为核心的互动式游戏体验。
- 保持 AI 提示词、角色状态、世界状态、资源文件、存档规则的长期可维护性。
- 在不推翻现有项目的前提下，逐步规范目录、模块边界与开发流程。
- 为未来的桌面打包与移动端适配建立统一约束。

## 当前运行方式

- 开发入口：`dev/scripts/dev-server.cjs`
- 运行页面：`publish/index.html`
- 默认访问地址：`http://127.0.0.1:8000/`

说明：
本项目当前不是标准的 `npm run dev` / Vite / Webpack HMR 工程，而是自定义本地静态开发服务。因此后续如果要补自动刷新、桌面壳或移动壳，需要在当前架构上渐进演进，而不是默认套用传统前端脚手架思路。

## 目录约定

### 1. 运行目录

- `publish/`
  - 当前网页前端运行主目录。
  - 页面、样式、脚本、静态资源、提示词模板、运行时模块都以这里为主。
  - 原则：任何会直接在浏览器运行的核心代码，都应明确知道自己是否属于 `publish/` 运行主链路。

### 2. 开发目录

- `dev/`
  - 开发辅助脚本、开发服务器、恢复脚本、后续开发工具脚本放这里。
  - 不应承载业务玩法逻辑。

### 3. 文档目录

- `docs/`
  - 统一放项目规范、需求说明、计划文档、系统设计、阶段规则说明。

建议后续细分：
- `docs/requirements/`：需求文档
- `docs/plans/`：实现计划 / 技术方案
- `docs/architecture/`：架构与模块规范
- `docs/game-rules/`：玩法规则、提示词规则、阶段规则

如果这些子目录尚不存在，可以按需要新增；后续新文档优先放进对应子目录，不要散落在根目录或临时目录。

### 4. 测试目录

- `tests/`
  - 放脚本测试、逻辑测试、回归测试。
  - 新功能如果已经具备稳定行为，优先补测试或最少补验收说明。

### 5. 资源目录

- `assets/`
  - 原始资料、作品资料、设定资料等偏源数据资源。
- `publish/assets/`
  - 运行时前端实际访问的静态资源。

资源放置原则：
- 浏览器直接访问的静态资源放 `publish/assets/`
- 源资料、整理资料、原始设定文件优先放 `assets/`
- 不要把一次性调试截图、日志、临时导出内容混入正式资源目录

### 6. 日志目录

- `logs/`
  - 本地运行日志、临时调试日志。
  - 原则上不作为功能代码提交对象，除非用户明确要求一并提交。

## AI 开发约束

以下规则用于约束后续 AI 修改项目时的行为。

### 1. 先查边界，再动代码

在新增或修改功能前，必须先确认：
- 这个需求属于哪个系统
- 当前系统已有入口文件在哪里
- 当前状态由哪个文件负责
- 当前 UI 由哪个文件负责

禁止在未确认边界时，直接在多个无关文件中散乱追加逻辑。

### 2. 不允许到处乱加代码

必须优先遵守以下顺序：
- 先找现有模块是否已有对应职责
- 能在原职责模块里扩展，就不要新建重复逻辑
- 必须新建文件时，要说明它属于哪个系统、解决什么问题

禁止行为：
- 在 `game.js` 中继续随意堆入无边界的新业务
- 在多个页面片段中复制相同判断
- 在不同脚本里各写一套“当前状态判断”
- 为了快速生效，绕过已有系统直接硬写 UI 文案和状态

### 3. 需求文档与计划文档必须有落点

中大型需求应写文档后再改，至少满足以下规范：

- 需求文档：`docs/requirements/`
- 实现计划：`docs/plans/`

建议命名：
- `YYYY-MM-DD-功能名-requirement.md`
- `YYYY-MM-DD-功能名-plan.md`

适用场景：
- 跨多个系统的改动
- 影响存档/提示词/资源/状态的改动
- 与后续平台适配相关的改动
- UI、状态、规则三者同时变动的改动

### 4. 新功能必须写清状态来源

任何新增功能，在实现前都应先明确：
- 权威状态字段是什么
- 谁负责更新这个状态
- 哪些页面读取这个状态
- 是否需要持久化
- 是否影响存档兼容

如果状态来源不清，不允许直接写展示逻辑。

### 5. 平台相关能力必须收敛

后续凡是涉及以下能力：
- 文件读写
- 图片保存
- key 管理
- 本地数据库
- 宿主通信
- dev server 专用接口

都必须视为“平台能力”，禁止直接散落进业务逻辑。
后续应逐步收敛到统一适配层，而不是让业务代码直接依赖桌面实现。

### 6. 静态资源放置规则

- 页面运行依赖资源：放 `publish/assets/`
- 源资料/设定资料：放 `assets/`
- 用户生成资源：优先收敛到专门子目录，并标注用途
- 临时截图、调试导出、日志：不要混入正式资源目录

如果资源是“运行时生成物”，新增时应说明：
- 是否需要入库
- 是否属于用户内容
- 是否属于临时本地文件

### 7. 提示词与规则文本也算代码资产

凡是会影响行为的提示词、规则模板、阶段说明，都应视为正式代码资产。
要求：
- 按系统分类
- 不要重复复制相同规则
- 不要在多个提示词里写互相冲突的要求
- 变更时说明影响范围

### 8. 先增量重构，不做无计划大重写

本项目已较大，后续结构规范化应遵守：
- 先定边界
- 再逐步迁移
- 新功能尽量写进规范位置
- 旧逻辑按模块逐步收口

禁止无计划进行整仓大搬迁或全面重写。

## 推荐的模块演进方向

后续建议逐步按功能域收敛，例如：
- `control/`
- `control-experience/`
- `character/`
- `real-world/`
- `wechat/`
- `prompt/`
- `storage/`
- `body-figure/`
- `platform/`

现阶段不要求一次性重构完成，但新增逻辑应尽量向明确功能域聚拢。

## 提交规范建议

提交前建议自查：
- 本次修改是否只包含目标功能
- 是否误混入日志、临时文件、调试导出
- 是否混入无关资源变更
- 是否变更了运行时生成资源，如果变更，是否确认需要提交

推荐提交信息格式：
- `feat: ...`
- `fix: ...`
- `refactor: ...`
- `docs: ...`
- `test: ...`

## 后续 AI 协作建议

每次开始中大型开发前，优先做这三件事：
1. 阅读根 `README.md`
2. 确认目标系统与状态边界
3. 判断是否需要先补 `docs/requirements/` 与 `docs/plans/`

每次完成改动后，至少说明：
- 改了哪些文件
- 状态来源是什么
- 是否影响存档/资源/提示词
- 是否需要后续迁移或补测试

## 当前阶段的现实原则

- 先保证功能持续可迭代
- 再逐步收敛结构
- 先避免继续把逻辑散落到各处
- 再为 `exe / apk` 做平台适配准备

这份 README 的目标不是一次性定义最终架构，而是给后续所有 AI 与人工协作提供统一边界，避免继续无序增长。
