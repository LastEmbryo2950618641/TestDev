# 项目说明

这是一个以 AI 推演、角色状态演化、现实世界 / 异世界双线叙事为核心的网页游戏项目。

当前项目以 `publish/` 作为运行主目录，使用本地开发服务器直接加载页面与静态资源。后续目标是在不破坏现有玩法逻辑的前提下，逐步完成结构规范化、平台边界拆分，并为桌面 `exe` 与移动端 `apk` 预留演进空间。

## 项目目标

- 提供以“控制 / 上线 / 下线 / 角色反馈 / 现实推演”为核心的交互式游戏体验
- 保持 AI 提示词、角色状态、世界状态、资源文件、存档规则的长期可维护性
- 在不推翻现有项目的前提下，逐步规范目录、模块边界与开发流程
- 为未来的桌面打包与移动端适配建立统一约束

## 当前运行方式

- 开发入口：`dev/scripts/dev-server.cjs`
- 运行页面：`publish/index.html`
- 默认访问地址：`http://127.0.0.1:8000/`

说明：本项目当前不是标准的 `npm run dev` / Vite / Webpack HMR 工程，而是自定义本地静态开发服务器。因此后续如果要补自动刷新、桌面壳或移动壳，需要在当前架构上渐进演进，而不是直接套用传统前端脚手架思路。

## 目录约定

### 1. 运行目录

- `publish/`
  - 当前网页前端运行主目录
  - 页面、样式、脚本、静态资源、提示词模板、运行时模块都以这里为主
  - 原则：任何会直接在浏览器运行的核心代码，都应明确知道自己是否属于 `publish/` 运行主链路

### 2. 开发目录

- `dev/`
  - 开发辅助脚本、开发服务器、恢复脚本、后续开发工具脚本放这里
  - 不应承载业务玩法逻辑

### 3.5. 多端壳目录

- `desktop/`
  - Windows `exe` 方向的宿主壳骨架目录
  - 只承载桌面宿主装配、平台桥接、打包约束，不承载新的玩法逻辑
- `mobile/`
  - Android `apk` 方向的宿主壳骨架目录
  - 只承载移动宿主装配、平台桥接、打包约束，不承载新的玩法逻辑

当前这两个目录已经是正式架构落点，不是临时草稿目录。后续如需推进多端适配，应优先在这两个目录扩展宿主壳能力，并通过 `publish/platform/` 下的 `platform.core.*` 与共享核心对接。

### 3. 文档目录

- `docs/`
  - 统一放项目规范、需求说明、计划文档、系统设计、阶段规则说明

建议后续细分：

- `docs/requirements/`：需求文档
- `docs/plans/`：实现计划 / 技术方案 / 验证记录
- `docs/architecture/`：架构、边界、迁移模式、长期协作规则
- `docs/game-rules/`：玩法规则、提示词规则、阶段规则

优先阅读：

- `docs/README.md`
- `docs/architecture/encoding-collaboration-rules.md`
- `docs/architecture/ai-development-workflow.md`
- `docs/architecture/module-migration-priority-ladder-2026-07-11.md`
- `docs/architecture/legacy-encoding-syntax-stabilization-backlog-2026-07-11.md`

### 4. 测试目录

- `tests/`
  - 放脚本测试、逻辑测试、回归测试
  - 新功能如果已经具备稳定行为，优先补测试或最少补验收说明

### 5. 资源目录

- `assets/`
  - 原始资料、作品资料、设定资料等偏源数据资源
- `publish/assets/`
  - 运行时前端实际访问的静态资源

资源放置原则：

- 浏览器直接访问的静态资源放 `publish/assets/`
- 源资料、整理资料、原始设定文件优先放 `assets/`
- 不要把一次性调试截图、日志、临时导出内容混入正式资源目录

### 6. 日志目录

- `logs/`
  - 本地运行日志、临时调试日志
  - 原则上不作为功能代码提交对象，除非用户明确要求一并提交

## 当前协作原则

- 优先做低风险结构化改造，不轻易直接重排高耦合旧主链
- 优先把真实实现落进明确目录，再让旧入口退化为兼容壳
- 先收展示层，再决定是否继续下沉规则层、平台层或持久化层
- 每轮改动都应尽量附带计划、验证或边界文档，避免后续会话失去上下文

## 当前建议的长期推进顺序

1. 先确认需求与影响范围
2. 再写计划文档，控制最小切口与停手边界
3. 先收 UI / helper / 平台边界，再逐步迁移调用面
4. 每一步都尽量保持玩法逻辑不变
5. 改动完成后补验证记录，方便后续继续推进

## 当前 AI 会话最小自检清单

- 新代码是否落在正确目录
- 是否复用了已有权威状态，而不是复制判断
- 是否误把平台能力写回业务文件
- 是否引入新的中文编码风险
- 是否产生了 `.bak`、日志、临时文件但没有处理说明
- 是否在文档里说明了影响范围与后续迁移建议

## 给后续会话的明确约束

- 不要因为文件大就直接整文件重写
- 不要因为赶进度就把新逻辑继续堆回 `publish/game.js` 或 `publish/` 根目录旧大文件
- 不要把“能跑”当作“结构正确”
- 不要只修眼前需求而无视多端复用边界
- 不要在未验证编码的情况下覆盖中文文件

这份 README 的目标不是替代详细架构文档，而是让任何后续 AI 或人工接手时，先知道这个项目的运行方式、目录边界、编码约束与协作底线。

### 7. 展示层优先收口入口（2026-07-11 补充）

当后续需求落在高耦合页面模块，但当前目标仍是低风险推进时，默认优先采用“展示层先收口”的方式推进。

最小执行顺序：

1. 先判断本轮是否只涉及展示派生
2. 优先抽 `title / subtitle / empty-state / row / card / dialog view`
3. 真正实现进入 `publish/ui/<module>/...`
4. 旧入口只保留兼容转发
5. 模板逐步改为消费 helper 对象
6. 每次只收一个相邻展示切面

默认不要混入同一轮的内容：

- 消息发送与接收主链
- 记忆写回
- 同步、恢复、初始化入口
- 图片生成与异步流程装配
- 跨页面隐式状态写入

每次最小验收至少包括：

- helper 已新增且可检索
- 兼容壳已接好
- 模板已实际消费新 helper
- `node --check` 通过
- 边界文档或 playbook 已同步

后续 AI 或协作者开始动手前，优先阅读：

- `docs/architecture/encoding-collaboration-rules.md`
- `docs/architecture/ai-development-workflow.md`
- `docs/architecture/wechat-display-refactor-playbook-2026-07-11.md`

### 9. 旧代码清理节奏（2026-07-12 补充）

当前项目已经进入多端并行演进阶段，因此旧代码清理必须服从“先稳定主链、再做收尾”的原则。

执行原则：

1. 先完成 shared runtime / desktop exe / android apk 的真实可验证链路
2. 再做旧代码、临时脚本、兼容壳、备份目录的正式清理
3. 清理顺序必须是：
   - 先盘点
   - 再分级
   - 再删除第一批低风险对象
   - 最后处理兼容层与历史副本

当前默认策略：

- 不要在多端主链尚未稳定时，大面积删除 `publish/` 旧文件
- 不要把 runtime 证据目录、desktop/mobile 产物目录当成普通垃圾文件直接清掉
- 可以先整理清理名单，但正式清理应放在多端目标基本达成后执行

当前清理分级入口：

- `docs/architecture/legacy-cleanup-triage-2026-07-12.md`

后续真正开始清理时，优先顺序应为：

1. 根目录临时 `tmp_*` 脚本
2. 无引用的一次性调试文件
3. 明确退役的兼容入口
4. 最后才是历史备份目录与旧实现收尾
