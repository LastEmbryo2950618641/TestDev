# Requirement Document Template

> 文件位置建议：`docs/requirements/YYYY-MM-DD-<topic>-requirement.md`

## 1. 背景

说明这次需求出现的背景、当前问题和触发原因。

建议写清：

- 现在遇到了什么问题
- 为什么这个问题现在要解决
- 这次需求更偏体验修复、玩法扩展、结构规范化，还是稳定化处理

## 2. 用户目标

说明用户真正想达到什么结果。

尽量避免只写“优化一下”“调整结构”，建议明确成：

- 用户希望看到什么变化
- 用户希望减少什么成本或风险
- 用户希望新增什么能力或约束

## 3. 预期行为

列出修改后系统应该表现出的行为。

建议逐条写清：

- 页面上会怎么显示
- 用户能够做什么
- 系统会如何响应
- 哪些旧行为必须保持不变

## 4. 不在本次范围内

明确这次不做什么，避免范围失控。

建议主动写清：

- 本轮不解决哪些相关但更大的问题
- 本轮不重构哪些历史高耦合文件
- 本轮不统一哪些暂时无收益的结构层级

## 5. 影响范围

说明本次需求可能影响：

- 哪些页面
- 哪些状态
- 哪些资源
- 哪些提示词 / 规则
- 哪些存档字段
- 是否涉及 `ui / domain / app / platform` 任一层

## 6. 约束与注意事项

说明本次实现必须遵守的特殊约束。

例如：

- 不破坏旧存档
- 不新增平台强依赖
- 不修改既有资源结构
- 不误碰初始化 / 同步 / 恢复 / 写回主链
- 不因为目录对称性强行新增无收益层级

## 7. 验收标准

列出完成后如何判断需求已经达成。

建议写成可验证结果，例如：

- 当……时，应显示……
- 当……操作后，应发生……
- 不应再出现……
- 某块展示改为消费 helper 对象
- 某轮改造不影响存档字段与写回主链

## 8. 与计划文档的衔接补充

如果该需求后续会进入结构化改造或多文件实现，建议在需求文档里先补充以下判断，方便后续直接衔接 `docs/plans/`。

### A. 本次更像哪一类问题

- 纯展示层问题
- 规则复用问题
- 状态主链问题
- 平台边界问题
- 持久化 / 兼容问题
- 历史污染稳定化问题

### B. 本次是否需要先控制范围

至少明确：

- 是否只要求先做最小切口
- 是否明确不碰高风险主链
- 是否允许先补文档再延后代码深拆
- 是否需要先做稳定化再进入功能开发

### C. 建议写清的非目标

需求文档中建议主动写清：

- 本轮不解决哪些相关但更大的问题
- 本轮不重构哪些历史高耦合文件
- 本轮不统一哪些暂时无收益的目录层级
- 本轮不顺手处理哪些平台或存档问题

### D. 成功标准写法建议

尽量避免只写“优化体验”“调整结构”这类抽象描述，建议写成可验证结果，例如：

- 页面某块展示改为消费 helper 对象
- 某类空态文案统一由 helper 提供
- 某个旧入口只保留兼容转发，不再新增真实实现
- 某轮改造不影响存档字段与写回主链
- 某个旧文件重新恢复 `node --check` 或模板可复用能力

### E. 与计划文档的关系

当需求文档写完后，若要进入实现计划，建议对应在 `docs/plans/` 中继续回答：

- 第一刀从哪里下手
- 哪些区域本轮明确不碰
- 停手条件是什么
- 最小验证证据是什么
