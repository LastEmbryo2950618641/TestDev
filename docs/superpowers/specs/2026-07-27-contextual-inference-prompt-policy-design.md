# 角色卡上下文完整推演提示词策略设计

## 背景

部分生成型提示词使用“禁止编造未出现的组织或角色”等表述。其原意是禁止生成与当前世界观、人物背景或已知事实矛盾的内容，但模型可能将其理解为：只要输入没有逐字提供完整名称，就应省略该项或返回空字段。

这一歧义会使角色卡丢失已有背景能够支持的信息。例如，输入已经包含公司与职位、学校与学生身份或“计算机科学与技术硕士”，模型仍可能只生成人事归属中的公民身份，并令公司、学校及证书为空。现有代码只要看到结构合法的数组就会接受，无法从内容上发现这种遗漏；标准化阶段若又丢失单位、职位等原始依据，后续补全也无法利用它们。

## 目标

1. 角色卡所有可推演字段统一执行“有依据就必须完整补全；完全没有事实或背景依据时才允许为空”。
2. 生成型提示词允许并要求依据世界观、时代、地区、年龄、职业、教育经历、家庭关系、组织关系和通用常识作最小充分推演。
3. 输出必须具体、完善并可直接使用，不得以“某公司”“未知学校”“相关机构”“初中生”“普通职员”“成员”等模糊占位或上位概念替代可推演出的具体信息。
4. “禁止编造”统一解释为：禁止与明确事实或设定矛盾、缺乏上下文依据、无关扩张或批量生成无关实体；它不禁止为已有事实补足合理专名和必要细节。
5. 代码只负责保留依据、校验结构、归一化、去重和同步，不判断组织名是否真实、是否著名或是否“足够完整”。
6. 不增加额外 AI 请求；完整性检查在现有单次 Part1 生成中由模型输出前自检完成。
7. 历史原文、已发生事件和状态变化等事实读取型提示词继续保持严格证据边界。
8. 证书与称号继续只保存在角色卡 `profile`，不进入 RPG `values`。
9. 正文后的 Stage4 角色卡结算使用相同的完整性与具体性规则，但只处理本轮新确认或发生变化的稳定事实，不扫描旧角色卡缺项。

## 核心内容规则

### 事实优先与依据触发

- 明确事实优先，推演不得修改、否定或覆盖输入已经确定的内容。
- “依据”既包括输入逐字给出的事实，也包括可由当前世界观、年代、地区、人物年龄、职业、教育经历、关系和已知组织背景合理推出的信息。
- 一旦某字段存在依据，模型必须生成完整值，不得省略，不得仅填写抽象类别。
- 完全没有事实或背景依据的字段允许为空，不为了填满角色卡而无依据扩写。
- 合理推演得到的细节在 `reason` 中说明依据，不伪装成输入逐字给出的事实。

### 具体性与最小充分推演

- 缺少次要细节时，模型必须作与上下文一致的最小充分推演，补齐使字段可直接使用所必需的信息。
- 推演出的专名允许是设定内合理的新实体，但必须符合时代、地区、组织类型、人物年龄及经历。
- 不得使用模糊占位、未知标记或过度概括来规避推演。
- 例如，已知人物位于成都且是初三学生，应生成类似“成都第一中学 / 初三学生”的完整归属；不能输出“某中学 / 初三学生”“成都第一中学 / 初中生”或“学校 / 学生”。示例表达规则，不要求固定使用该校名。
- 不得为了丰富内容批量增加无关组织、角色、地点、资格、荣誉或经历。

### 全角色卡覆盖

该规则覆盖角色卡所有可推演字段，而不只覆盖四类身份字段。职业、人物说明、当前地点、外貌、性格、喜好、关系、技能、知识、专业、装备及其他由现有角色卡模板定义的可推演字段，只要存在依据，都必须完整补全并避免模糊占位。

## 四类身份字段

### 社群角色

表达人物在家庭、社区、朋友圈、兴趣小组或其他软性社会关系网中的具体位置。每项必须包含：

- 完整、可指认的社群或圈子名称。
- 人物在其中的具体角色。
- 事实来源或推演依据。

展示语义为 `<完整社群名>/<具体角色>`。

### 人事归属

表达人物在学校、公司、机关、国家、正式家庭组织或其他可指认组织实体中的正式或准正式身份。每项必须包含：

- 完整组织名称。
- 具体职位、学籍、年级或成员身份。
- 部门存在依据时补全具体部门。
- 事实来源或推演依据。

展示语义为 `<完整组织名>/<具体职位、学籍或成员身份>`，有部门时在现有数据结构中一并保存。不能用“初中生”代替“初三学生”，也不能用“职员”代替已有依据支持的具体岗位。

### 证书

学历学位、执照、资质、等级考试、职业资格、驾驶证，以及世界观中的魔法、武道或异能认证都属于 `certificates`。每项必须包含：

- `orgName`：完整认证或授予主体。
- `field`：具体认证领域。
- `level`：具体资格、学位或认证等级。
- `reason`：事实来源及合理推演依据。

展示语义为 `<完整授予组织>/<具体领域>/<具体资格或等级>`。例如，“计算机科学与技术硕士”必须形成一项证书；它不能被省略，也不应归入称号或社群角色。输入未逐字给出授予组织时，模型应依据地区、教育体系、年龄与经历合理补全具体主体。

### 称号

公众、行业圈、族群、国家群众、门派或其他社会群体对人物功绩、名望或代表性身份的稳定认可属于 `titles`。每项必须包含：

- `society`：完整认可群体。
- `field`：具体认可领域。
- `title`：具体称号。
- `reason`：事实来源及合理推演依据。

展示语义为 `<完整认可群体>/<具体领域>/<具体称号>`。普通职位、学历和自我描述不能自动变成称号。完全没有社会认可依据时允许为空。

### 归类完备性

- 上下文中的稳定身份、组织归属、资格认证和社会称号必须归入语义对应的类别。
- 边界模糊时选择最贴近语义的一类，不能因为分类犹豫而全部省略。
- 同一事实确实同时构成不同类别的信息时，可按各类别的不同语义分别生成。
- 归一化和去重继续使用现有字段结构与唯一键。

## 提示词分类与覆盖范围

### 生成型提示词

本次统一修改以下生成链路中的完整性规则：

- 角色卡 Part1 主生成提示词。
- 单字段或缺失字段补全提示词。
- 角色卡稳定事实更新提示词。
- 身份、组织、势力背景和地图等生成型提示词中会阻止合理背景推演的同类表述。

所有入口均使用同一语义：明确事实不可改；有依据必须具体补全；没有依据允许为空；不得用模糊占位规避生成。

### 事实读取型提示词

历史查询、微信原文、承诺、图片记录、已经发生的剧情事件和结算变化只能读取或归纳已有证据：

- 没有记录时不得伪造已经发生的事实。
- 允许根据角色性格组织表达方式，但不能创造不存在的历史内容。
- 状态更新必须由正文、用户输入或已经落库的资料支持。
- 不能仅凭背景推演成“已经发生”的具体事件。

此类提示词中的“禁止编造”不改为自由推演。

## Stage4 正文后角色卡结算

### 职责范围

Stage4 是正文后唯一负责角色卡稳定事实写回的阶段。本次修改覆盖完整链路：

- `stage4-settlement-window` 主结算提示词。
- `role-card-update` 角色卡专用提示词。
- `membership-update` 人事归属专用提示词。
- `real-world-agent-loop.js` 动态生成的类型短规则、JSON 合约说明、正确示例与错误反例。

Stage8 势力、Stage9 地图和 Stage11 新闻不负责角色卡更新，不注入角色卡规则。新登场人物仍只生成介绍卡，不能由 Stage4 自动升格为完整角色卡；角色卡结算只作用于玩家卡和已有完整角色卡。

### 本轮稳定事实边界

- Stage4 只记录本轮正文新确认或发生变化的稳定事实，不扫描或修复此前已经存在的角色卡缺项。
- 明确事实与有充分行为、对话或连续动作支撑的稳定变化必须结算；弱氛围暗示不得结算。
- “合理推演”只用于补全已经成立的本轮稳定事实所缺少的专名和次要细节，不能制造正文中没有发生的新入职、转学、获证或获奖事件。
- 例如，正文已经确认人物转入成都一所重点中学读初三，可以依据上下文补成完整学校名和“初三学生”；不能只凭人物年龄凭空结算一次转学。
- 正文或已加载资料已经给出组织、职位、学校、年级或授予主体时必须原样保留，只补充缺失部分。
- 本轮完全没有相关稳定变化时，角色卡与人事归属类型允许输出空数组。

### Stage4 输出一致性

Stage4 靠近最终输出的各层规则必须统一使用以下格式：

- 社群角色：`<完整社群名>/<具体角色>`。
- 人事归属：`<完整组织名>/<具体职位、学籍或成员身份>`。
- 证书：`<完整授予组织>/<具体领域>/<具体资格或等级>`。
- 称号：`<完整认可群体>/<具体领域>/<具体称号>`。

Stage4 主提示词必须明确：本轮存在角色卡稳定事实时不得以“空数组合法”为由省略更新。动态类型短规则、合约、示例和反例必须同时覆盖四类字段，避免专用提示词被靠近输出位置的弱规则覆盖。

同一组织身份优先由 `membership-update` 专用类型写入，并通过既有同步链路保持 Profile/RPG 一致；不得再生成含义完全相同的重复角色卡更新。角色卡其他稳定字段及社群角色、证书、称号继续由 `role-card-update` 处理。

## 单次生成与代码边界

### 单次生成自检

不增加第二次 AI 完整性复核请求。Part1 主提示词在输出前加入强制自检清单，要求模型：

1. 逐项核对原始上下文与角色卡全部可推演字段。
2. 检查是否存在有依据但遗漏、留空、简写或模糊化的内容。
3. 检查四类身份字段是否完整归类并具备全部必要组成。
4. 检查推演内容是否与明确事实、世界观、时代、地区和人物经历冲突。
5. 完成自检后一次性返回最终结构，不输出中间分析。

空数组在结构上仍然合法，但提示词明确限定：只有完全没有事实或背景依据时才能返回空数组。

### 代码职责

代码只负责：

- 在角色卡标准化和提示词上下文组装中保留职业、单位、职位、学校、年级、学历、关系及其他原始推演依据。
- 校验 JSON、字段类型、数组结构和每项必填子字段为非空字符串。
- 确保字段能够组成现有约定结构，例如人事归属具有 `orgName`、`title`、`reason`，证书具有 `orgName`、`field`、`level`、`reason`。
- 归一化、去重并执行既有 Profile/RPG 一致性同步。
- 在字段缺失、类型错误或子字段结构不完整时，沿用现有重试或缺失字段补全流程。

代码不负责：

- 判断组织名称是否真实、著名或足够完整。
- 维护学校、公司、认证机构或称号的名称字典。
- 使用“某公司”“未知学校”等语义黑名单拒绝结果。
- 根据业务内容判断结构合法的空数组是否缺少某项事实。
- 硬编码刘悠的毕业学校或任何人物的具体组织。

因此，在不增加 AI 复核请求且不实施代码语义校验的前提下，若模型违反提示词并返回结构正确但语义模糊或遗漏的内容，代码不会进行语义拦截。这是本设计明确接受的模型概率性边界。

## 数据流

1. 玩家或角色的完整原始资料进入标准化流程，单位、职位、学校、年级、学历和关系等推演依据得到保留。
2. 上下文组装把这些依据完整传入角色卡生成提示词。
3. Part1 在单次请求中依据明确事实与背景推演全部相关字段，并在输出前执行提示词内自检。
4. 代码校验返回结果的字段类型、数组结构和必填子字段。
5. 结构不完整时进入现有重试或缺失字段补全流程；结构完整时接受结果，不作名称语义判断。
6. `mergeGeneratedParts()` 与 `validate()` 保留并归一化生成值。
7. 既有显示及 Profile/RPG 同步链路消费最终角色卡字段。
8. 新游戏后每轮正文结束，Stage4 从本轮材料提取稳定事实；若涉及角色卡变化，主提示词、专用提示词和动态输出规则共同要求完整写入。
9. Stage4 对缺少次要细节的已成立事实作最小充分推演，再按结构合约输出；没有本轮变化时输出空数组。
10. 人事归属专用更新落库后沿用既有 Profile/RPG 双向一致性同步；其他角色卡字段写入 Profile。

## 错误处理

- JSON 无法解析、字段类型错误、数组项缺少必填子字段或必填字符串为空：判为结构不完整，沿用现有重试或补全机制。
- 明确事实与推演内容冲突：由提示词要求模型保留明确事实，只补充缺失部分。
- 完全无依据：允许字段或数组为空，不触发无意义补全。
- 结构正确但内容仍模糊或漏项：代码接受，不增加隐藏的语义规则或额外 AI 请求。
- Stage4 JSON 缺 key、字段类型错误、操作非法或值结构不完整：沿用现有滑动窗口补齐；代码不判断名称是否为全称。
- Stage4 本轮没有稳定变化：允许角色卡和人事归属输出 `[]`，不得借机修复旧角色卡。

## 测试与验收

1. 公司与职位依据被标准化流程保留并进入 Part1 上下文；提示词要求输出完整公司名和具体职位。
2. 学校与学生身份依据被保留并进入 Part1 上下文；“成都、初三学生”被要求生成完整学校名和“初三学生”，不能以“某中学 / 学生”或“中学 / 初中生”代替。
3. “计算机科学与技术硕士”被提示词强制归入证书，并要求补全授予主体、领域和等级；不能误归为称号或社群角色。
4. 没有资格依据的普通人物允许 `certificates: []`；没有社会认可依据时允许 `titles: []`。
5. 四类身份字段分别通过现有必填子字段结构校验，缺少任一结构成分时判为不完整。
6. 测试不建立具体组织名称字典，也不要求代码识别“某公司”等语义。
7. 事实读取型提示词仍明确禁止生成不存在的历史事件。
8. Markdown 提示词生成的运行时 JavaScript 与 Android 镜像保持一致。
9. 现有 Profile/RPG 四类字段同步和身份页显示测试继续通过。
10. Stage4 主提示词明确本轮存在角色卡稳定事实时不得返回空数组。
11. Stage4 动态类型短规则、JSON 合约、正确示例和反例均覆盖社群角色、人事归属、证书和称号的完整格式。
12. 本轮确认入职、升学、取得学历或执照、获得社会称号时，分别要求落入正确字段；“某公司/职员”“某学校/学生”“相关机构/证书”等只作为提示词反例，代码不以正则拒绝。
13. 没有本轮角色卡变化时仍允许 `[]`，介绍卡不会自动升格为完整角色卡。
14. Stage4 现有解析、滑动窗口、Profile/RPG 同步、运行时提示词及 Android 镜像测试继续通过。
15. 验收以新游戏生成及后续正文结算为准，不执行旧存档迁移测试。

## 非目标

- 不增加固定的第二次 AI 完整性复核请求。
- 不由代码判断自然语言内容是否具体、真实或合理。
- 不把所有职业、学历或关系自动转换成称号。
- 不放宽历史记录和结算变化的事实证据要求。
- 不修改证书与称号的 profile-only 数据边界。
- 不扫描、迁移或修复已有存档角色卡中的历史缺项。
- 不让 Stage8、Stage9 或 Stage11 承担角色卡更新职责。
