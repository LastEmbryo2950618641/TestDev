# Stage4 结算滑动窗口瘦身设计

## 背景

Stage4 当前滑动窗口容易退化成“半截文本续写”：残缺类型的旧输出尾巴会被回灌，Update/Init 全文说明书会压过本轮事实，长正文和无关合同会撑爆窗口。结果是模型倾向继续补旧文本，而不是按未完成类型重新输出完整结算块。

本设计目标是把 Stage4 改为“未完成类型整块重放”：Stage3 只负责正文；Stage4 在内部提取本轮稳定事实，并只依据这些事实完成当前窗口内未完成类型的结算。

## 目标

- 删除旧尾巴原文回灌。
- 删除 Update/Init 全文说明书注入。
- 删除 Init schema 全文注入。
- 删除非最后一批必须超过 1000 字的扩写要求。
- 已完成类型只保留列表，不保留完整旧块。
- 未完成类型必须从类型标题开始整块重输。
- Stage4 内部提取“本轮稳定事实”，不得输出中间过程。
- 保留每类“何时更新 + 更新行格式”的短规则，避免模型不知道怎么填。
- 支持明确事实与强暗示事实的保守结算，禁止弱氛围暗示触发结算。

## 非目标

- 不修改 Stage3 输出协议；Stage3 仍只输出正文。
- 不新增 Stage4a/Stage4b 双请求链路。
- 不持久化本轮稳定事实摘要。
- 不重写内部 update/init 数据结构。
- 不清理本任务范围外的既有未提交文件。

## 推荐方案

采用 Stage4 专用输入构建器，而不是只改模板或新增一次 AI 请求。

新增/调整的代码侧职责：

- `buildSettlementFactContext(...)`：构建 Stage4 本轮结算材料。
- `settlementTypeShortRules(...)`：生成当前窗口类型的短规则。
- `summarizeSettlementFailure(...)`：把残缺类型转成失败原因，不保留旧输出原文。
- `buildSettlementTypeWindowPrompt(...)`：改用短输入结构。
- `completeConfiguredSettlementKvWindow(...)`：未完成类型只保存失败原因，已完成类型继续移出后续请求。

## Stage4 Prompt 输入结构

Stage4 prompt 只接收以下块：

```text
本次必须返回的类型：
已完成类型：
未完成类型：
当前窗口起始类型：
当前窗口结束类型：
本回合参与者：
本轮结算材料：
类型短规则：
未完成类型原因：
全局输出规则：
```

删除以下旧输入块：

```text
残缺原因或尾部：
现有 Update 提示词摘要：
现有 Init 提示词：
现有 Init 字段 Schema：
正文：
```

其中“本轮结算材料”可包含：

- Stage3 正文压缩版。
- 场景锚定报告。
- 本回合参与者列表。
- 可选的基础状态短摘要。

它不能包含：

- 旧输出尾巴原文。
- 已完成类型完整块。
- Update/Init 全文说明书。
- 与当前窗口无关的长合同。

## Stage4 内部流程规则

Prompt 中要求模型按两步在内部完成：

```text
第一步：根据本轮结算材料提取“本轮稳定事实”。
第二步：只依据“本轮稳定事实”输出当前未完成类型的完整结算。
不得输出第一步过程。
```

补充硬规则：

- 不得从上轮截断位置续写。
- 若某类型上轮被截断，本轮必须从该类型标题开始完整重输。
- 已完成类型不得重复输出。
- 未列入本次必须返回的类型不得输出。
- 每个类型要么完整输出，要么不输出。
- 没有稳定变化时输出无变化完整块。

## 结算依据分级

```text
明确事实：可直接结算。
强暗示事实：可保守结算，但必须有明确行为、对话或连续动作支撑。
弱氛围暗示：不得结算。
```

类型边界：

- 强暗示可用于：基础结算、地图结算、系统记录、小幅情绪变化、当前场景焦点变化。
- 强暗示不可单独用于：感觉、关系、身体状态、穿着状态、物品状态、性经历、性历史、势力总览、势力结构。
- 感觉、关系、身体状态、穿着状态、物品、性经历、性历史、势力类必须以明确事实为主。

若依据强暗示结算，`变化原因` 必须写出具体行为或对话证据，但不要求输出“强暗示”字样。

## 类型短规则

每类短规则只保留两件事：

1. 什么时候才更新。
2. 更新行怎么写。

示例：

```text
情绪结算规则：
只有明确行为、对话或强行为暗示支撑时才更新；弱氛围不更新。
格式：更新N：情绪，情绪名，+/-数值，变化原因
```

```text
物品结算规则：
只有获得、失去、转移、损坏、消耗、购买成功被明确确认时才更新。
格式：更新N：物品，物品类型，物品名，事实或变化，变化原因
```

基础结算保留固定字段格式；其他类型沿用现有解析器能识别的中文 K:V 更新行格式。

## 未完成类型处理

当前逻辑会把未完成类型的旧输出行保存到 `partialByType`，下一轮作为“残缺原因或尾部”回灌。新逻辑改为只保存失败原因。

示例：

```text
情绪：缺少“结算结束：是”，需从“情绪结算：”开始整块重输。
物品：本轮未返回该类型，需从“物品结算：”开始整块输出。
```

禁止保存：

- 半截类型块正文。
- 已完成类型正文。
- 上轮输出尾巴。
- 模型旧回复中的修辞段落。

## 风险与缓解

### 风险：规则压缩后模型不知道怎么填

缓解：保留每类短规则和现有 `settlementTypeContracts()` 的输出格式，不删除“怎么填”的信息，只删除长说明书。

### 风险：过严导致暗示型事实漏记

缓解：引入明确事实 / 强暗示事实 / 弱氛围暗示三级规则。强暗示允许用于基础、地图、系统记录和小幅情绪变化。

### 风险：过松导致关系、感觉、物品乱更新

缓解：感觉、关系、身体、穿着、物品、性经历、性历史、势力类必须以明确事实为主，不能仅凭氛围暗示更新。

### 风险：和现有解析器不兼容

缓解：类型标题、`更新N：...`、`类型完成：是`、`结算结束：是` 保持现有格式；只改 prompt 输入和失败原因，不改解析器主协议。

## 验收标准

- Stage4 prompt 不再出现旧尾巴原文、Update/Init 全文、Init schema 全文、1000 字扩写要求。
- Stage4 prompt 明确要求内部提取稳定事实并只依据稳定事实结算。
- 未完成类型下一轮从类型标题开始整块重输。
- 已完成类型下一轮不再请求、不再输出。
- 类型短规则覆盖所有结算类型。
- 新增测试和既有回归全部通过。
- 不创建 git commit，除非用户明确要求。
