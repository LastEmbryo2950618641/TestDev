# 上线体验阶段提示词注入设计

日期：2026-07-10

## 目标

为“被上线操控”的角色反应增加一套可配置、可持续复用的阶段提示词机制。

本次方案目标：

- 保留一份可编辑的“上线体验总提示词模板”
- 由代码根据“上线次数 + 适应度”计算当前阶段
- 将阶段信息注入到即时上线反馈与后续正文链路
- 新增桌面 App 让用户配置该总提示词
- 不在 Stage1 中直接生成角色反应，只让 Stage1 继续承担资料收集职责

本次方案不做：

- 不开放每个阶段单独配置一份提示词
- 不把阶段阈值做成 UI 可编辑
- 不新增第二套独立 AI 流程

## 背景与现状

当前项目中，`control_experience` 已经存在完整数据基础：

- 角色卡初始化阶段存在 `control_experience.上线次数` 与 `control_experience.习惯程度`
- 运行态状态中存在 `onlineCount`、`feeling`、`adaptation`、`summary`
- `character-feedback` 已把 `上线次数`、`上线感觉`、`适应度`、`上线摘要` 注入到 prompt
- `story-agent-context` 已把 `control_experience` 摘要并入剧情上下文
- Stage1 已允许“上线体验”作为资料摘要的一部分进入后续阶段

因此，本次改动重点不是补数据结构，而是在现有数据链路上增加一层“阶段解释器 + 模板注入器”。

## 核心原则

### 1. Stage1 只收集资料，不直接写反应

Stage1 的职责保持不变：

- 规划还缺哪些资料
- 补足角色卡、场景、参与者、关系、上线体验摘要等上下文

Stage1 不负责：

- 直接生成上线心理反应
- 直接决定角色是恐惧、愤怒、兴奋还是冷静

### 2. 阶段只描述经历深度，不规定固定情绪

“上线次数 + 适应度”只用于判定：

- 她是否第一次经历
- 她对这种状态是否熟悉
- 她是否有心理准备
- 她对这种体验的认知承受程度与习惯程度

阶段信息不能直接写死成：

- 一定恐惧
- 一定抗拒
- 一定顺从
- 一定兴奋

最终情绪与反应必须结合角色性格、身份、当前场景来生成。

### 3. 提示词只保留一份总模板

用户通过桌面 App 编辑唯一一份“上线体验总提示词模板”。

代码运行时负责：

- 计算阶段
- 生成阶段说明
- 将阶段说明与角色上下文注入总模板

## 方案概览

### 运行流程

1. 读取角色当前 `control_experience`
2. 根据 `onlineCount + adaptation` 计算阶段
3. 生成：
   - `stageKey`
   - `stageLabel`
   - `stageDescription`
4. 读取用户配置的总提示词模板
5. 将阶段信息与角色上下文变量注入模板
6. 把注入后的规则块拼接进：
   - `character-feedback`
   - `story-engine`

### 挂载点

- Stage1：继续作为资料上下文来源
- `character-feedback`：即时上线反馈主入口
- `story-engine`：后续正文持续沿用

## 阶段划分

### 次数层

- `0次`：首次上线
- `1-10次`：早期重复体验
- `11-30次`：熟悉期
- `31次以上`：高频习惯期

### 适应度层

- `0-10`：极低适应
- `11-35`：低适应
- `36-65`：中适应
- `66-100`：高适应

### 输出原则

阶段计算器不直接输出情绪词结论，只输出“经历深度与适应深度说明”。

例如：

- `0次 + 0-10`
  - 首次
  - 几乎没有经验与预期
  - 认知冲击强
- `1-10次 + 0-10`
  - 已不是第一次
  - 能意识到这类状态再次出现
  - 仍未真正适应
- `11-30次 + 36-65`
  - 已形成一定经验
  - 对这种状态不再完全陌生
  - 反应中应体现熟悉感和应对感
- `31次以上 + 66-100`
  - 对这种状态已有较深经验
  - 具备较高熟悉度与适应度
  - 反应中应体现明显的习惯化和稳定化特征

## 默认总提示词模板

总模板目标：

- 先让 AI 理解当前上线阶段
- 再让 AI 根据角色性格、身份、场景生成反应
- 严禁机械复读阶段说明

默认模板只规定“如何使用阶段信息”，不直接替 AI 预设“应该恐惧”或“不要恐惧”。

模板需要支持的变量：

- `${被控制者}`
- `${上线次数}`
- `${适应度}`
- `${上线阶段}`
- `${阶段说明}`
- `${角色性格}`
- `${角色身份}`
- `${当前场景}`

## 配置 App 设计

### App 名称

`上线体验配置`

### 入口位置

手机桌面 App 列表新增一个图标入口。

### 字段

- `enabled`
  - 是否启用上线体验阶段提示词注入
- `masterPrompt`
  - 总提示词模板
- `preview`
  - 若干典型阶段说明的只读预览

### 操作

- 保存配置
- 恢复默认模板

本次 App 不支持：

- 编辑阈值
- 为每个阶段单独写提示词
- 多模板切换

## 数据与存储

### 新增配置数据

建议结构：

```json
{
  "enabled": true,
  "masterPrompt": "..."
}
```

### 存储位置

沿用现有 `storage.js` 风格落盘，作为全局用户配置持久化。

## 与 Stage1 的关系

本次设计明确要求：

- Stage1 不直接写角色反应
- Stage1 不负责上线提示词注入
- Stage1 只负责保证角色卡、性格、上线体验等资料能被后续生成阶段拿到

也就是说：

- Stage1 是资料来源层
- 阶段计算器是规则解释层
- `character-feedback / story-engine` 是生成使用层

## 默认阶段说明写法原则

阶段说明必须：

- 客观描述当前经历深度与适应深度
- 不预设固定情绪结论
- 不替角色下最终心理判断
- 让后续 prompt 能结合角色性格自然展开

示例写法：

```text
这是她第一次经历被上线操控，对这种身体控制权变化几乎没有相关经验与预期。反应应体现首次遭遇时的陌生感、突发感与认知冲击，并结合角色性格、身份和当前场景自然展开。
```

## 风险与约束

### 风险

- 如果阶段说明写得过于情绪化，AI 会被提前锁死
- 如果总模板写得过于抽象，阶段差异会不明显
- 如果同时在 `character-feedback` 和 `story-engine` 中重复注入过多规则，可能导致正文变重

### 约束

- 必须避免把规则写成固定句式模板
- 必须避免“第一次就恒恐惧”“次数高就恒顺从”这类结论化描述
- 必须保留角色个体差异

## 验收标准

满足以下条件视为方案成功：

- 用户可在桌面 App 中编辑唯一一份上线体验总提示词
- 系统可根据 `onlineCount + adaptation` 自动计算阶段
- `character-feedback` 能稳定反映阶段差异
- `story-engine` 后续正文能延续同一阶段倾向
- 同一阶段下，不同性格角色反应不会明显同质化
- 阶段说明本身不写死情绪结论

## 后续实施建议

实施时建议按以下顺序：

1. 先实现阶段计算器
2. 再实现配置存储
3. 接入 `character-feedback`
4. 接入桌面 App
5. 最后接入 `story-engine`

这样可以先验证“即时反应”是否正确，再扩展到持续正文。
