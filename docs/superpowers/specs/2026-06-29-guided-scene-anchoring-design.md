# 引导式场景锚定推演链路设计

日期：2026-06-29

## 目标

在现有 Gamefy 原生模型链路中，为现实推演与异世界/操控剧情推演统一引入“引导式场景锚定推演链路”。

核心目标：

- 先规划查询，再受控加载资料。
- 查询规划与场景锚定报告使用中文 K:V 固定结构，不要求模型输出 JSON。
- 资料请求也使用中文语义格式，由程序映射到白名单函数。
- AI 面向输出中的角色、地点、势力、作品、世界线等名称必须使用可读全称，不得用内部 id、缩写 id 或代号替代。
- 先生成场景锚定报告，再生成正文。
- 角色卡可提前加载，但加载角色卡不等于当前参与者，也不等于可以结算。
- 随机场外主动事件增加世界活性，默认不污染当前场景；若时间、空间、能力/交通、动机和因果都成立，现实与异世界都允许偶尔闯入。

一句话：先用中文结构规划资料，再程序化加载资料，再用中文结构锚定场景，最后按锚定边界写正文和结算；加载角色卡服务于准确性，不自动代表参与和结算。

## 非目标

第一版不做：

- DeepSeek BYOK。
- 外部向量数据库。
- 完整 L1/L3 长期缓存系统。
- 复杂 UI 配置页。
- 全流程严格 JSON。
- 自动大规模世界记忆压缩。
- 服务端函数。

原因：当前优先跑通 Gamefy 原生模型最小闭环，避免一次引入过多变量。

## 现有基础

可复用模块：

- `publish/real-world-agent-loop.js`：现实与异世界当前共用的 `request_context → loadRequests → narration → stage3 updates` 多步链路。
- `publish/real-world-agent-context.js`：现实角色卡、地点、历史、记忆、物品等资料查询能力。
- `publish/story-agent-context.js`：异世界/操控剧情的作品设定、世界线、角色、记忆等资料查询能力。
- `publish/prompts/materials/real-world-materials.js`：现实资料清单与资料 session 记录。
- `publish/prompts/materials/work-lore-materials.js`：作品/异世界资料清单与资料 session 记录。
- `publish/update/*`：已有通用结算与 UI 展示。

当前主要问题：

- `autoLoadForStep()` 主要依赖 `actionText.includes(name)`，无法覆盖“地点/因果/伏笔引导”的候选角色。
- `participants` 没有稳定分层，强制出场、候选、背景、禁止角色容易混在一起。
- `stageParticipants()` 会通过 `loadedRoleCardParticipants(loaded)` 把已加载角色卡无条件带入 Stage3，导致“加载即参与/结算”的污染风险。
- 现实与异世界虽共用 loop，但缺少统一的 guided 协议，导致查询、正文、结算边界没有明确分工。

## 总体方案

采用统一 Guided Pipeline，共享核心逻辑，按 `config.mode` 区分现实与异世界规则。

流程：

```text
Stage1 Guided 查询规划循环
  → 第1轮中文 K:V 查询规划
  → 程序执行中文资料请求映射后的白名单资料加载
  → 第2轮基于已加载资料判断是否仍缺关键资料
  → 必要时继续加载资料
  → 输出资料已足够
→ Stage2 场景锚定报告（单独 LLM 调用，中文 K:V）
→ Stage3 正文生成
→ Stage4 严格结算
```

Stage1 不是一次性规划，而是保留现有 loop agent 的多轮资料补齐能力。每一轮都使用中文 K:V 协议；每轮加载后，下一轮必须基于“已动态载入资料”判断是否仍缺会直接改变正文结果、人物反应、出场资格或结算边界的关键资料。

### 现实与异世界差异

`real` 模式：

- 地点依据现实地图、房间、公司、微信、电话、交通距离。
- 随机事件可以是微信、电话、附近等待、临时到场、背景行动。
- 闯入需满足现实距离、时间窗口、交通方式、动机和因果伏笔。

`story` 模式：

- 地点依据作品世界地点、原作时间线、世界线、能力规则。
- 随机事件可以是传令、远处异动、原作角色行动、环境征兆、魔术/能力影响。
- 闯入需满足作品设定、canon/时间线、空间距离、角色能力/交通方式、动机和因果伏笔。
- 禁止为了热闹硬塞原作角色，禁止使用当前阶段角色不应知道的后期情报。

## Stage1：Guided 查询规划循环

执行者：Gamefy LLM + 程序资料加载。

目的：通过有限多轮查询规划与资料加载，逐步补齐本轮正文所需的关键资料、参与者分层和随机事件候选；不写正文、不结算。

循环规则：

- 第 1 轮基于基础上下文、用户行动、随机事件候选池规划资料请求。
- 后续轮基于基础上下文、用户行动、已动态载入资料、上一轮查询规划继续判断是否仍缺关键资料。
- 如果仍缺资料，输出新的中文 K:V 查询规划与资料请求。
- 如果资料已足够，输出固定中文 K:V，并在 `资料状态` 中写 `资料已足够`，`资料请求：无`。
- 默认最多 3 轮 guided 查询；复杂异世界、跨地点、旧因果、多人候选场景最多 4 轮。
- 后续轮只允许请求会直接改变正文结果、人物反应、出场资格或结算边界的资料。
- 衣着氛围、背景补全、重复确认、无效替代查询不得继续请求。

### 输出协议

Stage1 每一轮都只输出中文 K:V，不输出 JSON、Markdown、正文或解释。字段必须按固定顺序输出。

必填字段：

```text
查询规划：
资料状态：
地点查询：
地点查询理由：
因果查询：
因果查询理由：
冲突查询：
冲突查询理由：
强制出场：
高优先候选：
戏剧候选：
禁止出场：
随机事件候选：
随机事件闯入条件：
资料请求：
资料请求结束：
```

`资料状态` 只能写 `继续请求资料` 或 `资料已足够`。`资料请求` 字段用于概述请求数量或写“无”；具体请求用 `资料请求1`、`资料请求2` 依次输出，可以为 0 到多条；无请求时仍输出 `资料状态：资料已足够`、`资料请求：无` 与 `资料请求结束：是`。

### 中文资料请求格式

资料请求不用英文 `skill/method/params`，统一使用中文语义格式。涉及角色、地点、势力、作品、世界线等名称时必须写可读全称，不得用内部 id、缩写 id 或代号代替；程序侧再将全称解析为稳定 id：

```text
资料请求1：角色查询，搜索角色卡，刘思琪，2026现代都市现实世界
资料请求2：地点查询，查询附近地点，当前地点
资料请求3：世界线查询，按关键词搜索，刘思怡 房间 门口
资料请求4：记忆查询，搜索角色记忆窗口，player-self，刘思琪 choker
资料请求5：作品设定查询，搜索人物，阿尔托莉雅，Fate/stay night
资料请求结束：是
```

资料已足够时仍输出完整 K:V，但不再请求资料：

```text
查询规划：已加载资料足够生成本轮正文。
资料状态：资料已足够
地点查询：无新增
地点查询理由：当前地点与邻近空间已足够判断出场边界。
因果查询：无新增
因果查询理由：旧伏笔与直接因果已足够。
冲突查询：无新增
冲突查询理由：直接互动对象反应可由已加载资料判断。
强制出场：玩家；直接互动对象
高优先候选：无
戏剧候选：无
禁止出场：无
随机事件候选：无
随机事件闯入条件：无明确条件则禁止闯入
资料请求：无
资料请求结束：是
```

解析规则：

1. `资料请求N` 按中文逗号、英文逗号、顿号或分号切分。
2. 第 1 段是查询类别。
3. 第 2 段是查询动作。
4. 后续段是参数。
5. 程序通过白名单将“查询类别 + 查询动作 + 参数”映射为内部 `{ skill, method, params }`。
6. 未知类别、未知动作、参数不足或 mode 不允许的请求不得执行。

## Stage1 解析策略

代码侧按以下顺序解析：

1. **固定顺序直接映射**：按预定义 key 顺序读取每个 K:V。
2. **Key 相似度匹配兜底**：例如“必须出场”可映射到“强制出场”，“不能出场”可映射到“禁止出场”。只允许映射到已知字段集合。
3. **中文资料请求映射**：将 `资料请求N` 映射到白名单函数。
4. **解析评分**：对每次输出计算映射成功度。

映射成功度：

```text
映射成功度 = 已成功映射必填字段数 + 已成功映射资料请求数 + 关键边界字段权重
映射成功率 = 实际得分 / 满分
```

关键边界字段包括：

- `强制出场`
- `禁止出场`
- `随机事件闯入条件`
- `正文写作重点`（场景锚定报告阶段）
- `结算边界`（场景锚定报告阶段）

### 两次请求取最高成功度

每次 AI 返回都要解析并评分：

```text
第 1 次请求
→ 结构映射 + 相似度映射 + 资料请求映射
→ 记录 partialResultA 和 scoreA
→ 若完整通过，直接使用
→ 若不完整，带错误原因重试

第 2 次请求
→ 同样映射，并重新判断资料是否已足够
→ 记录 partialResultB 和 scoreB
→ 若完整通过，直接使用
→ 若仍不完整，以 score 更高的一份为主，合并另一份中成功映射且不冲突的新增资料请求和候选信息
```

阈值规则：

- 成功率 `>= 80%`：使用最佳 partialResult，并合并另一份中成功映射且不冲突的新增资料请求和候选信息；缺失字段用保守默认值补齐，无法映射的资料请求丢弃，trace 标记 `parseDegraded: true`。
- 成功率 `< 80%`：直接抛出解析异常，提示“解析错误请重试”，不进入正文。

同分优先级：

1. 成功解析关键边界字段更多者。
2. 成功解析资料请求更多者。
3. 第二次结果，因为它接受过纠错提示。

合并规则：

- 用户明确约束、禁止出场、强制出场不得被重试结果删除。
- `资料状态` 以证据更充分的一方为准：若第二次能说明“资料已足够”，可结束查询循环；若任一结果有成功映射且不重复的关键资料请求，可并入待加载请求。
- 同一查询类别与动作、参数相同的资料请求去重。
- 冲突候选分层以更保守层级为准：强制出场优先于候选，禁止出场优先于任何出场层级。
- 无法解释的冲突不合并，保留主结果并在 trace 中记录 `mergeConflicts`。

保守补齐只允许在成功率 `>= 80%` 时启用。

## Stage1b：受控检索

执行者：程序逻辑。

输入：Stage1 每轮成功解析出的中文资料请求。

规则：

- 只执行白名单映射成功的资料请求。
- 角色卡最多 3 张。
- 地点资料最多 2 条。
- 历史/记忆/势力/物品摘要最多 2 条。
- 禁止角色不加载完整角色卡。
- 成功加载的角色卡标记为 `loaded-role-card`，只代表资料已加载，不代表出场或结算。

角色卡加载优先级：

1. 强制出场：必加载。
2. 高优先候选：优先加载，计入 Top3。
3. 戏剧候选：只有仍有名额且场景开放时加载。
4. 背景角色与随机场外角色：默认不加载完整卡。

`autoLoadForStep()` 保留作为兜底：当 action 明确提到角色名时可自动加载角色卡，但仍只标记为 `loaded-role-card`。

## Stage2：场景锚定报告

执行者：Gamefy LLM，单独一次调用。

目的：把多轮查询规划、全部已加载资料、参与者分层、随机事件和用户约束整合为正文前决策报告。

长度建议：

- 简单行动：200-350 字。
- 普通多人/地点行动：400-650 字，默认目标。
- 复杂跨地点/跨世界/旧因果行动：700-1000 字上限。

### 输出协议

场景锚定报告只输出中文 K:V，不输出 JSON、Markdown、正文或解释。字段必须按固定顺序输出。

必填字段：

```text
场景锚定报告：
当前地点：
当前时间：
空间状态：
当前动作：
强制出场：
高优先候选：
戏剧候选：
禁止出场：
随机事件影响：
正文写作重点：
结算边界：
```

示例：

```text
场景锚定报告：本轮发生在刘思琪房间门口，动作焦点是玩家拉扯 choker。
当前地点：刘思琪房间门口
当前时间：12:56
空间状态：门口与相邻房间距离较近，较大声响可能被听见，但相邻角色不能无理由立刻闯入。
当前动作：玩家拉扯刘思琪的 choker。
强制出场：刘悠；刘思琪
高优先候选：刘思怡，条件是听见动静或已有相邻房间伏笔。
戏剧候选：无
禁止出场：无
随机事件影响：王主管可能发微信询问位置，默认只形成通知压力，不代表本人出场。
正文写作重点：写清拉扯动作、刘思琪身体和情绪反应、门口空间压迫感，避免无证据让刘思怡强行入场。
结算边界：只结算刘悠与刘思琪；刘思怡若正文未确认入场和互动，不结算；王主管只发微信不结算。
```

解析策略与 Stage1 相同：固定顺序直接映射、key 相似度兜底、两次请求取最高成功度、成功率低于 80% 则抛异常。

## Stage3：正文生成

执行者：Gamefy LLM。

输入：

- 用户行动。
- 基础上下文。
- 已动态加载资料。
- Stage1 多轮查询规划摘要。
- 场景锚定报告。
- 写作风格。

规则：

- 正文必须服从场景锚定报告。
- 强制出场角色必须处理。
- 高优先候选可以自然入场，但不得强行出现。
- 戏剧候选只有触发理由充分时才出现。
- 随机事件默认场外；若闯入，必须在正文中写清成立条件。
- 禁止出场角色不得出现、不得发声、不得被代行动、不得通过随机事件绕过限制。
- 不替玩家执行下一步新行动，不把亲吻、抚摸、摩擦、按住等动作自动扩展为脱衣、转移地点、插入、高潮等未输入的新阶段。

## Stage4：严格结算

执行者：现有 Stage3 分组更新，但模型输出也改为中文 K:V；程序负责把中文结算 K:V 映射为内部更新补丁。

复用分组：

- `metrics`
- `bodySex`
- `survival`
- `worldSocialInventory`

新增结算边界：

可结算：

- 玩家本人。
- 场景锚定报告中的强制出场角色。
- 正文中实际入场、行动、互动、被影响的候选角色。

不可结算：

- 只是被加载角色卡的人。
- 只是候选但未入场的人。
- 随机延迟事件或纯场外事件角色。
- 背景提及角色。
- 禁止出场角色。

关键改动：`loadedRoleCardParticipants()` 不能再无条件加入 `stageParticipants()`。

结算 prompt（现有 Stage3 更新 prompt）需注入：

- 场景锚定报告。
- 结算边界。
- 本回合可结算参与者。
- 禁止结算对象。

### 结算中文 K:V 协议

结算阶段不要求模型直接输出最终 JSON。每个结算分组输出固定中文 K:V，再由程序映射为内部 `genericUpdates`、基础字段或分组补丁。

基础结算字段示例：

```text
基础结算：
结算状态：需要更新
经过时间：180秒
当前状态：呼吸急促，仍停在房间门口
当前目标：处理刘思琪的即时反应
场景标题：房间门口的拉扯
地点名称：刘思琪房间门口
备选行动1：松开 choker 并观察她的反应
备选行动2：低声询问她是否疼痛
备选行动3：后退半步保持距离
备选行动4：查看门外是否有人靠近
结算结束：是
```

分组结算示例：

```text
情绪感觉结算：
结算状态：需要更新
结算对象：刘思琪｜角色｜允许结算
更新1：情绪，紧张，+2，正文确认 choker 被拉扯后身体紧绷
更新2：对玩家感觉，警惕，+1，正文确认她对玩家动作产生防备
结算对象结束：刘思琪
结算结束：是
```

```text
身体穿着结算：
结算状态：无变化
结算理由：正文只确认拉扯动作和短期身体反应，没有确认新的身体状态、性经历、穿着变化或物品变化
结算结束：是
```

规则：

- 结算 K:V 只能描述正文与锚定报告已确认的变化。
- `结算对象` 只写显示名全称、对象类型与结算许可，不要求也不信任 AI 输出内部 id；角色、地点、势力等对象不得用 id、缩写 id 或代号替代，程序必须根据已知状态库、角色卡或姓名匹配稳定 id。
- `结算对象` 必须来自可结算参与者；禁止对象、仅加载角色卡对象、未入场候选不得输出更新。
- 每条 `更新N` 使用中文类型与证据，由程序映射到白名单更新类型。
- 未命中白名单更新类型、对象不在可结算范围、证据不足的更新必须丢弃。
- 若分组无变化，必须输出 `结算状态：无变化` 与 `结算理由`。
- 解析策略沿用固定顺序直接映射、key 相似度兜底、两次请求取最高成功度、低于 80% 抛异常。

## 随机事件规则

现实和异世界都启用随机事件，但默认场外。

程序可随机抽取 0 到 3 个外部角色加入 Stage1 prompt。建议概率：

- 0 人：50%
- 1 人：30%
- 2 人：15%
- 3 人：5%

同一角色主动事件冷却 3 到 5 轮。

随机事件可以闯入，但必须同时满足：

- 时间窗口成立。
- 空间距离或移动方式成立。
- 角色动机成立。
- 现实交通或异世界能力/规则成立。
- 与当前行动或历史伏笔存在因果连接。

禁止：

- 为热闹硬塞角色。
- 禁止出场角色通过随机事件绕过限制。
- 纯场外事件参与结算。
- 异世界违反 canon、当前阶段信息或地点规则。

## 参与者分类

### 强制出场

来源：

- 玩家本人或被操控主体。
- 正在此地。
- 要去此地。
- 跟踪、陪同、约定或伏笔确认会到场。
- 与本轮动作直接互动。

行为：

- 必须进入正文。
- 可参与结算。
- 角色卡优先加载。

### 高优先候选

来源：

- 未回收伏笔涉及。
- 地点/职责/关系天然合理。
- 当前动作可能触发其反应。

行为：

- 优先加载角色卡。
- 可以进入正文。
- 未入场不得结算。

### 戏剧候选

来源：

- 与主角情绪或目标有即时冲突。
- 最近情绪激动。
- 职责上可能介入。
- 听见声响、收到通知、路过、被传令。

限制：

- 只在开放场景启用。
- 不强制出场。
- 未入场不得结算。

### 禁止出场

来源：

- 用户明确禁止。
- 系统约束禁止。
- 当前地点、时间、世界观或 canon 不可能出现。

行为：

- 不加载完整卡。
- 不进入正文。
- 不主动联系。
- 不通过随机事件绕过限制。
- 不结算。

## 错误与兜底

### 解析重试与资料轮次区分

- 解析重试：同一轮查询规划输出格式不合格，最多请求 AI 重来 1 次；两次结果都评分，并取映射成功度最高者。
- 解析重试不是单纯修格式：重试 prompt 必须携带本轮已成功映射的字段、已成功映射的资料请求、已丢弃请求、错误原因和当前已动态载入资料，让 AI 同时重新判断“资料是否已足够”。
- 重试时允许在原本已成功映射内容基础上新增必要资料请求，也允许把 `资料状态` 改为 `资料已足够`；但不得删除用户明确约束、禁止出场、已确认强制出场等关键边界。
- 两次结果合并时，不是简单取单份全文：以映射成功度最高者为主，并可合并另一份中成功映射且不冲突的新增资料请求和候选信息；冲突字段以关键边界更完整、证据更充分的一方为准。
- 资料轮次：上一轮资料加载成功后，仍缺关键资料，进入下一轮 guided 查询；默认最多 3 轮，复杂场景最多 4 轮。
- 解析重试不计入资料轮次；资料轮次只在成功解析并执行资料加载，或成功解析为 `资料状态：资料已足够` 后推进/结束。

### 查询规划解析失败

若同一资料轮次内两次 Stage1 输出的最佳映射成功率 `< 80%`：

```text
抛出解析异常：解析错误请重试。
不进入正文，不使用低质量结构。
```

若最佳映射成功率 `>= 80%` 但不完整：

```text
使用最佳 partialResult。
缺失字段用保守默认值补齐。
无法映射的资料请求丢弃。
trace 标记 parseDegraded: true。
```

保守默认值：

```text
高优先候选：无
戏剧候选：无
随机事件候选：无
随机事件闯入条件：无明确条件则禁止闯入
结算边界：只结算玩家与正文实际确认互动对象
```

### 查询循环耗尽

若达到最大资料轮次仍未输出 `资料状态：资料已足够`：

```text
停止继续请求资料。
使用已加载资料进入场景锚定报告。
场景锚定报告必须标记：资料轮次已达上限，未证实内容按保守原则处理。
后续正文不得补完无证据设定；结算边界按正文确认事实收紧。
```

### 场景锚定报告解析失败

同样使用两次请求取最高成功度和 80% 阈值。

若低于 80%，抛出解析异常，不进入正文。

若达到 80%，使用最佳 partialResult 并保守补齐。

### 资料请求映射失败

单条资料请求失败不导致整份规划失败，但会计入成功率。

失败请求：

- 不执行。
- 写入 `droppedMaterialRequests`。
- 若失败过多导致成功率低于 80%，整体抛异常。

## 验收标准

完成后应满足：

- 现实与异世界都经过多轮 guided 查询规划循环、资料加载、场景锚定报告、正文生成、严格结算。
- Stage1 每轮、场景锚定报告与结算更新都使用中文 K:V，而不是要求模型直接输出 JSON。
- 资料请求使用中文语义格式，并由程序映射到白名单函数。
- 同一资料轮次内两次解析取映射成功度最高者，并合并另一份中成功映射且不冲突的新增资料请求和候选信息；成功率低于 80% 时抛出解析异常。
- 角色卡提前加载更合理，但不会因为被加载就自动参与正文或结算。
- 正文出场受场景锚定报告控制。
- 随机场外事件能增加世界活性；现实与异世界都可偶尔闯入，但必须满足合理条件。
- 禁止出场约束在查询、正文、随机事件、结算阶段均生效。
- Stage4/现有 Stage3 更新只结算玩家、强制出场、正文实际确认入场/互动/被影响的角色；中文结算 K:V 需经白名单映射后才生成内部更新补丁。

## 设计原则

KISS：不引入 DeepSeek、外部向量库、复杂 UI，先改现有 loop/context/materials。

YAGNI：第一版不做完整 L1/L3 缓存，不做复杂 AST，只做固定中文 K:V + 相似度兜底。

DRY：现实与异世界共享 guided pipeline、中文解析、资料请求映射、锚定报告、结算 K:V 映射和结算过滤。

SOLID：查询规划、资料检索、场景锚定、正文生成、结算边界分工清晰。解析器只负责结构解析，context 只负责资料映射，loop 只负责编排。
