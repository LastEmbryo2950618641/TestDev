# 项目结构规范

本文档用于补充根 `README.md`，重点说明后续代码应如何落位、哪些边界必须保持清晰，以及 AI 在实现新功能时应如何避免继续把项目写散。

## 1. 总体原则

项目后续采用“功能域收敛 + 平台能力隔离 + 文档先行”的演进方式。

核心原则：
- 业务规则与平台实现分离。
- 状态判断应有单一权威来源。
- 新功能优先落在明确功能域，而不是继续扩散到全局入口。
- 中大型改动先有需求或计划文档，再进入实现。
- 目录规范不仅服务阅读体验，也服务未来 `exe / apk` 的多端复用。

## 2. 功能域建议

建议后续逐步围绕以下功能域收敛：

- `control`：控制角色、连接、上线、下线、首页当前目标显示。
- `control-experience`：上线体验、阶段规则、体验配置、注入逻辑。
- `character`：角色资料、角色反馈、角色状态摘要、角色卡。
- `real-world`：现实世界推演、日志、事项、显示状态。
- `wechat`：微信联系人、消息、图片、微信相关状态。
- `prompt`：提示词模板、阶段规则、注入配置。
- `storage`：存档、SQLite、持久化兼容。
- `body-figure`：身体图、外观资源、资源索引。
- `platform`：文件系统、宿主桥接、key 管理、dev-only 能力。

现阶段不要求一次性迁完，但以后任何新增逻辑都应优先归属到这些域之一。

## 3. 入口文件约束

当前入口主要集中于：
- `publish/index.html`
- `publish/game.js`
- `publish/boot/*`

约束：
- `index.html` 负责页面结构与挂载点，不负责复杂业务判断。
- `game.js` 负责装配与状态注册，但不应继续无限膨胀。
- 复杂业务判断应逐步沉到对应功能域文件中。
- `script-manifest` 需要保持与真实落地模块同步，新增运行时模块时必须同步登记。

## 4. 状态规范

每个新功能在实现前必须明确：
- 权威状态字段是什么。
- 谁负责更新它。
- 谁负责消费它。
- 是否需要持久化。
- 是否影响历史存档兼容。

禁止：
- 同一业务状态在多个文件中各写一套判断逻辑。
- 页面直接拼凑“猜测状态”来驱动 UI。
- 通过临时字段绕开现有状态链路。

## 5. 平台能力规范

以下能力统一视为平台能力，不允许直接散落到业务文件：
- 本地文件读写
- 用户生成资源落盘
- key 文件或密钥读取
- 宿主通信
- 本地服务专属接口
- 平台差异判断

后续建议逐步形成 adapter 层，例如：
- `platform/storage-adapter`
- `platform/file-adapter`
- `platform/host-adapter`
- `platform/ai-adapter`

## 6. 文档落位规范

### 需求文档

放在：`docs/requirements/`

适用：
- 描述用户需求、目标行为、影响范围。

### 实现计划

放在：`docs/plans/`

适用：
- 拆解实现步骤、模块影响、数据变更、风险与验收项。

### 架构文档

放在：`docs/architecture/`

适用：
- 结构规范
- 模块边界说明
- 平台适配原则
- 长期重构方向

### 游戏规则文档

放在：`docs/game-rules/`

适用：
- 阶段规则
- 提示词规则
- 结算规则
- 角色行为约束

## 7. 资源落位规范

- `assets/`：原始资料、设定资料、整理用资源。
- `publish/assets/`：运行时浏览器直接访问的资源。
- `logs/`：本地调试与运行日志。

对运行时生成物，必须先说明：
- 是否属于用户内容。
- 是否应提交到仓库。
- 是否仅保存在本地。

## 8. AI 修改代码时的最小流程

后续 AI 在实现中大型需求时，推荐遵循：

1. 阅读根 `README.md`
2. 确认功能归属的系统
3. 判断是否需要先补需求或计划文档
4. 明确权威状态来源
5. 再进入实现
6. 完成后说明影响文件、状态、资源与持久化范围

## 9. 近期结构治理优先级

优先建议后续逐步治理：

1. `control` 相关状态与 UI 判断
2. `platform` 相关本地能力
3. `storage` 持久化边界
4. `body-figure` 用户生成资源逻辑
5. `prompt` / `control-experience` 规则收敛

## 10. 仓库卫生与编码约束

- 中文文档和中文字符串默认使用 `UTF-8` 保存。
- 不要因为终端显示异常就直接认定文件损坏，先用显式 UTF-8 方式复核。
- `.bak`、`.bak2`、临时恢复文件、日志文件不是正式架构的一部分。
- 如果确实需要保留临时恢复文件，必须在相关计划或修复说明中写明原因。

## 11. 禁止事项

禁止以下行为：
- 未确认边界就跨多个文件直接硬改。
- 把平台实现混入业务规则。
- 在 `game.js` 持续无边界堆新系统。
- 复制已有状态判断而不复用权威方法。
- 将日志、截图、临时文件混入正式资源目录。
- 让新目录规范与旧兼容入口同时失控，导致后续会话无法判断真实入口。

本文档的目的不是一次性冻结结构，而是为后续长期演进提供统一约束。
