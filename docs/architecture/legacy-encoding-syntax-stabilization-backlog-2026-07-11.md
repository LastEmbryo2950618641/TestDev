# Legacy Encoding And Syntax Stabilization Backlog（2026-07-11）

本文档用于记录当前最影响持续改造速度与稳定性的历史污染问题，并给出推荐处理顺序。

这里的“历史污染”主要指两类：

- 编码污染：中文内容被错误解码，出现乱码、半残缺文本、不可安全整段替换的历史文件
- 语法污染：老文件中已经存在会影响最小校验、局部修改或工具操作的语法异常片段

它服务于以下目标：

- 降低后续结构化改造的编辑风险
- 提升 `node --check`、局部检索、最小补丁替换的可靠性
- 减少因为历史乱码导致的误替换、误覆盖、误判
- 为未来 exe / apk 多端共用结构整理提供更稳定的基础

## 1. 分级标准

### P0：优先稳定化

满足任一条件即可进入 P0：

- 会阻断当前模块的最小语法检查
- 会显著影响后续局部补丁编辑
- 已经在近期改造中反复暴露问题
- 如果不先稳定化，会迫使后续会话绕开正常验证手段

### P1：应尽快清点与逐步修复

通常表现为：

- 文件还能继续局部编辑，但乱码明显
- 当前不会立刻阻断改造，但持续增加误替换风险
- 已经影响文档可读性、模板消费可见性或边界理解

### P2：先记录观察，后续随模块推进顺手清理

通常表现为：

- 问题目前可控
- 对正在推进的路线影响不大
- 还没有必要专门开一轮稳定化处理

## 2. 当前 P0 清单

### publish/ui/settings/view-helpers.js

当前问题：

-
`node --check publish/ui/settings/view-helpers.js` 当前失败
- 文件内已确认存在断串、破损模板字符串与历史乱码混合污染
- 这会直接阻断 settings 展示层 helper 的继续对象化

当前风险：

- 后续会话难以区分“旧污染”与“新改动”
- 无法稳定依赖最小语法检查做验收
- 会迫使协作者绕过正常验证，放大误改风险

建议处理方式：

1. 单独开一轮 helper 语法恢复
2. 只修能恢复
`node --check` 的最小片段
3. 不混入设置功能改造、provider 改造或保存链改造

### publish/settings-actions.js

当前问题：

-
`node --check publish/settings-actions.js` 当前失败
- 文件前部已存在断串，且靠近超时包装与测试调用链
- 这说明历史污染已经进入动作与请求入口层

当前风险：

- 继续在该文件上混做功能开发风险很高
- 很容易误伤请求链、保存链或 system test 行为
- 会拖慢后续多端结构整理与验证节奏

建议处理方式：

1. 将其单列为 P0 语法稳定化项
2. 放在 helper 语法恢复之后处理
3. 稳定化完成前，不在该文件上做非必要结构性改造

### `publish/faction-actions.js`

当前问题：

- `node --check publish/faction-actions.js` 命中历史语法异常
- 异常并非本轮新引入，而是文件既有污染
- 这会直接削弱 `faction` 后续每一刀展示层改造的最小验收能力

当前风险：

- 即使本轮只改兼容壳，也无法依赖整文件语法检查确认安全
- 后续会话可能误把历史问题当成新改动引入的问题
- 容易导致“为了绕开校验而减少自检”这种坏习惯

建议处理方式：

1. 单独开一轮“语法稳定化”处理，不混入新功能改造
2. 先只修能恢复 `node --check` 的最小污染片段
3. 修复后补一份 validation 或风险记录，说明这是稳定化而非玩法改造

### `README.md`

当前问题：

- 根 README 仍存在大面积历史编码污染
- 虽然近期已补充有效入口，但主文大段内容可读性仍然较差

当前风险：

- 后续 AI 会话把根 README 视为入口时，容易先读到乱码
- 它会降低项目级规则、边界、目录原则的传达稳定性
- 继续在其上做整段替换的风险很高

建议处理方式：

1. 不要整份重写
2. 先分节替换最核心入口段落
3. 每次只修一节，并与 `docs/README.md` 保持互补

## 3. 当前 P1 清单

### `publish/index.html`

当前问题：

- 文件中仍有大量历史乱码文本
- 但目前通过“逐行定位替换”仍可安全推进局部展示层收口

当前风险：

- 整段字符串替换不稳定
- 模板行内硬编码文案可能与真实显示不一致，增加理解成本
- 容易因为乱码导致替换命中失败

建议处理方式：

- 继续坚持逐行、小块替换
- 不要做整文件格式化或大范围重排
- 后续若要专门稳定化，应按模块分区逐段修复，而不是一次性清整页

### `docs/architecture/event-ui-helper-boundary-2026-07-10.md`

当前问题：

- 旧主体仍存在历史乱码
- 但文件尾部新增段落已可正常阅读

当前风险：

- 前半部分可读性差，影响完整边界传达
- 新旧内容并存，后续会话可能只读到前半段而误判模块现状

建议处理方式：

- 不要整份重写
- 未来若继续推进 `event`，可按章节逐段修正
- 保持“新补充先写在干净尾部”的策略，直到有单独稳定化窗口

### `docs/architecture/faction-ui-helper-boundary-2026-07-11.md`

当前问题：

- 与 `event` 类似，主体中仍有历史乱码残留
- 但近期增量记录可读性正常

当前风险：

- 会影响 `faction` 边界文档作为完整样板的阅读体验
- 但尚未阻断当前改造路线

建议处理方式：

- 按章节逐步替换
- 不与 `faction` 代码改造混在同一轮

### `docs/plans/_template.md`

当前问题：

- 模板主体已有明显编码污染
- 会影响后续新会话直接复用计划模板

当前风险：

- 降低计划文档的可复制性
- 容易让后续协作者绕开模板，回到随意落文档的状态

建议处理方式：

- 单独开一轮模板稳定化
- 与 `_validation-template.md`、`requirements/_template.md` 一起做一致性修正

## 5. 推荐处理顺序

当前建议的稳定化顺序：

1. `publish/faction-actions.js` 语法稳定化
2. `README.md` 核心入口段落稳定化
3. `docs/plans/_template.md` 模板稳定化
4. `publish/index.html` 分区稳定化策略文档化
5. `event` / `faction` 边界文档分节修复

## 6. 稳定化处理规则

任何“历史污染清理”都应遵守以下规则：

- 不与新功能开发混在同一轮
- 不把“清乱码”顺手扩展成“重构主链”
- 先恢复可验证性，再追求美观或完整统一
- 优先修复入口文档、模板文档、最常被编辑的大文件
- 对旧大文件一律采用最小替换，不做全文件重排
