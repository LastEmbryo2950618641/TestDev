# 目录规范演进草案

本文档用于说明当前项目在不一次性大搬迁的前提下，后续应如何逐步规范目录与代码落位。

## 1. 目标

在保持当前项目可持续迭代的前提下，逐步让目录结构具备：
- 更清晰的功能归属
- 更稳定的状态边界
- 更低的平台耦合
- 更高的桌面/移动端复用潜力

## 2. 当前现实

当前项目的运行主目录是 `publish/`，大量业务逻辑、页面模板、资源访问都以此为中心。

因此目录规范化必须遵守：
- 渐进式收敛
- 新结构优先用于新逻辑或正在重构的逻辑
- 不做一次性全量迁移

## 3. 推荐的长期目录分层

### A. 入口层
负责：
- 页面入口
- 脚本装配
- 启动初始化

当前对应：
- `publish/index.html`
- `publish/game.js`
- `publish/boot/`

### B. 功能域层
负责：
- 各系统的状态、动作、展示摘要、规则

建议逐步收敛到以下方向：
- `publish/control-*`
- `publish/control-experience-*`
- `publish/character-*`
- `publish/real-world-*`
- `publish/prompt-*`
- `publish/storage-*`
- `publish/body-figure-*`
- `publish/wechat-*`

### C. 平台层
负责：
- 平台能力适配
- 文件系统
- 宿主桥接
- key 管理
- dev-only 能力

建议后续预留方向：
- `publish/platform-*`
- 或后续独立到更明确的平台子目录

### D. 共享层
负责：
- 工具函数
- 通用常量
- schema
- helper
- 通用格式转换

### E. 文档层
负责：
- 需求
- 计划
- 架构
- 游戏规则

当前对应：
- `docs/`

## 4. 落位规则

### 新增逻辑落位
新增逻辑必须优先回答：
- 它属于哪个系统
- 它是状态判断、动作逻辑，还是平台能力
- 它是运行时规则，还是文档/配置资产

然后再决定放在哪里。

### 禁止事项
- 为了图快，把无边界逻辑继续塞进 `game.js`
- 页面里直接堆复杂业务判断
- 平台实现直接混进业务文件
- 同一系统的状态、动作、规则散落在多个不相邻文件且无说明

## 5. 阶段性策略

### 第一阶段
- 先收敛控制域
- 只抽状态判断与统一入口
- 不追求一次性拆完动作流

### 第二阶段
- 收敛平台边界
- 定义适配层方向
- 不急着迁移所有平台实现

### 第三阶段
- 将高频模块按功能域逐步收口
- 控制体验 / 提示词 / 存档 / 资源 / 现实世界依次推进

## 6. 文档与目录的关系

目录规范变化必须同步记录在：
- `docs/architecture/`
- 必要时配套 `docs/plans/`

这样后续 AI 才不会只看文件位置、不看规则背景。

## 7. 结论

目录规范化不是为了“看起来整洁”，而是为了：
- 控制耦合
- 提高复用
- 降低跨系统影响风险
- 为 `window exe / 安卓 apk` 复用打基础

因此目录调整必须服务于这些目标，而不是单纯做大搬迁。
