# 目录演进与落点规则

## 目标

这份文档不是抽象愿景，而是后续开发必须遵守的落点规则。

核心目标：

- 保持玩法逻辑不变
- 降低跨模块耦合
- 降低修改扩散风险
- 为 Windows `exe` 与 Android `apk` 复用预留稳定边界
- 让后续 AI / 人工新增代码优先进入规范目录，而不是继续散落在 `publish/` 根目录

## 总原则

1. 新增代码优先落到目标目录，不再默认写进 `publish/` 根目录。
2. 旧代码不做大爆炸搬迁，只在相关需求触达时逐步迁移。
3. 同一轮修改优先只做一种边界动作：
   - 要么抽规则
   - 要么抽平台能力
   - 要么抽 UI 适配
   - 不要一轮里同时大搬目录和改玩法
4. 旧入口如果已有外部依赖，优先保留兼容层，再把真实实现迁入新目录。
5. 目录落点比命名更重要：先放对层，再谈后续命名整理。

## 目标目录职责

### `publish/app/`

放应用装配层。

应该放这里的内容：

- 启动编排
- 模块注册与组装
- 跨系统接线逻辑
- 多模块组合动作
- 运行时流程驱动器

不应该放这里的内容：

- 具体玩法规则
- 平台读写实现
- 纯 UI 展示细节
- 通用工具函数堆积

允许依赖：

- `domain`
- `platform`
- `ui`
- `shared`

禁止反向要求：

- 不要让 `domain` 依赖 `app`
- 不要把所有业务逻辑塞回应用装配层

### `publish/domain/`

放领域逻辑与玩法规则。

应该放这里的内容：

- 规则判断
- 状态计算
- 补丁构建
- 领域状态入口
- 角色/控制/成长/世界线相关的纯业务逻辑

不应该放这里的内容：

- 直接访问 SQLite / 原生桥 / 文件系统
- 资源路径拼接
- 页面展示拼装
- 平台可用性判断实现

允许依赖：

- `shared`
- 少量稳定的 `platform` 抽象入口

禁止混写：

- 不要把 UI 文案拼装和领域规则写在同一个新文件
- 不要把底层平台访问直接写进领域 helper

### `publish/platform/`

放平台能力边界与平台实现。

应该放这里的内容：

- 存储源与后端适配
- 资源访问入口
- key / body-figure / world-lore 这类外部来源入口
- 未来 exe / apk 桥接能力
- 可用性判断与平台特性检测

不应该放这里的内容：

- 玩法状态推进
- UI 交互细节
- 页面组件逻辑

允许依赖：

- `shared`
- 必要时可依赖当前具体实现（例如现阶段 `sqliteSave`）

约束：

- 新平台能力优先先建 `platform/*` 入口，再让上层接入
- 如果旧路径已有调用方，优先采用“新路径是真实现，旧路径做兼容别名”

### `publish/ui/`

放展示适配与 UI 专用动作。

应该放这里的内容：

- 展示状态拼装
- UI 点击/切换/筛选动作
- 页面展示专用派生值
- 与 DOM 呈现强相关的轻逻辑

不应该放这里的内容：

- 平台存储实现
- 跨系统持久化编排
- 核心玩法规则

允许依赖：

- `app`
- `domain`
- `shared`
- 稳定的 `platform` 读取入口

约束：

- UI 层可以消费领域结果，但不要重新复制一套领域判断

### `publish/shared/`

放跨层通用能力。

应该放这里的内容：

- 小型工具函数
- 格式化逻辑
- 通用常量
- 与具体系统无关的帮助方法

不应该放这里的内容：

- 具体玩法规则
- 平台专用代码
- 页面专用状态

约束：

- `shared` 只放真正跨层复用的稳定能力
- 不要把它当成新的根目录杂物箱

## 模块落点决策表

新增或拆分模块时，按下面规则决定目录：

### 1. 如果模块主要回答“规则怎么判定”

目标目录：`publish/domain/`

例子：

- 控制规则
- 状态修正
- 补丁生成
- 角色成长判定

### 2. 如果模块主要回答“当前平台怎么读取/保存/访问”

目标目录：`publish/platform/`

例子：

- storage backend
- character state source
- real-world log source
- world lore source
- key source
- body figure source

### 3. 如果模块主要回答“页面上怎么展示/交互”

目标目录：`publish/ui/`

例子：

- 面板展开收起
- 列表筛选与选择状态
- 展示字段映射

### 4. 如果模块主要回答“多个系统怎么接起来执行”

目标目录：`publish/app/`

例子：

- 启动 warmup 编排
- 存档恢复后的系统重建流程
- 多模块组合入口

### 5. 如果模块与多个系统都有关，但本质只是公共小工具

目标目录：`publish/shared/`

前提：

- 不包含具体玩法知识
- 不依赖具体平台实现
- 不绑定具体页面

## 当前已经验证有效的落点模式

以下模式已经在当前重构中验证可行，应优先复用：

### 模式 A：真实实现迁入新目录，旧路径保留兼容壳

适用：

- 旧文件外部依赖较多
- 直接改 manifest 风险偏高

当前例子：

- 控制状态边界
- body figure 来源边界
- key 来源边界

### 模式 B：先抽 source / backend，再迁移调用方

适用：

- 底层实现分散在多个业务文件
- 目标是先收口依赖点

当前例子：

- character state source
- real-world log source
- storage backend
- world lore source

### 模式 C：保留旧编排层，只把纯逻辑或平台访问抽出去

适用：

- 原文件承担流程编排责任
- 一次性拆空风险高

当前例子：

- `control-link-actions.js` 保留为编排层
- `storage.js` 保留为存档编排层

## 新增代码的强制规则

后续任何新功能开发，默认遵守：

1. 新平台访问代码，不允许直接新增到 `publish/` 根目录。
2. 新规则计算代码，不允许直接和 SQLite / 原生桥混写。
3. 新 UI 展示逻辑，不允许顺手写进 platform source 文件。
4. 新编排代码，如果只是把多个模块串起来，优先进入 `app/` 或保留在现有编排层，不要塞进 `shared/`。
5. 若需求必须在旧文件落一小段兼容代码，真实实现仍应优先放入目标目录。

## 迁移顺序建议

后续目录规范化按以下优先级推进：

1. 继续让所有新平台能力进入 `publish/platform/`
2. 继续把纯规则/补丁/状态帮助方法迁入 `publish/domain/`
3. 对高耦合旧文件保留编排层身份，不急着清空
4. 当新目录承接足够稳定后，再考虑新增 `app/` 与 `ui/` 的真实落地模块
5. 最后再做更大范围目录清理，而不是一开始就全搬

## AI / 会话执行要求

后续任何 AI 会话在动代码前，必须先回答这三个问题：

1. 这次新增或修改的核心职责是什么？
2. 它应该落到 `app / domain / platform / ui / shared` 的哪一层？
3. 是否需要保留旧入口兼容壳？

如果这三个问题答不清，不应该直接开始写大块代码。

## 当前结论

目录规范化现在不再停留在“未来想法”阶段。

从这一版开始，`publish/app / domain / platform / ui / shared` 应被视为后续新增代码的正式目标目录骨架；旧文件仍可继续存在，但不应该继续成为新代码的默认落点。
