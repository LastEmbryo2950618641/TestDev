# Safe Refactor Execution Rules（2026-07-11）

本文档用于给后续 AI 会话提供一套可直接执行的低风险改造规则，目标是：

- 保证逻辑玩法不变
- 降低关联影响
- 提升代码复用性
- 逐步形成适合 `exe` / `apk` 复用的前端边界
- 避免在 Windows + 中文旧文件环境下反复踩编码坑

本文档不是替代 `README.md` 或架构文档，而是把“如何实际动手”写成可执行约束。

## 1. 默认工作模式

后续改造默认遵循以下模式：

1. 先读文档，再动代码
2. 先选安全切口，再选文件
3. 先抽只读 helper，再保留旧入口兼容
4. 先验证局部，再决定是否继续扩展
5. 一次只推进一小刀，不并发进入多个高风险链路

默认目标不是“一次重构干净”，而是“持续增加可复用边界，同时不破坏现有玩法”。

## 2. 允许优先改造的安全切口

优先改造以下内容：

- title / subtitle / description
- badge / tag / label / empty-state
- facts summary / chip rows / list item text
- 只读 tooltip / note / placeholder / fallback 文案
- 已有数据上的纯展示拼装
- 与 UI 相关但不写状态的 view helper
- 平台无关的纯计算 / 纯格式化 helper

这些切口通常适合进入：

- `publish/ui/...`
- `publish/domain/...`
- `publish/platform/...` 中的无副作用 adapter

## 3. 默认禁止直接进入的高风险链路

若没有单独计划文档和充分验证，默认不要进入：

- 初始化主链
- 状态同步链
- save / load / restore 链
- cache 写回链
- 异步编排链
- 曝光 / 可见性 / 推理 / 结算主链
- 运行时状态总线
- 大型旧文件中的中文密集业务主干

典型表现：

- 同时负责读状态、写状态、调别的模块、改 UI
- 文件里有大量全局状态访问和副作用
- 改一处可能影响存档、恢复、渲染、AI 提示词或事件推进

遇到这类文件，默认策略是：

- 不重写
- 不顺手清理
- 不趁机统一风格
- 只做最小兼容入口变更，或者完全不碰

## 4. 推荐的目录落位规则

### 展示层 helper

放在：

- `publish/ui/<module>/...`

适合承载：

- 只读展示文本
- tag / badge / summary / empty-state
- 列表 item 格式化
- template 可直接消费的结构化视图数据

### 规则 / 纯逻辑 helper

放在：

- `publish/domain/<module>/...`

适合承载：

- 平台无关的纯判断
- 规则计算
- 数据派生
- 不依赖 DOM、不写回状态的公共逻辑

### 平台来源 / 宿主差异 adapter

放在：

- `publish/platform/...`

适合承载：

- 文件来源
- 宿主环境差异
- 本地运行时桥接
- 未来桌面壳 / Android 壳差异对接

### 兼容壳 / 旧入口

继续保留在旧文件：

- `publish/*-actions.js`
- 老 root 文件
- 旧聚合入口

职责仅限：

- 转发到新 helper
- 保持当前调用面不崩
- 承接旧模板或旧模块调用

## 5. 推荐改造顺序

每次改造前先问：

1. 这段逻辑是不是只读展示？
2. 能不能抽成 helper 而不改调用链语义？
3. 能不能保留旧入口作为兼容壳？
4. 改完能不能只做局部验证？

若以上四项里有两项以上回答不清楚，则默认先补文档，不直接改代码。

推荐顺序：

1. 只读展示 helper
2. 纯格式化 / 纯派生 helper
3. 平台来源 adapter
4. 小型装配层
5. 最后才考虑主链瘦身

## 6. 编码损坏文件处理规则

当前仓库现实情况是：

- 存在历史中文乱码文件
- Windows PowerShell 容易破坏模板字符串与特殊字符
- 某些旧文件在工作树内已经不是“可安全自动重写”的状态

因此必须遵循以下规则。

### 可以 whole-file rewrite 的文件

仅限：

- 新增 helper 文件
- 自己刚创建、边界清楚、依赖面小的文件
- 已确认主要内容是结构化 JS，不依赖复杂旧乱码文本的文件

例如：

- `publish/ui/<module>/...-helpers.js`
- 新增文档文件

### 不可以 whole-file rewrite 的文件

默认包括：

- `publish/index.html`
- `publish/*-actions.js` 旧主文件
- `publish/game.js`
- `publish/save-actions.js`
- `publish/loading-actions.js`
- `publish/settings-actions.js`
- 任何存在大量旧中文业务文本和副作用链的文件

对这些文件只能：

- 小范围替换
- 局部插入兼容入口
- 精准修改模板片段

### 修改旧乱码文件时的验证原则

若旧文件本身已经语法损坏或编码损坏：

- 不得把该文件的全量 `node --check` 失败简单归因到本轮改动
- 应改为验证“新增 helper 可解析 + 新入口存在 + UI 引用存在”
- 必须在文档里明确说明旧文件的既有风险，不伪造完整通过

### PowerShell 编辑约束

在 Windows 环境下：

- 含有大量模板字符串时，优先用 here-string 一次写入新 helper 文件
- 避免对旧文件做大段正则替换
- 避免在带 `${...}`、反引号、中文符号混杂的内容上反复 replace
- 一旦发现字符串字面量被破坏，立即停手，先恢复最小可控状态

## 7. 最小验证标准

每一刀改造后，至少满足以下一组验证：

### A 类：新增 helper 文件

至少验证：

- 文件可被读取
- `node --check` 通过
- 方法名可检索

### B 类：旧入口兼容转发

至少验证：

- 旧入口方法存在
- 入口转发到新 helper
- 没有改动主链流程语义

### C 类：模板消费替换

至少验证：

- 新 helper 被模板实际引用
- 旧的内联拼装已收口
- 空态或 fallback 仍存在

### D 类：高风险旧文件

若该文件原本已有损坏：

- 明确记录“无法作为本轮全量语法验收依据”
- 只声明已验证的局部证据
- 不夸大为“整体完成”

## 8. 文档联动要求

每次有效改造，至少要在以下两类文档里更新其一：

- `docs/architecture/...`：边界、职责、停手位置
- `docs/plans/...`：本轮计划、验证、剩余 backlog

若改造形成了可复用模式，则应补一条：

- 哪个模块成为新样板
- 哪个切口已被验证安全
- 后续可复制到哪些模块

## 9. 面向多端复用的判断标准

一段逻辑若满足以下条件，优先抽离：

- 不依赖浏览器 DOM
- 不直接操作窗口或宿主 API
- 不依赖当前页面模板上下文
- 可被桌面壳 / Android 壳 / 浏览器共用

满足以上条件的逻辑，应优先进入：

- `domain`
- `ui` helper
- `platform` adapter

而不是继续散落在：

- `index.html` 模板拼接里
- 大型 action 文件里
- 单一宿主入口里

## 10. 当前默认推进策略

基于当前仓库状态，默认采用：

- 文档先行
- 模块逐个推进
- 只读展示优先
- 兼容壳长期保留
- 高风险旧文件只做最小接触

不采用：

- 一次性目录大迁移
- 大型旧文件全量重写
- 边改功能边顺手清理所有历史问题
- 在未验证前提下强行引入统一构建体系替代当前运行链

## 11. 后续 AI 会话的必答问题

准备动代码前，后续 AI 至少先回答：

1. 这次改的是展示、规则、平台还是装配？
2. 为什么不需要碰初始化 / 同步 / save / load 主链？
3. 新逻辑会落在哪个目录，为什么？
4. 旧入口是否保留兼容壳？
5. 本轮最小可验证证据是什么？

如果回答不清楚，默认先写计划或边界文档，不直接下刀。
