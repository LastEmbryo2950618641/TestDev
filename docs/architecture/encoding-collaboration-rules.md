# 编码与安全编辑协作规则

## 目的

本项目已经出现过多次历史编码污染、PowerShell 文本替换误伤、CRLF/LF 混杂、宿主镜像与主运行目录不同步等问题。
这份文档用于约束后续 AI 与人工协作者在编辑代码时采用更稳妥的做法，降低“为了重构而引入额外故障”的风险。

## 当前已确认的风险

### 1. 历史文件存在编码脏字

部分旧文件中已经存在乱码或疑似错误转码文本，例如：

- `publish/ui/company/company-pay-view-helpers.js`
- `publish/ui/company/company-attendance-view-helpers.js`

这类文件不能因为“看起来有乱码”就直接整文件重写；否则很容易把本来还能工作的旧内容进一步破坏。

### 2. PowerShell here-string / 引号 / 反引号易导致脚本误执行

在当前 Windows 开发环境下，以下情况都已经真实发生过：

- `&&` 在 PowerShell 中不是稳定可用的命令连接方式
- here-string 终止符不匹配会导致整段脚本失效
- Markdown 列表、反引号、模板字符串混入 shell 命令时容易触发解析错误
- 文本替换脚本写得稍大，就可能把目标文件改坏或没有命中却不易察觉

### 3. CRLF / LF 会造成 diff 噪音

当前仓库中存在 CRLF 与 LF 混用现象。
即使逻辑没有变化，只要改写方式不稳，也可能让 diff 充满无意义噪音，增加审查和回滚成本。

### 4. 宿主镜像目录不是主权威源码

以下目录包含宿主侧镜像或产物，不应随意混同为主权威编辑目标：

- `mobile/android-webview-shell/app/src/main/assets/publish/`
- `publish/platform/.artifacts/`

默认应优先判断真正权威来源是否仍是 `publish/`、`shared/`、`desktop/`、`mobile/` 各自的主开发目录，再决定是否需要同步镜像。

## 默认编辑策略

### 1. 优先小步、低风险、可验证修改

- 每次只改一个小切口
- 优先改纯只读 helper / pure query / pure format / pure state assembly
- 旧入口优先保留 compat facade，不要先硬删
- 改完立刻做最小语法验证

### 2. 优先局部替换，不优先整文件重写

若目标文件包含历史编码风险、长模板字符串或旧逻辑混杂：

- 优先做最小块替换
- 优先拆出新 helper 文件承接新职责
- 不要为了省事直接整文件覆盖

只有在满足以下条件时，才适合整文件重写：

- 文件较小
- 文件职责单一
- 当前内容编码稳定
- 已确认不会误伤历史逻辑

### 3. 修改后立即验证

推荐最小验证顺序：

1. `node --check <file>`
2. `git diff -- <file>`
3. 必要时再看调用方是否仍走旧兼容入口

如果只是 shell 命令层面发生失败，不代表业务代码有问题；先区分“脚本炸了”还是“文件炸了”。

### 4. 不做目录级暂存

仓库当前长期处于脏工作树状态。
因此：

- 不要使用目录级 `git add`
- 不要把未确认的文档、镜像资源、构建产物一起提交
- 只精确暂存当前这轮真正改过且验证过的文件

## 推荐编辑方式

### 推荐顺序

1. 先读目标文件与相邻 README / boundary 文档
2. 判断该逻辑是展示层、状态层、平台层还是宿主镜像层
3. 能拆新 helper 就拆新 helper
4. 旧入口只做转发兼容
5. 立刻运行最小校验
6. 形成小提交，再继续下一刀

### 推荐工具习惯

- 搜索文件优先用 `rg` / `rg --files`
- 多文件阅读时优先先看只读 helper、README、boundary 文档
- PowerShell 下优先使用更朴素、可控的小命令，而不是超长 here-string 拼接脚本
- 当 `apply_patch` 不稳定时，可退回到安全文本替换，但必须立刻复核 diff

## 不推荐的做法

- 因为看见乱码就整文件“顺手修编码”
- 在一次改动里同时处理重构、编码清洗、宿主镜像同步
- 未验证就把 `publish/` 和 `mobile/.../assets/publish/` 一起改掉
- 为了追求快，把大段旧逻辑直接搬动到多个文件
- 在高风险文件里做大批量正则替换后不检查 diff

## 与多端复用目标的关系

编码与编辑稳定性不是附属问题，而是多端复用前提的一部分。
如果基础文件经常因为编码或编辑脚本被误伤，那么：

- Web 主链会先失稳
- Windows `exe` 宿主复用会缺少稳定源目录
- Android `apk` 镜像同步会更容易出现“源文件和壳内文件不一致”

因此，后续多端推进应坚持：

- 先稳定主源码边界
- 再稳定同步机制
- 最后再扩大宿主层自动化

## 当前执行建议

在接下来的渐进式重构中，默认优先选择以下工作：

- 展示层 helper 下沉
- 状态组装 helper 下沉
- query / format / view object 收口
- README / boundary 文档同步

以下工作默认后置，除非已经专门开计划：

- 编码清洗
- 宿主镜像大规模回填
- 旧代码删除
- 大型批量替换
