# 模块迁移模式总规则（2026-07-11）

本文档用于总结当前仓库已经验证可行的结构迁移模式，帮助后续会话在继续规范化时，不再靠感觉决定“该拆到哪一层”或“该不该继续深拆”。

## 1. 文档目标

这份文档不替代状态地图，也不替代单模块边界文档。

它主要回答三个问题：

- 当前有哪些已经验证成功的迁移模式。
- 什么类型的模块适合哪一种模式。
- 什么时候应该继续推进，什么时候应该明确停手。

## 2. 已验证的迁移模式

### 模式 A：完整三层样板

适用特征：

- 同时存在清晰的展示层、规则层、流程编排层。
- 写回主链与外围辅助逻辑之间能切出明确边界。
- 模块具有较高复用价值，适合作为后续样板。

当前代表：

- `taobao`

推荐结构：

- `publish/ui/<module>/`
- `publish/domain/<module>/`
- `publish/app/<module>/`
- 旧根入口保留兼容壳

判断原则：

- 如果一个模块既有稳定展示 helper，又有可独立复用的规则 helper，同时还存在明显的 orchestration 流程，那么优先考虑完整三层样板。

停手规则：

- 一旦高风险副作用链已经被隔离到兼容壳外围，不要为了“层数完整感”继续深拆写回链。

## 3. 模式 B：UI + 轻量 Domain 样板

适用特征：

- 展示层已经很适合收敛。
- 存在一批纯规则、轻判断、轻格式化逻辑可独立复用。
- 但还没有足够稳定的流程编排切口，不应强行建 `app`。

当前代表：

- `wechat`
- `control`

推荐结构：

- `publish/ui/<module>/`
- `publish/domain/<module>/`
- 旧根入口保留兼容壳或编排壳

判断原则：

- 如果主要收益来自统一按钮文案、状态标签、轻规则、轻格式化、入口流转，而深层流程仍然高风险，那么优先停在 `ui + 轻量 domain`。

停手规则：

- 不要为了结构对称性强行继续补 `app/<module>`。
- 只有当调用顺序本身能稳定独立，并且不直接拖动高副作用链时，才考虑继续往 `app` 扩。

## 4. 模式 C：已有 System 事实承担 Domain 角色

适用特征：

- 模块中已经存在一个较强的 `system` 对象或规则中心。
- 规则、标准化、评分、时间判断等核心逻辑已经集中在这个对象中。
- 再复制一层 `domain/<module>` 很容易造成重复权威。

当前代表：

- `event`

推荐结构：

- `publish/ui/<module>/`
- `publish/<module>-system.js` 或等价规则中心
- `publish/<module>-actions.js` 作为兼容壳 / 编排入口

判断原则：

- 如果现有 `system` 已经承担领域规则职责，应优先承认它的地位，而不是机械补目录。

停手规则：

- 不要为了目录一致性再建一层重复 `system` 职责的 `domain/<module>`。

## 5. 模式 D：UI + 极小 Domain + 兼容壳

适用特征：

- 已有稳定 UI helper。
- 存在一小簇纯构造、纯格式化、纯派生 helper 可抽离。
- 但数据组合、写回、持久化或外部协作链仍然紧耦合。

当前代表：

- `worldline`

推荐结构：

- `publish/ui/<module>/`
- `publish/domain/<module>/` 仅承载极小纯 helper
- `publish/<module>-actions.js` 保留兼容壳与写回编排

判断原则：

- 如果一个模块能安全抽离的只有“极小且纯”的 helper 簇，那么只落一个极小 `domain` 即可，不要贪多。

停手规则：

- 先停在 `ui + 极小 domain + 兼容壳`。
- 后续只有在读写链出现更明确边界时，才考虑继续下沉或引入 `app`。

## 6. 模式 E：稳定优先，不以拆分为目标

适用特征：

- 当前结构已经足够清晰。
- 继续拆分的主要风险来自启动时序、黑屏、存档恢复、加载顺序等问题。
- 收益已经低于稳定性风险。

当前代表：

- `loading`

判断原则：

- 如果一个模块继续拆分最大的影响是系统级不稳定，而不是代码长期不可维护，那么当前阶段优先保持稳定。

停手规则：

- 后续只有在具体问题驱动下再处理，比如黑屏、进度条错误、预热顺序异常等。

## 7. 模式 F：明确停手边界

适用特征：

- 模块已经有部分样板基础。
- 但旧入口后段高耦合，继续深拆需要一起带动玩法、存档或多块状态写回。
- 当前看不到低风险切口。

当前代表：

- `save`

判断原则：

- 如果继续推进的唯一方式是直接进入高耦合后段，那么当前阶段更应该留下边界文档，而不是继续硬拆。

停手规则：

- 暂不继续代码改造，先把边界、风险和后续条件说明白。

## 8. 模式 G：已有 UI 样板继续扩展

适用特征：

- 模块已经有可用的 UI/helper 基础。
- 近期需求主要是补更多展示 helper，而不是改主链。

当前代表：

- `settings`

判断原则：

- 如果现阶段目标只是继续把已验证的 UI helper 扩下去，那么应优先小步扩展，而不是同时开新层。

## 9. 迁移时的统一动作顺序

无论选择哪种模式，当前仓库都应优先遵循以下动作顺序：

1. 先判断当前模块属于哪一种模式。
2. 只抽最稳的一簇 helper 或一小块流程。
3. 新目录承载真实实现。
4. 旧根入口保留兼容壳。
5. 不混合玩法改动与结构改动。
6. 迁移后补边界文档或状态地图记录。

## 10. 什么时候必须停手

出现以下任一情况时，应默认停手并先补文档：

- 继续拆分会直接进入写回链、持久化链或启动链。
- 文件历史上已经有结构损坏或编码污染风险。
- 继续推进的唯一理由只是“目录看起来更整齐”。
- 当前没有明确的低风险切口，只能依靠大面积替换或重写。

## 11. 多端复用导向规则

为了未来支持 `window exe` 与 `android apk`，迁移时默认优先抽离：

- 纯状态访问
- 纯规则判断
- 纯格式化 / 构造 helper
- 与宿主无关的轻量流程编排

默认暂缓：

- 本地存储细节
- 宿主桥接细节
- 直接写回链
- 启动加载时序

原因：

- 这些纯 helper 最适合未来多端共用。
- 高副作用链更适合在平台边界稳定后再逐步抽离。

## 12. 对后续会话的硬约束

后续会话在继续规范化前，至少应先看：

- `docs/architecture/module-status-map-2026-07-10.md`
- `docs/architecture/business-module-migration-template-phase1.md`
- `docs/architecture/publish-directory-expansion-rules-phase1-5.md`
- 本文档

如果准备继续某个模块，先回答两个问题：

1. 当前模块属于哪一种已验证模式。
2. 这一步为什么不会把工作推进到高副作用链里。

回答不清楚时，默认先停手补文档，不直接开改。
