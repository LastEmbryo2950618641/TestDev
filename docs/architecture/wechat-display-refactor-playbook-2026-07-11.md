# WeChat Display Refactor Playbook（2026-07-11）

本文档不是微信模块的边界流水账，而是从本轮连续实践中沉淀出来的“展示层收口操作手册”。

目标：

- 让后续 AI 会话知道微信模块应该怎么继续拆
- 让相同方法可以复制到其它高耦合页面模块
- 明确什么能先动，什么绝对不要在展示层收口阶段碰

## 1. 这份 playbook 解决什么问题

微信模块的问题不是“完全没有结构”，而是：

- 模板内联展示逻辑过多
- 同一个页面里同时混着文案、状态判断、按钮行为、写回动作
- 一旦直接大拆，很容易误伤消息链、记忆链、同步链

因此它更适合采用一种渐进方式：

- 先只收展示层
- 先让模板从“直接读原始状态 + 写死文案”变成“消费展示对象”
- 再决定哪些纯规则适合进入 `domain/wechat`
- 最后才评估是否需要 `app/wechat` 或更深层流程装配

## 2. 已验证有效的微信模块收口模式

本轮已经在 `wechat` 中连续验证了以下模式：

1. 真正实现进入 `publish/ui/wechat/view-helpers.js`
2. 旧入口继续保留在 `publish/wechat-view-actions.js`
3. 旧入口只做兼容转发，不重写主链语义
4. `publish/index.html` 逐步从内联表达式改为消费 helper 对象或 row
5. 每一刀只收一个相邻展示切面，不跨进消息、记忆、同步、写回动作

一句话总结：

- 微信模块最稳的改法，不是“一次性模块重构”，而是“相邻展示岛逐块收口”。

## 3. 推荐的切口顺序

微信模块后续继续拆时，优先顺序已经被验证过：

1. `title / subtitle / empty-state`
2. `row` 列表对象化
3. `card` 卡片展示对象化
4. `entry rows` 入口行对象化
5. `dialog view object` 弹窗展示对象化
6. 最后才考虑跨读链纯规则是否需要进入 `domain/wechat`

不建议的顺序：

- 先动消息发送链
- 先动记忆写回链
- 先动同步/恢复链
- 先把页面全部改成组件再补边界

## 4. 在微信模块里，哪些切口已经证明安全

以下切口已经证明适合先做：

- 联系人列表展示
- 聊天线程列表展示
- 联系人资料页标题
- 联系人资料卡
- 我的页卡片
- 卡片入口行
- 相册工具栏展示
- 相册空态展示
- 相册照片列表展示
- 相册删除确认弹窗展示
- 相册照片卡片按钮文案展示
- 头像裁剪弹窗展示

这些切口的共同点：

- 只读
- 主要服务模板展示
- 不改变数据来源
- 不承担副作用
- 不直接写状态主链

## 5. 微信模块当前不该先碰的区域

在没有单独计划和更强验证前，以下区域不要与展示层收口混在一轮里：

- 消息发送流程
- 消息接收与线程推进
- 记忆系统写回
- 图片生成主链
- 相册生成 prompt 编辑主链
- 存档恢复、同步、初始化入口
- 任何跨页面的隐式状态重算

原因：

- 这些区域的回归成本高
- 很难通过只看模板引用来完成验证
- 一旦和展示层收口绑在一起，风险面会急剧放大

## 6. 推荐的数据形状

### A. 单对象展示

适合标题、资料卡、弹窗文案：

- `xxxView()`
- `xxxCard()`
- `xxxState()`

典型字段：

- `title`
- `subtitle`
- `description`
- `confirmLabel`
- `cancelLabel`
- `disabled`

### B. 行对象列表

适合联系人、线程、入口行、照片卡片：

- `xxxRows()`

典型字段：

- `key`
- `id`
- `label`
- `value`
- `name`
- `avatarText`
- `avatarStyle`

### C. 空态对象

适合列表页和生成中状态：

- `xxxEmptyState()`

典型字段：

- `show`
- `loading`
- `text`

## 7. 旧入口文件应该怎么处理

`publish/wechat-view-actions.js` 的职责应继续保持为：

- 向模板暴露旧调用入口
- 转发到 `ui/wechat/view-helpers.js`
- 不在这一层新增流程拼装
- 不顺手改动作逻辑

推荐写法：

```js
wechatProfileCard() {
  return window.GameModules.wechatViewHelpers.wechatProfileCard.call(this);
}
```

不推荐写法：

- 在旧入口里边转发边拼文案
- 在旧入口里加状态写入
- 在旧入口里顺手改点击行为或异步流程

## 8. 模板替换时的安全规则

每次只替换一个小区域，优先使用以下顺序：

1. 先加 helper
2. 再加兼容壳
3. 再改模板消费
4. 再补文档
5. 最后做最小验证

模板改动时必须满足：

- 原交互行为保持不变
- `x-show` / `x-text` / `x-for` 的语义不被扩大
- 空态、fallback、loading 仍然存在
- 不因为“顺手优化”把多个不同风险层级的逻辑混到一起

## 9. 本轮实践暴露出的真实工程注意点

### 9.1 PowerShell 对模板字符串不稳定

本轮已经多次验证：

- 直接用 PowerShell 写带 `${}` 的模板字符串很容易损坏内容
- 中文文案也容易在替换时出现乱码或截断

因此推荐：

- 在 helper 中优先使用普通字符串拼接
- 避免在 PowerShell 替换里直接写复杂模板字符串
- 改动后立刻执行 `node --check`

### 9.2 大文件模板要小范围改

`publish/index.html` 体积较大，且已有旧编码痕迹，因此推荐：

- 只按明确行段局部替换
- 不做大范围全局替换
- 每次改完都立即回看邻近结构，尤其是闭合标签

### 9.3 文档必须同步沉淀

每完成一批切口，至少要更新一份 architecture 文档，记录：

- 新 helper 名称
- 模板消费落点
- 保持没动的高风险链路
- 这一步为什么安全

## 10. 面向多端复用时，微信模块应该优先抽什么

如果目标是后续复用到：

- Windows EXE 壳
- Android APK 壳
- 浏览器部署版本

则微信模块应优先抽离：

- 纯展示 helper
- 与宿主环境无关的只读规则
- 不依赖 DOM 的展示对象生成逻辑

暂时不要优先抽离：

- 直接依赖浏览器交互上下文的动作逻辑
- 强依赖当前页面状态机的写回过程
- 带副作用的流程装配

## 11. 后续会话继续推进微信模块时的建议顺序

推荐继续顺序：

1. 继续找小型展示岛
2. 先把页面切面收干净
3. 再回头评估 `domain/wechat` 是否有新的只读规则值得下沉
4. 只有在展示层和轻规则边界都稳定后，再考虑更深的流程层拆分

若后续改到别的模块，也可以反过来使用这份 playbook：

- 如果一个模块和微信一样“模板很重、行为很多、流程很危险”，就优先复制微信这套渐进收口方法。
