# Compat Entry Template Migration Prep (2026-07-12)

## 目的

在真正删除 `publish/game.js` 上的 compat 入口之前，先把模板迁移准备工作拆清楚。

这份文档回答的问题不是“现在能不能删”，而是：

- 如果将来要删，模板和镜像需要先做哪些迁移准备
- 哪些入口只是桥接还不够，必须先有新的稳定公开面
- 多端同步时哪些环节最容易漏

## 当前前提

根据以下文档，当前这批入口虽然已经桥接，但仍不是删除候选：

- `docs/architecture/compat-entry-bridge-inventory-2026-07-12.md`
- `docs/architecture/compat-entry-template-consumer-audit-2026-07-12.md`

结论基线：

1. Web 主模板仍直接消费 `$store.game` 上的同名入口
2. Android 镜像模板仍同步消费同名入口
3. 因此，删除前必须先处理模板公开面迁移

## 迁移准备的三种模式

### 模式 A：继续保留 `$store.game`，但把实现彻底下沉

适用场景：
- 模板层短期不想大改
- 多端镜像同步成本较高
- 入口名本身已经足够稳定，不需要换名

要求：
1. `publish/game.js` 仅保留极薄 compat facade
2. 真实逻辑全部移入模块侧
3. fallback 是否保留要有明确结论

说明：
- 这种模式下，旧入口不会被立刻删除
- 但可以先把它降级为稳定公开 contract 层

### 模式 B：模板迁移到新的模块公开面

适用场景：
- 当前 `$store.game` 上的入口名带有明显历史残留味道
- 希望缩小 `game.js` 公开面
- 模块已经具备更清晰的公开结构

要求：
1. 先定义新的稳定公开面
2. Web 模板先迁移
3. Android 镜像模板同步迁移
4. 确认没有残余调用后，旧 compat 入口才进入删除候选

说明：
- 这是删除 compat 入口更彻底的路线
- 但迁移成本明显更高

### 模式 C：混合迁移

适用场景：
- 同一模块中，一部分入口适合长期保留为 facade
- 另一部分入口适合迁出 `$store.game`

要求：
1. 先分清“稳定公开 contract”与“历史过渡入口”
2. 不要整组一刀切迁移
3. 先迁最薄、最纯展示、最少副作用的一批

## 当前模块的迁移准备建议

### 1. taobao

当前状态：
- 模板直接消费面较广
- Web / Android 模板均大量依赖
- 已桥接到 `taobaoActions` / `domain` / `viewHelpers`

建议：
- 短期优先使用模式 A
- 保持 `$store.game.taobao...` 作为稳定模板 contract
- 后续若要进一步删除 compat，先定义新的模块公开面并做成批迁移

### 2. calendar

当前状态：
- 入口少
- 纯视图/派生能力为主
- 迁移成本相对低

建议：
- 可优先评估模式 B 或模式 C
- 因为入口数量少，后续做模板迁移的难度最低

### 3. skills

当前状态：
- 只读查询入口
- 模板结构相对集中

建议：
- 很适合成为第一批“模板迁移准备样板”
- 可考虑先在文档层定义模块公开面，然后再决定是否迁模板

### 4. prompt

当前状态：
- 只读展示面为主
- 模板消费集中

建议：
- 与 skills 类似，适合做第一批迁移准备样板
- 若未来做 B 模式迁移，应和 skills 一样先从集中模板区块开始

### 5. boss

当前状态：
- 展示/派生面已开始桥接
- 动作链仍复杂
- 模板消费面较广

建议：
- 当前优先继续使用模式 A
- 暂不适合率先做彻底模板迁移
- 应在生成、预约、申请链彻底解耦前，继续保留 `$store.game.boss...` 的稳定公开面

## 删除前最少门槛

无论采用哪种模式，真正删除 compat 入口前，至少要满足：

1. Web 模板调用点已完成迁移或确认长期保留 facade
2. Android 镜像模板同步完成相同决策
3. `publish/game.js` 对应入口不再承担必要 fallback 兜底职责
4. 模块内部调用链复核完成
5. 至少有一份删除 gate 审计记录“为什么现在可以删”

## 推荐的下一步工作顺序

1. 先挑 `skills` / `prompt` / `calendar` 三类低副作用入口做迁移准备样板
2. 明确“长期保留 facade”与“后续计划删掉”的入口分层
3. 再考虑是否让 `boss`、`taobao` 进入同类迁移准备
4. 最后才进入真正的 compat 删除批次

## 当前阶段结论

当前最正确的方向不是马上删 `game.js` 上的 compat 入口，而是：

1. 持续让它们变薄
2. 明确哪些入口未来只保留 contract，哪些入口未来要迁模板
3. 先把模板迁移准备文档化
4. 等多端消费面和 fallback 责任都清楚后，再进入删除阶段
