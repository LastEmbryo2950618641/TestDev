# 发布端目录扩展规则（阶段 1.5）

本文档基于当前已经落地的 `publish/app/`、`publish/domain/`、`publish/platform/`、`publish/ui/` 实现样板，补充后续目录扩展时必须遵守的落位规则。

它的目标不是重新设计目录，而是把“已经验证可行的兼容迁移方式”固定下来，减少后续会话继续把代码写回 `publish/` 根目录。

## 1. 当前结论

当前项目已经不再只是“准备规范化”。

以下目录已经存在真实实现：

- `publish/app/`
- `publish/domain/`
- `publish/platform/`
- `publish/ui/`

因此后续新功能或旧逻辑拆分时，默认原则改为：

- 先判断能否落到已有规范目录。
- 只有在确实无法归类时，才允许暂时保留在 `publish/` 根目录。
- 不能因为历史上文件都在根目录，就继续沿用旧习惯。

## 2. 四层默认职责

### `publish/app/`

适合放：

- 启动编排
- 流程装配
- 模块接线
- 顺序控制
- 对多个模块的组合调度

不适合放：

- 纯 UI 文案拼装
- 平台读写细节
- 纯规则判断

判断标准：

如果一个模块主要在做“先调用 A，再调用 B，再根据结果决定是否调用 C”，它更像 `app` 层。

### `publish/domain/`

适合放：

- 状态规则
- 业务判断
- 补丁构建
- 领域 helper
- 玩法约束

不适合放：

- DOM 操作
- 文件系统访问
- dev server 专属路径判断

判断标准：

如果一个模块即使换成 `exe` 或 `apk` 仍然应该原样复用，它优先属于 `domain` 层。

### `publish/platform/`

适合放：

- 存储后端接入
- key 来源
- 本地文件访问
- 资源来源适配
- 宿主差异能力
- 未来原生桥接入口

不适合放：

- 角色玩法规则
- UI 展示拼装
- 与特定页面强耦合的 DOM 行为

判断标准：

如果逻辑的核心问题是“这个环境下怎么读、怎么写、怎么接宿主”，它优先属于 `platform` 层。

### `publish/ui/`

适合放：

- 展示 helper
- 视图格式化
- 面板派生数据
- 只读显示逻辑
- 与交互显示直接相关的轻量桥接

不适合放：

- 深层存储写入
- 平台路径解析
- 大量玩法状态改写

判断标准：

如果逻辑的主要产物是“给界面显示什么、怎么显示、按钮怎么命名、面板怎么组合”，它优先属于 `ui` 层。

## 3. 根目录文件新增限制

从现在开始，新增 `publish/*.js` 根级运行时文件应视为例外，不应再是默认做法。

允许新增根级文件的场景：

- 历史兼容入口必须保留
- `script-manifest` 当前阶段只能稳定引用旧入口
- 新目录实现已经存在，但需要旧文件做薄转发壳

不允许新增根级文件的场景：

- 仅仅因为复制旧模式更快
- 没有先判断能否放进 `app/domain/platform/ui`
- 把新系统直接塞进 `game.js` 或其他根级大文件附近图省事

## 4. 已验证的迁移模式

当前仓库已经验证过以下模式可行：

1. 在目标目录创建真实实现
2. 保留旧入口文件
3. 把旧入口改成薄转发层
4. 保持 `script-manifest` 与运行时行为稳定

### 4.1 已验证的“三段式兼容迁移”

当模块已经开始形成主题目录后，后续优先采用：

1. 真实实现文件
2. 兼容聚合入口
3. 动作入口 / 根入口保留

建议职责切分如下：

- 真实实现文件：放主题 helper、规则 helper、纯格式化、纯构造、只读派生逻辑
- 兼容聚合入口：只保留旧命名与旧访问路径，对外转发到真实实现文件
- 动作入口 / 根入口：保留流程编排、运行时缓存、交互状态写入、副作用调用

最近已验证的可行形态：

- `real-world`：`map-interior-view-helpers.js` 等真实实现 + `map-view-helpers.js` 聚合入口 + `real-world-map-actions.js` 动作入口
- `faction`：`overview-view-helpers.js` 真实实现 + `faction-actions.js` 兼容动作入口
- `control`：`domain/control/*` 真实规则 helper + `control-*-actions.js` 旧入口转发

强约束：

- 不要把新的展示 helper 继续加回聚合入口。
- 不要让聚合入口再次承担业务判断或状态写回。
- 不要因为“顺手”就在动作入口里复制一份已经迁出的 helper。
- 如果新需求只是展示层增强，优先改真实 helper 文件，不优先改动作入口。

后续应优先复用这套模式，而不是：

- 直接大规模移动文件
- 一次性改清单 + 改引用 + 改玩法
- 为了目录整洁删掉旧兼容入口

## 5. 目录扩展的推荐顺序

后续新增或拆分时，建议按以下顺序判断：

1. 这段逻辑是不是纯显示 helper。
2. 如果不是，它是不是纯规则/状态判断。
3. 如果不是，它是不是平台来源/宿主适配。
4. 如果都不是，再看它是否属于流程装配。
5. 只有都无法明确归类，才暂时留在旧位置，并在计划文档说明原因。

## 6. 多端复用导向规则

为了未来支持 `window exe` 与 `android apk`，目录扩展时默认遵循：

- `domain` 尽量不感知宿主环境。
- `ui` 尽量复用 `domain` 输出，而不是重新复制一套状态判断。
- `platform` 集中承接文件、本地资源、桥接、后端差异。
- `app` 负责把这些层装配起来，不把平台细节再次扩散出去。

这样做的直接收益：

- Windows 桌面端只需要替换平台实现，不必回改玩法规则。
- Android 壳接入时，可先接平台桥，不必重写整套业务层。
- 浏览器开发版仍可继续跑当前链路，降低迁移风险。

## 7. 文档与计划联动要求

后续中大型改造，如果涉及新增目录落位或模块迁移，至少应在 `docs/plans/` 里说明：

- 旧入口文件是什么
- 新真实实现文件是什么
- 哪一层负责什么职责
- 是否保留兼容转发
- 是否影响 `script-manifest`
- 是否涉及编码高风险文件

如果只是小型 helper 抽取，也应至少在提交说明或阶段文档中写明新旧边界。

## 8. 当前建议的默认策略

基于当前仓库现状，后续最稳的策略不是“大迁移”，而是：

- 继续在已有四层目录中扩样板
- 继续使用兼容转发壳
- 优先抽离只读 helper、来源 adapter、规则 helper、装配流
- 暂缓高风险中文密集大文件的深改
