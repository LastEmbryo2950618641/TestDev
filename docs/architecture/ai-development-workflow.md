# AI 开发工作流

本文档定义后续 AI 在本项目中处理需求、编写文档、实施改动、提交结果时的推荐流程。

## 1. 目标

确保后续开发满足以下要求：
- 先理解边界，再修改代码
- 中大型需求先有文档落点
- 状态来源清晰
- 平台能力不直接混入业务
- 减少“哪里都能改一点”的无序增长

## 2. 接到需求后的第一步

收到新需求后，优先做以下判断：
1. 这是小改还是中大型改动
2. 属于哪个功能域
3. 是否影响状态、存档、资源、提示词或平台能力
4. 是否需要先写需求文档或计划文档

如果这些问题还没回答清楚，不应直接进入跨文件修改。

## 3. 需求分类

### A. 小改动
适用：
- 单点 UI 文案调整
- 已有状态的简单展示修正
- 已有函数内的小范围修复
- 不影响存档、资源和平台边界的局部改动

处理方式：
- 可直接实现
- 但仍应先确认目标模块与状态来源

### B. 中大型改动
适用：
- 跨多个系统
- 影响存档结构
- 影响提示词规则
- 影响运行时生成资源
- 需要新增平台能力
- 需要新增一整块功能域逻辑
- UI、状态、规则三者一起变动

处理方式：
- 先写文档，再实现

## 4. 文档编写规则

### 需求文档
放在：`docs/requirements/`

建议内容：
- 背景
- 用户目标
- 预期行为
- 不做什么
- 影响范围
- 验收标准

建议命名：
- `YYYY-MM-DD-功能名-requirement.md`

### 实现计划
放在：`docs/plans/`

建议内容：
- 涉及模块
- 权威状态来源
- UI 入口
- 数据结构变化
- 存档兼容影响
- 风险点
- 验收步骤

建议命名：
- `YYYY-MM-DD-功能名-plan.md`

## 5. 实施前检查清单

进入编码前，至少确认：
- 该功能属于哪个系统
- 当前系统已有入口文件在哪里
- 权威状态字段是什么
- 是否需要持久化
- 是否需要新增资源文件
- 是否会影响 `publish/` 主运行链路
- 是否涉及平台能力

若涉及平台能力，应优先考虑适配层，而不是直接把实现写进业务脚本。

## 6. 编码约束

### 必须遵守
- 优先复用已有模块职责
- 新逻辑尽量向明确功能域收敛
- 避免复制已有状态判断
- 页面展示优先读取统一状态，而不是自行猜测
- 新增资源文件前先确认归属与用途

### 禁止事项
- 未确认状态来源就直接写展示逻辑
- 在 `game.js` 中继续无边界堆积新系统
- 通过临时变量绕开既有状态链路
- 把平台实现散落到业务模块
- 把运行日志、截图、调试导出混入正式资源目录

## 7. 提交前检查清单

提交前应检查：
- 是否混入日志文件
- 是否混入临时调试文件
- 是否混入无关运行时生成资源
- 如果有资源变更，是否已明确这些资源要不要入库
- 文档是否已落到正确目录
- 是否说明了状态来源和影响范围

## 8. 完成后的说明格式

后续 AI 在完成一项改动后，建议至少说明：
- 改了哪些文件
- 新逻辑的权威状态来源是什么
- 是否影响存档
- 是否影响提示词
- 是否影响资源目录
- 是否还存在后续待收敛点

## 9. 对后续结构治理的特殊要求

如果需求涉及结构规范化、平台适配、双端准备，应优先考虑：
- 是否可以先补架构文档
- 是否应该先抽适配层
- 是否可以先收敛状态判断，再移动 UI
- 是否可以先收敛目录，再逐步迁移代码

禁止直接进行无计划的大重构。

## 10. 推荐的长期工作方式

建议长期采用以下节奏：
1. README 定总规则
2. architecture 文档定结构规则
3. requirements / plans 文档承接中大型需求
4. 新功能按规范落位
5. 旧逻辑逐步迁移，不一次性推翻

本文档用于减少后续 AI 的随机性，让需求分析、文档落位、代码实现与结构治理形成统一流程。
