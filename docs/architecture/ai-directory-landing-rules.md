# AI 目录落点执行规则

## 目的

这份文档用于指导后续 AI 会话在实际改代码时，如何应用目录规范，而不是只停留在阅读架构说明。

## 每次动代码前必须先做的判断

在新增文件、抽模块、迁移逻辑之前，先明确三件事：

1. 这段代码的主要职责是什么。
2. 它属于 `app / domain / platform / ui / shared` 的哪一层。
3. 这次是否需要保留旧路径兼容层。

如果不能明确回答，不应直接创建新文件或大面积改动旧文件。

## 执行顺序

推荐按以下顺序执行：

1. 先确认模块职责。
2. 再选目标目录。
3. 再决定是直接新建、还是“新目录真实现 + 旧路径兼容壳”。
4. 最后才开始改调用方。

## 新增文件默认规则

### 新平台能力

默认放：`publish/platform/`

适用：
- 存储
- 资源访问
- 可用性判断
- 桥接接口
- 平台特定读写

### 新玩法规则

默认放：`publish/domain/`

适用：
- 判定逻辑
- 状态修正
- 规则计算
- 领域 patch/helper

### 新展示适配

默认放：`publish/ui/`

适用：
- 展示字段拼装
- UI 筛选
- 页面派生值
- 纯交互状态

### 新编排入口

默认放：`publish/app/`

适用：
- 启动链路
- 多模块接线
- 恢复流程组合
- 跨系统调用顺序控制

### 新通用工具

默认放：`publish/shared/`

前提：
- 与具体玩法无关
- 与具体平台无关
- 与具体页面无关

## 兼容迁移规则

当旧文件已经被很多地方引用时，不要直接粗暴搬走。

优先使用：

1. 新目录文件承载真实实现。
2. 旧文件保留为薄兼容层。
3. 调用方按小批量逐步迁移。

## AI 会话必须遵守的落位限制

- 不要因为“暂时方便”就把新平台能力继续写回 `publish/` 根目录。
- 不要因为函数来自旧文件，就默认新逻辑也必须继续塞回旧文件。
- 不要新建一个职责混杂的文件同时承载 `app + domain + platform + ui`。
- 不要把 `shared/` 当成分类不清时的垃圾桶。
- 不要一轮里同时做大搬迁、重命名、玩法改动三件事。

## 中文文件与编码协作规则

- 修改中文文档或含大量中文字符串的代码前，先确认文件真实编码，不要只看终端显示。
- PowerShell 显示乱码时，优先视为显示问题，先用显式 UTF-8 方式复核。
- 对中文较多的文件，优先做小范围补丁；除非是在重建干净版本，否则避免整文件覆盖。
- 如果出现 `.bak`、`.bak2`、乱码副本或临时修复文件，不要把它们当正式结构继续扩展。

## 临时文件与仓库卫生规则

- `logs/` 下的运行日志默认不提交。
- 临时截图、调试导出、恢复副本不应混入正式目录。
- 保留备份文件必须有明确理由，并在计划或说明文档中注明。
- 当一个临时文件已经不再承担恢复价值，应在安全前提下尽快清理，避免误导后续会话。

## 本项目当前推荐策略

当前阶段优先策略是：

1. 新平台相关代码继续沉到 `publish/platform/`
2. 新规则 helper 继续沉到 `publish/domain/`
3. 旧高耦合文件先保留编排层身份
4. 需要兼容时，优先保留旧入口壳
5. 新文档优先写进 `docs/architecture/` 或 `docs/plans/`，不要写散

## 一次合格落地至少满足的结果

一次合格的目录规范化修改，至少应满足：

- 能说明为什么代码落在该目录
- 没有改变原本玩法逻辑
- 没有无必要扩大影响面
- 给后续 exe/apk 适配增加了稳定边界，而不是增加新耦合
- 没有把编码风险、临时文件和结构问题一起带进正式实现
