# First Compat Cleanup Candidate Ranking V2 (2026-07-12)

## 目的

在补齐 `calendar` 的长期定位判断后，对“首批 compat 清理候选排序”做第二版修正。

这份修正版的核心目标是避免一个误区：

- 某个模块越成熟，不一定越应该先删 compat

相反，有些模块成熟到一定程度后，更适合被认定为“稳定 facade 样板”，而不是继续作为首删试点。

## 与第一版相比的关键修正

第一版中，`calendar` 因为成熟度高，被排在“最接近进入 compat 删除 gate 评估”的位置。

在补齐以下证据后：

- 模板主显示面收敛情况
- 模板外调用面审计
- 最小验证方案
- 长期定位判断

当前结论已经发生细化：

- `calendar` 更像“高成熟度稳定 facade 样板”
- 不再适合作为首批优先删除 compat 的对象

## 修正后的当前排序结论

### 第 1 位：skills

当前定位：`最适合作为首批真实 compat 删除候选评估的轻量模块`

理由：

1. 只读查询面已完成桥接
2. 模板消费区域集中
3. Web / Android 镜像消费一致
4. 相比 `prompt`，轻交互复杂度更低
5. 相比 `calendar`，它仍明显带有“迁移后可以继续压缩旧公开面”的过渡特征

当前仍缺：

- 动作面与只读面进一步拆分策略
- `skillsState.detailOpen` 等模板状态依赖的长期处理方式
- 删除前的最小验证方案

结论：

- `skills` 当前是最适合进入“首批真实 compat 删除候选评估”的第一候选

### 第 2 位：prompt

当前定位：`次优先的轻交互 compat 删除候选评估模块`

理由：

1. 只读展示面已桥接
2. 模板区块集中
3. Web / Android 镜像结构对齐
4. 轻交互复杂度高于 `skills`，但远低于 `boss`、`taobao`

限制：

1. 详情弹层与筛选状态交互较多
2. `promptState` 的模板直接依赖仍较明显

结论：

- `prompt` 适合作为第二优先的轻交互删除候选评估模块
- 但应排在 `skills` 后面

### 第 3 位：calendar

当前定位：`稳定 facade 样板模块`

理由：

1. 模板主显示面已较成熟地收敛到 `calendarPanelView()` + `changeCalendarMonth(delta)`
2. 存在模板外公开能力与跨模块运行时调用
3. 当前薄 facade 的结构负担已经很低
4. 继续强求删除 compat 的收益，可能不如直接认定为稳定 facade 来得高

结论：

- `calendar` 不再是首批优先删除 compat 的对象
- 当前更适合作为“哪些 facade 应长期保留”的样板

### 第 4 位：boss

当前定位：`复杂模块展示/派生面收口样板`

理由：

1. 一批只读展示/派生入口已桥接
2. 证明复杂模块也能沿 compat facade 路线收薄

限制：

1. 预约、申请、生成、公司同步等动作链仍复杂
2. 模板消费面广
3. 高副作用路径显著多于轻量模块

结论：

- `boss` 当前仍应停留在“收口优先、删除后置”的阶段

### 第 5 位：taobao

当前定位：`长期收口模块`

理由：

1. 桥接已落地一批
2. 模块实现已分散到 `actions` / `domain` / `viewHelpers`

限制：

1. 模板消费面极广
2. 筛选、详情、购买、结果展示等路径交织明显
3. 删除前需要更重的模板迁移与回归成本

结论：

- `taobao` 当前最不适合作为首批 compat 删除试点

## 当前阶段推荐路线（V2）

### 第一阶段：首批真实候选评估

优先顺序：

1. `skills`
2. `prompt`

目标：
- 在轻量、集中、低副作用模块中，真正开始评估哪一组 compat 入口未来可以进入局部删除候选

### 第二阶段：稳定 facade 样板沉淀

优先模块：

1. `calendar`

目标：
- 把“成熟 facade 不必继续硬删”的判断固化下来
- 避免后续误把成熟公开面当成必须继续压缩的旧残留

### 第三阶段：继续收口但不优先删的模块

优先顺序：

1. `boss`
2. `taobao`

目标：
- 继续扩展示示/派生面桥接覆盖
- 删除讨论仍后置

## 当前总判断

第二版排序的最大变化不是简单调换顺序，而是调整了一条更重要的原则：

- “最成熟”不等于“最该先删”
- “最像稳定公开面”的模块，应优先被认定为 facade 样板，而不是硬拉进删除试点

## 当前结论

如果当前必须给出一版更稳妥的排序：

1. `skills`：首批真实 compat 删除候选评估第一名
2. `prompt`：首批真实 compat 删除候选评估第二名
3. `calendar`：稳定 facade 样板，不再优先按删除候选推进
4. `boss`：复杂模块展示面收口样板
5. `taobao`：长期收口模块，当前不宜提早进删除阶段

这份修正版排序意味着：

- 后续若要真正挑一个开始进入“局部 compat 删除评估”的模块，优先看 `skills`
- `calendar` 则更适合作为“哪些公开面应该长期保留”的正面样板
