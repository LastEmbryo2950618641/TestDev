# Module Migration Priority Ladder（2026-07-11）

本文档用于给后续 AI 会话或人工协作者一个更可执行的迁移顺序判断：

- 先改哪个模块最划算
- 为什么它应该排在前面
- 哪些模块只适合继续做展示层收口
- 哪些模块在当前阶段更适合先稳住、补文档或做风险清点

它服务的核心目标不是“平均推进所有模块”，而是：

- 保证低耦合
- 提高代码复用性
- 保持逻辑玩法不变
- 降低关联性影响风险
- 为 Windows exe / Android apk 的多端复用做准备
- 让目录规范化按低风险顺序推进

## 1. 优先级判定原则

### P0：优先继续推进的模块应同时满足

- 已有真实 helper 落点
- 已有兼容壳
- 模板已有真实消费
- 当前还能找到相邻的纯展示切口
- 不需要为了推进而碰初始化 / 同步 / 写回主链

### P1：可推进但要更谨慎的模块通常表现为

- 已有样板雏形，但模板消费还不连续
- 展示层与旧主链挨得很近
- 模块本身数据结构复杂，容易误碰状态逻辑
- 文档已有边界说明，但停手点仍不够稳定

### P2：当前应冻结或只补文档的模块通常表现为

- 还没有清晰 helper 落点
- 主链、状态写回、恢复链和展示层严重纠缠
- 文件存在明显编码污染或历史语法污染
- 一旦动手就容易从“展示层改造”滑向“主链重排”

## 2. 当前优先级清单

### 第一梯队：继续优先推进

#### `real-world`

原因：

- 当前最成熟的模块级展示层样板
- 已有多主题 helper 文件
- 已有跨多个消费点的复用证据
- 与未来多端共用展示规则最直接相关

适合继续推进：

- title / subtitle / summary / badge / empty-state
- facts / room / interior / control 相关只读展示包装
- 已在多个读链重复出现的展示拼装逻辑

当前不要碰：

- cache 主链
- map fog 写回语义
- 地点推理 / 补齐 / 纠偏逻辑
- 任何运行时交互状态管理

结论：

`real-world` 仍然是“展示层标准答案”优先参考模块。

#### `wechat`

原因：

- 当前是最丰富的“相邻展示岛逐块收口”真实样板
- 联系人、线程、资料卡、相册、裁剪弹层等都已形成连续展示收口证据
- 很适合继续验证“模板里零散展示文案如何逐块回收到 helper”

适合继续推进：

- profile / album / dialog / toolbar / card / row 的只读展示字段
- 模板里仍然写死的空态、标题、副说明、按钮文案
- 相邻展示区域的小步替换

当前不要碰：

- 消息收发主链
- 图片处理主链
- 同步、记忆写回、异步装配
- 任何跨页面隐式状态修改

结论：

`wechat` 适合继续做“高频 UI 模块的渐进展示层收口”主样板。

#### `faction`

原因：

- 已完成连续多刀跨模块复制验证
- 列表、详情、档案、结构区、org chart 模态都已有真实样板
- 很适合继续验证“组织/档案/模态类 UI 也能低风险收口”

适合继续推进：

- 详情头部、badge、empty-state、row、modal header
- 模板里仍然内联的只读标题、说明、按钮文案
- helper 返回更完整展示对象的区域

当前不要碰：

- `initFactionSystem()`
- `syncCompanyFaction()`
- `normalizeFactionStructure()`
- 曝光评分、组织关系、company / territory / membership 同步链

结论：

`faction` 是当前最适合做“跨模块复制验证”的样板模块。

### 第二梯队：适合小步推进，但不要深拆

#### `event`

原因：

- 已经证明“已有规则中心 + 渐进 UI 收口”成立
- `eventSystem` 当前就是事实上的规则中心
- 展示层 helper 路线清晰，但继续深拆的收益已经开始下降

适合继续推进：

- 页头、详情、空态、按钮、标签等最后一层展示文本
- 仍然写死在模板里的小块只读文案

当前不要碰：

- `eventSystem` 的规则承接职责
- 事件抽取、草稿写入、随机触发、prompt 主链
- 为了目录对称性强行新建 `domain/event`

结论：

`event` 适合作为“轻量标准样板”，但不适合再作为高优先级深挖模块。

#### `critical-action`

原因：

- 已有纯展示 helper 抽离样例
- 更适合继续做 text / metric / log 等只读展示规则收口
- 有机会成为另一类“AI 推演相关页面展示层”样板

适合继续推进：

- text helper
- metric / dialog / novel log 的纯展示切面
- fallback block 里的只读拼装逻辑

当前不要碰：

- AI prompt 主链
- 推演结果写回
- 复杂 fallback 行为重排

结论：

`critical-action` 适合作为第二梯队候选模块，按小块验证推进。

### 第三梯队：当前更适合先补边界和风险清点

#### `loading / save / storage / restore`

原因：

- 这些模块天然与初始化、恢复、持久化、兼容层强耦合
- 即使存在 helper 抽离空间，也更容易误碰主链
- 更适合作为“先画边界、后动代码”的模块

当前更适合做：

- 文档补边界
- 恢复链 / 存档链 / 持久化责任地图
- 高风险旧文件的最小切口规划

当前不适合做：

- 大范围目录迁移
- 兼容层重写
- 初始化顺序重排

#### `control / online / link / body-figure / platform-key`

原因：

- 往往同时牵涉平台状态、身份链、配置链或在线控制链
- 很容易从展示层问题滑向规则和写回问题
- 当前更需要先做风险分层与编码稳定化

当前更适合做：

- 边界梳理
- 风险点清单
- 小型 helper 候选审计

## 3. 推荐推进顺序

如果后续目标仍然是“低风险推进 + 多端复用准备”，默认推荐顺序如下：

1. `real-world`
2. `wechat`
3. `faction`
4. `event`
5. `critical-action`
6. 其他高耦合模块先补文档，再决定是否动代码

这个顺序的原因是：

- 前三者已经具备最强的样板复用价值
- `event` 已验证成立，但继续深挖边际收益较低
- `critical-action` 有潜力，但当前样板密度还不如前四者
- 高耦合模块如果没有先梳理边界，直接开改更容易破坏玩法和兼容性

## 4. 每轮改造前的快速决策问题

开始改某个模块前，先回答这 5 个问题：

1. 这次是不是只读展示问题？
2. 是否已经有 `publish/ui/<module>/...` 落点？
3. 旧入口能否保留为兼容壳？
4. 模板能否在本轮真实切过去？
5. 如果继续做，会不会误碰初始化 / 同步 / 写回 / 恢复主链？

如果前 4 个答案大多是“是”，第 5 个答案是“否”，就适合继续推进。

## 5. 停手信号

出现以下情况时，默认停止继续深拆，转去补文档或换模块：

- 下一刀已经不再是相邻展示切口
- 为了继续推进，必须修改初始化 / 同步 / 恢复 / 写回主链
- 需要新建目录只是为了对称，而不是因为职责真的分离了
- 模块已形成样板，但继续深挖对多端复用帮助有限
- 历史编码或语法污染已经开始影响稳定编辑
