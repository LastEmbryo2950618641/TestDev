# 多端复用边界说明

本文档说明当前项目在未来支持 `window exe` 与 `安卓 apk` 时，应如何划分可复用层与平台相关层，以避免业务逻辑与平台实现继续耦合。

## 1. 目标

在保证现有玩法逻辑不变的前提下，逐步形成：
- 可被桌面端与移动端共同复用的业务层
- 可独立替换的桌面/移动平台适配层
- 不依赖特定宿主环境的状态判断与规则层

## 2. 推荐分层

### A. 业务规则层
这层未来应尽量双端复用。

适合归入这一层的内容：
- 控制状态判断
- 角色状态规则
- 上线 / 下线 / 召唤规则
- 上线体验规则
- 提示词注入规则
- 现实推演规则
- 结算规则

特点：
- 不直接访问平台文件系统
- 不直接依赖浏览器以外的宿主能力
- 不直接持有平台专属路径

### B. 前端展示层
这层在桌面与移动端大部分也可复用，但允许少量容器差异。

适合归入这一层的内容：
- 页面模板
- UI 状态展示
- 用户输入交互
- 页面级组合逻辑

特点：
- 可复用大部分展示逻辑
- 不直接承担平台能力实现

### C. 平台适配层
这层不复用业务，而是按平台分别实现。

适合归入这一层的内容：
- 本地文件读写
- 用户生成资源写入
- key 管理
- 本地数据库落点
- dev-only 本地接口
- 宿主通信
- 平台能力探测

## 3. 当前项目中的第一批平台依赖点

当前项目已知的高优先级平台依赖包括：
- `dev/scripts/dev-server.cjs`
- `publish/body-figure.js` 中依赖的 `__dev/*`
- key 文件读取逻辑
- 运行时生成资源写入逻辑
- `window.dzmm` 等宿主能力

这些能力不适合继续直接散落在业务代码中。

## 4. 当前最适合优先双端复用的部分

建议优先双端复用的第一批能力：
- `control-state`
- 控制域相关的只读状态判断
- 首页与角色列表的状态摘要逻辑
- 提示词阶段判断规则
- 不依赖平台文件系统的角色/世界状态规则

原因：
- 这些逻辑本质上属于业务规则，不依赖桌面/移动端差异
- 越早收敛，越能减少后续双端重复实现

## 5. 不应立即强行抽成双端复用的部分

以下部分当前不建议立刻做双端统一实现：
- 本地文件落盘细节
- 存档最终落点实现
- 图片生成资源保存路径
- 调试开发服务器能力
- 宿主桥接具体 API

这些更适合先定义接口边界，再按平台分别实现。

## 6. 当前阶段的现实策略

推荐顺序：
1. 先收敛业务状态判断与规则逻辑
2. 再收敛平台边界
3. 最后再接桌面壳与移动壳

这样可以避免过早把平台能力绑进业务层。

## 7. 对目录规范化的影响

未来目录规范应支持以下分层：
- 入口层
- 功能域层
- 平台层
- 共享层
- 文档层

建议后续逐步往以下方向收敛：
- `publish/control-*`
- `publish/real-world-*`
- `publish/prompt-*`
- `publish/storage-*`
- `publish/platform-*`

现阶段不要求一次性搬迁，但新增逻辑应尽量贴近这类分类。

## 8. 与当前重构的关系

当前阶段一控制域收敛，属于“双端复用的前置工作”。

原因：
- 它先把控制状态判断从入口与页面中抽出
- 让状态判断变成更纯粹的业务逻辑
- 后续桌面壳与移动壳只需要消费统一状态，而不是各自再写一套判断

## 9. 结论

当前最合理的多端路线不是直接做 `exe / apk` 工程，而是：
- 先完成结构规范化
- 再完成业务层状态与规则收敛
- 最后再补平台适配层

这样才能同时满足：
- 低耦合
- 高复用
- 玩法不变
- 风险可控
- 双端可演进
