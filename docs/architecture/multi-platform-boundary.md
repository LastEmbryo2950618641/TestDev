# 多端复用边界说明

本文档说明当前项目在未来支持 `window exe` 与 `安卓 apk` 时，应如何划分可复用层与平台相关层，以避免业务逻辑与平台实现继续耦合。

## 1. 目标

在保证现有玩法逻辑不变的前提下，逐步形成：
- 可被桌面端与移动端共同复用的业务层。
- 可独立替换的桌面 / 移动平台适配层。
- 不依赖特定宿主环境的状态判断与规则层。

## 2. 推荐分层

### A. 业务规则层

这层未来应尽量双端复用。

适合归入这一层的内容：
- 控制状态判断。
- 角色状态规则。
- 上线 / 下线 / 召唤规则。
- 提示词阶段规则。
- 资源选择规则。

要求：
- 不直接读取本地文件。
- 不直接调用 dev-only 接口。
- 不直接判断桌面端或移动端差异。

### B. 应用装配层

这层负责把业务层、平台层、UI 层接起来。

适合放：
- 启动装配。
- 模块注册。
- 运行时桥接。
- 全局注入关系。

### C. 平台适配层

这层负责平台相关实现。

适合放：
- 文件系统访问。
- 图片保存。
- key 读取。
- 本地服务接口。
- 宿主桥接。
- 平台差异判断。

这层未来可以按宿主替换，例如：
- Windows 桌面壳实现。
- Android WebView / Capacitor 实现。
- 开发环境 dev server 实现。

## 3. 当前项目中的平台风险点

当前重点需要逐步收口的地方包括：
- 本地 key 文件读取。
- 用户生成资源落盘。
- dev-only 资源接口。
- 依赖固定路径的资源访问。

这些能力如果继续散落在业务模块里，会直接阻碍后续 exe / apk 复用。

## 4. 当前演进策略

当前不直接做双端完整适配，而是先做以下准备：

1. 统一平台入口。
2. 让业务层只依赖平台接口，而不依赖具体实现路径。
3. 逐步把桌面开发环境能力收进 `platform` 层。
4. 为未来移动端桥接预留替换点。

## 5. 验收标准

如果某项重构满足以下条件，就说明它朝多端复用前进了一步：
- 玩法逻辑未改变。
- 平台路径或文件能力不再散落在业务层。
- 同一能力有统一入口。
- 替换宿主时只需要改平台层，而不是回改业务层。

## 6. 当前建议优先级

建议后续继续优先处理：

1. key 读取入口。
2. body figure 资源链路。
3. 存档 / 持久化边界。
4. 宿主能力接口。
5. 双端通用的模块命名与目录承载。

本文档的目标不是立即完成跨端，而是先把未来跨端一定会卡住的耦合点提前拆开。
