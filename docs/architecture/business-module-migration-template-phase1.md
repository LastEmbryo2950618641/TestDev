# 业务模块迁移模板（阶段 1）

本文档将当前已经在 `taobao`、`wechat`、`real-world`、`company` 中验证过的低风险迁移方式，整理为后续任何业务模块都可直接套用的模板。

目标不是要求所有模块一步到位拆成完全一致的层数，而是提供一套：

- 低耦合
- 低回归风险
- 保持玩法不变
- 兼容旧入口
- 便于未来 `window exe` / `android apk` 复用

的默认迁移方法。

## 1. 适用范围

适用于当前 `publish/` 下的业务模块，例如：

- `taobao`
- `wechat`
- `real-world`
- `company`
- 未来的 `settings` / `save` / `loading` / 其它 app 模块

不适用于：

- 编码已损坏且尚未重建的文件
- 高耦合大文件中未经校验的中文异常片段
- 尚未识别出清晰边界的深层副作用链

## 2. 迁移总原则

后续业务模块迁移默认遵循以下原则：

1. 先拆只读展示 helper。
2. 再拆只读规则 / 状态 helper。
3. 最后再拆流程装配层。
4. 高风险副作用链放到最后，且不要求每个模块都必须继续深拆。
5. 旧入口优先保留兼容壳，不做一次性硬迁。

核心思想：

- 先把“可安全复用”的逻辑沉下去。
- 把“有副作用的执行链”留在原位，直到边界足够清晰。
- 结构演进服务于风险降低，而不是目录整齐本身。

## 3. 推荐拆分顺序

### 第一阶段：`ui/<module>/`

优先迁移内容：

- 面板展示文案
- 列表摘要拼装
- 选中态展示派生
- 只读展示数组/对象拼装
- 与按钮文案、标签文案、状态展示直接相关的 helper

不要迁移：

- 状态写回
- 文件读写
- AI 请求
- 消息发送/接收
- 存档
- 复杂规则判定

阶段目标：

- 先把“看什么、怎么显示”从旧入口抽出去。
- 让旧入口开始变成兼容壳。

### 第二阶段：`domain/<module>/`

优先迁移内容：

- 状态读取入口
- 轻规则判断
- 只读状态派生
- 标准化 helper
- 购买前/生成前的纯判断
- 与平台无关的业务规则

不要迁移：

- DOM 操作
- 平台接口
- 保存时机
- 资产同步
- 高风险副作用主链

阶段目标：

- 把“业务上怎么判断”从旧入口中沉下去。
- 让 `ui` 主要消费 `domain` 输出，而不是复制判断。

### 第三阶段：`app/<module>/`

优先迁移内容：

- 流程装配
- 顺序控制
- 请求循环壳
- 轻量动作入口
- 进入高风险主链前的流程门槛

不要迁移：

- 纯展示 helper
- 纯规则 helper
- 尚未识别清楚边界的副作用深链

阶段目标：

- 把“先做什么，再做什么”的 orchestration 从旧入口中拆出去。
- 让旧入口进一步变成兼容转发层。

### 第四阶段：高风险副作用链

只有当以下条件满足时才考虑继续：

- 前三层已经比较稳定
- 状态入口清晰
- 文案与规则已下沉
- 该副作用链边界足够明确
- 这一轮不会同时夹带大范围玩法改动

常见高风险部分：

- 库存更新主链
- 财富扣减
- 资产同步
- 存档时机
- 消息发送/接收
- 记忆写回
- 多系统联动结算

阶段目标：

- 不追求每个模块都必须拆到这一层。
- 如果继续拆会明显提高风险，可以停在 `ui + domain` 或 `ui + domain + app`。

## 4. 兼容迁移模式

默认模式：

1. 在新目录创建真实实现。
2. 保留旧入口文件。
3. 把旧入口改成薄转发壳。
4. 在 `script-manifest` 中先加载真实实现，再加载旧入口。

推荐结果：

- 新文件是真实实现。
- 旧文件负责兼容调用点。
- 运行时行为保持稳定。
- 后续可以渐进继续收口，而不是一次性大搬迁。

## 5. 是否该停手的判断标准

以下情况说明当前模块应暂时停手，而不是继续硬拆：

- 剩余逻辑主要是高风险副作用链
- 没有清晰、低风险的 `app` 切面
- 继续拆分只是为了层数好看
- 当前剩余函数明显既不是纯 UI，也不是纯 domain，也不是清晰 app 流程
- 会把玩法改动和结构改造绑在同一轮里

这类情况下，应在边界文档中明确写出：

- 当前停在什么阶段
- 为什么停在这里
- 后续要等待什么条件再继续

## 6. 每轮迁移最小交付物

每完成一轮模块迁移，至少应交付：

- 新真实实现文件
- 旧入口兼容转发
- `script-manifest` 同步
- 对应目录 README（首次进入该目录时）
- 对应边界文档或阶段说明

如果缺少这些，后续接手成本会明显升高。

## 7. 最小验收标准

一轮迁移至少要满足：

- 原功能逻辑不变
- 旧入口仍可被现有调用链使用
- 新文件已被 manifest 正确加载
- 新 helper 的职责比旧入口更单一
- 没有把高风险副作用链误搬进 `ui` 或 `domain`
- 边界文档说明了哪些还没有动

## 10. 当前推荐优先级

如果后续继续批量推进，优先顺序建议为：

1. 在已成型样板上继续巩固边界
2. 在第二样板上补强到稳定阶段
3. 再复制到第三个边界清晰模块
4. 最后才考虑高耦合大文件的深层迁移

本文档的目的，是让后续模块规范化从“凭经验推进”变成“按模板推进”，在不牺牲玩法稳定性的前提下，持续提高项目的复用性与可迁移性。

## 11. 已有样板继续扩展场景

并不是所有模块都需要从“新建 `ui/domain/app` 目录”开始。

当前已验证另一种同样重要的迁移场景：

- 模块已经存在 `ui/<module>/` 样板
- 后续继续把新的只读 helper 追加到已有真实实现中
- 旧入口继续转发到同一个真实实现文件
- 不需要新增 manifest 文件项

已验证示例：

- `settings`
- `save`（当前已确认有 `ui/save` 基础，但不适合本轮继续深拆高耦合后段）

这种场景下，推荐策略是：

1. 先确认现有 `ui/<module>/` 是否已经在加载链中。
2. 只追加真正的只读展示 helper。
3. 不因为“已有 ui 样板”就误以为整个模块都适合继续深拆。
4. 如果旧入口后段已经混入高耦合业务链，允许在边界文档里明确停手。

## 12. 结构基础已足够清晰的模块

还有一类模块，不属于“继续深拆收益高”的对象。

特征：

- 已经存在 `ui/<module>/` 与 `app/<module>/` 明确样板
- 剩余逻辑主要靠近高敏感主链
- 再继续拆分的主要风险是运行时故障，而不是代码阅读成本

已验证示例：

- `loading`

这类模块的默认策略应改为：

1. 优先维持稳定。
2. 等具体问题出现时，再围绕具体问题做最小切口。
3. 不为了“层数更完整”继续主动重构。

## 13. 已有 system 对象已承担 domain 角色的模块

还有一类模块，并不是没有 domain，而是规则已经集中在独立的 `*System` 对象中。

特征：

- 旧入口主要负责状态读写与触发
- 模块内已经存在类似 `eventSystem` 这样的独立规则中心
- 规则标准化、类型归一、时间判断、匹配评分等能力已经有集中承载点

已验证示例：

- `event`

这类模块的默认策略应为：

1. 先把只读展示 helper 收进 `ui/<module>/`。
2. 先承认现有 `*System` 已承担部分 domain 角色。
3. 不为了目录一致性强行再建一层 `domain/<module>/`。
4. 只有当状态入口、只读规则或跨文件复用需求明显增多时，再评估是否拆出单独的 domain 目录。
