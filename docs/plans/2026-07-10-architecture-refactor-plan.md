# 2026-07-10 结构规范化与双端准备重构计划

## 1. 背景与目标

当前项目已经具备较多功能模块，但代码组织仍然存在以下问题：
- 全局入口与业务逻辑耦合较高，`publish/game.js` 承载过多职责
- 同一业务状态在多个文件中重复判断，容易导致首页、控制列表、流程页展示不同步
- 平台能力（本地文件、dev server、宿主能力）与业务逻辑耦合，后续会阻碍 `exe / apk` 演进
- 资源、提示词、存档、运行时生成物的边界尚未完全收敛

本次重构目标不是大重写，而是建立一条可渐进推进的结构治理路线，满足以下目标：
- 保持当前功能逻辑尽量稳定
- 提升状态判断的一致性
- 提升代码可读性、复用性与可维护性
- 为后续桌面壳、移动壳和平台适配层预留清晰边界

## 2. 总体原则

本次重构遵守以下原则：
- 先规划、后实施，不边改边决定结构
- 先收敛状态判断，再迁移 UI 与动作逻辑
- 先抽功能域，再抽平台适配层
- 每次只重构一个清晰边界，避免跨系统大爆破
- 优先保证现有功能行为不变，再优化内部结构
- 新结构先加、旧逻辑后迁，允许过渡期并存

## 3. 当前主要问题拆解

### 3.1 状态问题
- 当前连接目标、是否已上线、首页显示、列表按钮状态等判断分散在多个文件
- `online` 等字段在不同语义下被复用，容易误导展示逻辑
- 缺少统一的“权威状态来源”层

### 3.2 模块问题
- `publish/game.js` 更像总装配和总状态容器，但仍承载过多业务判断
- `control` 相关逻辑分散在 `game.js`、`core-actions.js`、`control-link-actions.js` 和页面模板中
- 部分系统的 UI、状态、动作、规则边界还不够清晰

### 3.3 平台问题
- `dev/scripts/dev-server.cjs` 提供本地开发与部分业务所需能力
- `body-figure`、key 文件、运行时生成资源等依赖本地实现
- 如果未来做 `exe / apk`，这些能力必须从业务中抽离出来

## 4. 总体阶段计划

本次重构建议拆成三个阶段。

### 阶段一：控制域收敛
目标：
- 把“当前控制目标、连接状态、首页显示、角色列表按钮状态”统一到一个控制域
- 不改玩法，只统一状态读取和职责边界

范围：
- 当前连接目标状态
- 首页显示状态
- 控制角色列表的按钮状态
- 上线 / 下线 / 召唤流程的状态依赖

产出：
- 统一的控制状态模块
- 更明确的控制动作边界
- 首页与列表不再各自猜测状态

### 阶段二：平台边界收敛
目标：
- 将平台能力从业务中剥离，建立适配层骨架

范围：
- 本地文件读写
- key 管理
- `__dev/*` 接口
- 用户生成资源写入
- 宿主通信

产出：
- adapter 设计草案
- 至少一层平台能力抽象入口
- 业务代码减少对桌面本地实现的直接依赖

### 阶段三：系统级结构规范化扩展
目标：
- 将其他高频模块逐步按功能域收敛

优先顺序建议：
1. `control-experience`
2. `prompt`
3. `storage`
4. `body-figure`
5. `real-world`

产出：
- 功能域逐步清晰化
- 模块职责更稳定
- 后续大功能接入有固定落位

## 5. 阶段一细分计划

### 5.1 子目标
- 定义“当前真正控制目标”的权威来源
- 统一首页与控制角色列表的显示逻辑
- 明确“链接 / 已连接 / 上线 / 下线 / 召唤”的状态关系
- 避免一个页面用 `online`、另一个页面用 `sharedControlTargetId`、第三个页面用日志推断

### 5.2 预计拆分方式
建议将控制域拆成以下几个层次：
- `control-state`：只负责状态判断与只读衍生值
- `control-actions`：只负责控制流程动作
- `control-ui`：页面展示所需的统一文案、按钮态、摘要态

说明：
- 第一阶段不一定一次性拆完 `control-ui`，但应先完成 `control-state`
- 所有页面和动作逻辑先改成优先读取 `control-state`

### 5.3 低耦合策略
- 页面不直接拼装状态，统一读控制状态模块
- 动作逻辑不自行决定展示态，展示态由状态模块计算
- 状态模块只读 store，不直接操作 DOM
- 尽量不让 `index.html` 拥有复杂条件组合判断
- 先把“权威来源”抽出来，再逐步迁移消费方

### 5.4 代码复用策略
- “当前控制目标是谁”“某角色是否为当前连接目标”等判断只保留一套方法
- 首页卡片、角色列表、现实世界展示共用同一套控制目标判断
- 后续如新增状态标签、顶部状态栏、角色详情栏，也复用控制状态模块

### 5.5 风险点
- 已有流程依赖老字段含义，收敛时容易误伤页面显示
- 若状态收敛过快，可能造成某些过渡页面显示异常
- 部分功能与 `sharedControlActive`、`started`、`online` 的语义混用，需要谨慎区分

### 5.6 验收标准
- 首页与控制角色列表显示的“当前连接对象”一致
- 当前已连接角色按钮显示“已连接”且不可再次点击
- 非当前角色仍可切换
- 一次只存在一个当前控制目标
- 不改变现有上线、下线、召唤的原有行为结果

## 6. 阶段二细分计划

### 6.1 子目标
- 识别所有平台能力入口
- 将平台能力与业务逻辑分离
- 保证未来 `exe / apk` 共用业务层成为可能

### 6.2 预计适配层方向
建议逐步形成以下抽象：
- `fileAdapter`
- `storageAdapter`
- `hostAdapter`
- `aiAdapter`

### 6.3 低耦合策略
- 业务文件不直接访问本地文件系统细节
- 业务文件不直接依赖 dev-only 接口路径
- 平台差异集中在适配层，不在多个业务模块重复出现

### 6.4 风险点
- 适配层抽象过早过深会增加短期复杂度
- 某些现有实现本身耦合严重，需要分步抽离而不是一次性搬空

## 7. 阶段三细分计划

### 7.1 子目标
- 将高频改动模块逐步向功能域结构收敛
- 减少“一个需求同时在多个不相关脚本硬插代码”的情况

### 7.2 收敛顺序原因
- `control-experience`：与当前主玩法密切相关，规则和提示词耦合度高
- `prompt`：提示词本身是代码资产，需要从散落状态变成明确系统
- `storage`：牵涉存档兼容，后续要为平台迁移做准备
- `body-figure`：涉及生成资源、平台文件能力、运行时资源
- `real-world`：系统庞大，适合在前几个高风险点稳定后再收敛

## 8. 模块边界建议

建议后续长期收敛成以下结构思路：
- 入口层：装配、初始化、脚本加载
- 功能域层：control / character / real-world / prompt / storage 等
- 平台层：桌面/浏览器/移动端能力适配
- 共享层：工具、常量、schema、通用 helper

## 9. 不做事项

本次重构明确不做以下事情：
- 不一次性全量迁移所有系统
- 不同时重构所有提示词结构
- 不在没有验证的情况下直接改成 `exe / apk` 工程
- 不为了目录漂亮而先做大搬迁
- 不追求一次性消灭所有历史结构

## 10. 推荐执行顺序

建议按以下节奏推进：
1. 先完成阶段一，并单独提交
2. 阶段一稳定后，再开始阶段二骨架
3. 阶段二形成最小平台边界后，再逐步进入阶段三
4. 每一阶段结束后都进行回归检查与说明
