# Validation Document Template

> 文件位置建议：`docs/plans/YYYY-MM-DD-<topic>-validation.md`

## 1. 验证目标

用 1 到 3 句话说明本轮验证要证明什么。

建议明确：

- 这是在验证哪一刀改造
- 想证明的是“行为不变”“边界更清晰”还是“模式可复制”
- 是否属于低风险结构化改造验证

## 2. 本轮验证切口

说明这次实际验证的最小切口。

建议写清：

- 改的是哪个 helper / 哪个模板区域 / 哪个兼容壳
- 为什么选它作为本轮切口
- 为什么它属于低风险范围

## 3. 真实落点

列出本轮验证涉及的真实文件：

- 真实实现文件
- 兼容入口文件
- 模板消费文件
- 边界文档 / 计划文档

## 4. 保持不变的内容

明确说明本轮刻意没有改变什么，例如：

- 初始化主链
- 同步 / 恢复 / 持久化写回
- 规则中心
- 平台能力
- 提示词或异步流程装配

这一节用于证明“低关联影响风险”不是口头描述，而是有明确停手边界。

## 5. 结果

总结这轮验证完成后，已经成立的事实。

建议写成结论句，例如：

- 模板已改为消费 helper 对象
- 旧入口已退化为兼容转发
- 某个模块已具备第一刀复制验证证据
- 某类逻辑更适合停留在当前层级，而不是继续深拆

## 6. 证据

至少列出本轮最小验证证据：

- helper 方法名可检索
- 兼容壳已存在
- 模板已实际消费 helper
- `node --check` 或等价最小语法验证已通过
- 边界文档 / playbook / 高层文档已同步

建议把证据写成可定位项，而不是笼统写“已验证通过”。

## 7. 风险评估

建议至少分两类：

- 已控制住的风险
- 仍然保留的风险

例如：

- 已控制：本轮只改只读展示逻辑
- 保留：旧 action 文件仍然体量大 / 有编码痕迹 / 后续深拆仍需谨慎

## 8. 未验证项

明确说明本轮还没有证明什么，避免把局部成功夸大成整体完成。

例如：

- 尚未验证跨读链复用
- 尚未验证多端真实运行效果
- 尚未验证存档兼容层
- 尚未验证更深层 domain / app 演进

## 9. 后续建议

说明下一步最自然的推进方式。

建议写成：

1. 继续同模块做第二刀 / 第三刀
2. 回到文档层补成熟度或样板记录
3. 转去另一个模块做复制验证

## 10. 适用场景补充

如果本轮属于“模式验证”，建议加一句明确判断：

- 这是单模块内部收口验证
- 这是跨模块复制验证
- 这是已有规则中心下的第三类验证
- 这是高层文档回收验证
