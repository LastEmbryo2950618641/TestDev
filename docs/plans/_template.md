# Plan Document Template

> 文件位置建议：`docs/plans/YYYY-MM-DD-<topic>-plan.md`

## 1. 目标

用 1 到 3 句话说明本轮实现计划要解决什么问题。

建议写清：

- 这轮计划对应的真实需求是什么
- 本轮更偏功能实现、结构化改造，还是稳定化处理
- 想优先解决的是体验问题、复用问题、边界问题，还是风险问题

## 2. 涉及模块

列出本轮预计会改动的系统 / 模块 / 文件范围。

建议至少说明：

- 主功能域
- 可能受影响的辅助模块
- 是否涉及 `ui / domain / app / platform` 其中某一层
- 是否会触及旧大文件兼容壳

## 3. 权威状态来源

明确本轮依赖哪些状态，以及谁负责写入这些状态。

建议写清：

- 本轮依赖哪些核心状态字段
- 哪个字段是权威来源
- 谁负责更新该状态
- 哪些页面或读链会读取它

## 4. UI 与交互入口

说明用户从哪里进入该功能，以及页面上哪些区域会变化。

建议写清：

- 用户入口在哪里
- 会影响哪些页面、弹窗、面板或卡片
- 是否新增按钮、文案、流程或交互分支

## 5. 数据与持久化影响

说明本轮是否会影响数据结构、存档或运行时生成资源。

建议至少说明：

- 是否影响存档字段
- 是否新增状态字段
- 是否需要兼容旧数据
- 是否影响运行时生成资源或缓存

## 6. 提示词 / 规则影响

如果本轮涉及 AI 推演、提示词、阶段规则或数值规则，应说明：

- 改哪些提示词或规则
- 是否会影响其他阶段或其他系统
- 是否需要同步新增 / 修改规则文档

如果完全不涉及，也建议明确写“本轮不涉及提示词 / 规则调整”。

## 7. 风险点

列出本轮最主要的实现风险。

常见风险包括：

- 状态来源不一致
- 展示与真实状态不同步
- 存档兼容风险
- 平台能力耦合风险
- 历史编码 / 语法污染导致的编辑风险

## 8. 实施步骤

按顺序写出建议实施过程。

推荐写法：

1. 先确认最小切口与停手边界
2. 再落真实实现或稳定化处理
3. 再接兼容壳或模板消费
4. 最后补最小验证与文档同步

## 9. 验收步骤

说明完成后如何验证本轮计划已经达成。

建议至少覆盖：

- 主路径
- 边界情况
- 存档恢复或兼容影响
- 资源生成、模板消费或最小语法校验

尽量把验收写成可执行、可观察的检查项，而不是抽象描述。

## 10. 后续事项

记录这次不一定立刻完成，但后续应继续收敛的问题。

例如：

- 下一刀可继续推进的区域
- 当前刻意没有触碰的高风险链路
- 需要单独开验证文档或风险文档的事项

## 11. 低风险结构化改造补充检查

如果本轮属于目录规范化、helper 拆分、展示层收口或兼容迁移，请额外补齐以下内容。

### A. 本轮优先切口

说明本轮为什么先从以下类型切入：

- `title / subtitle / empty-state`
- `row` 列表对象
- `card / view object`
- 工具栏或弹窗展示对象

### B. 兼容策略

明确说明是否采用以下结构：

1. 新 helper 文件承接真实实现
2. 旧入口文件保留兼容转发
3. 模板逐步改为消费 helper 对象

### C. 本轮明确不碰的区域

至少说明本轮是否刻意避开以下高风险区：

- 消息发送与接收主链
- 记忆写回
- 同步、恢复、初始化入口
- 异步流程装配
- 跨页面隐式状态写入

### D. 停手条件

说明本轮遇到哪些情况就应停手，不继续深拆：

- 下一刀将进入写状态主链
- 需要同时修改多个高风险旧文件
- 编码风险或模板结构风险明显扩大
- 无法在当前轮提供最小验证证据

### E. 最小验证证据

建议至少列出：

- helper 方法名可检索
- 兼容壳入口存在
- 模板已实际消费 helper
- `node --check` 或等价最小语法验证通过
- 边界文档 / playbook / workflow 是否已同步
